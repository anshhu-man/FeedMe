# Today / My Plate client integration plan

14 September 2026. **Preparation only; no social client implementation or release acceptance is claimed.** This ordinary handoff was written during the ninth source freeze. It complements the existing [photo/composer backend plan](PHOTO_MEDIA_BACKEND_PLAN.md), [circle HTTP handoff](SOCIAL_HTTP_INGRESS.md) and [media processor plan](MEDIA_PROCESSOR_EXECUTION_PLAN.md); none is an existing retained Today/My Plate client plan. No source, contract, test, migration, runner or verification receipt is changed here.

## Intended next user-visible slice

After the cookbook-removal package, connect **HOME → TODAY → STORY** and **PROFILE_PLATE → POST** to actual authorized canonical responses, with explicit refresh, bounded pagination, expiry, Back and owner retention/removal controls. Today is chronological recent circle food; My Plate is retained social posts, **not** the private cookbook. Cooking, downloaded private recipes and existing cooking/timer state remain usable when social discovery is empty or unavailable.

The smallest first client checkpoint is placement reading plus truthful unavailable states. It must not populate a production feed with sample posts to conceal the missing server. Owner mutation and media checkpoints follow through the same retained owner. Full photo/text publishing, attachments, circles management and safety controls remain required V1 work, not cuts made by this sequencing. The [V1 scope](V1_RELEASE_SCOPE.md) still contains all 44 P1 features and excludes the ten existing later features, including clips, pacts, polls, potlucks and expanded collections. Their presence on a shared canonical screen is not permission to expose their actions.

## Canonical protocol, not older prose spellings

The [API JSON](../../outputs/biteclub_blueprint/architecture/04_API_Contract.json) and [screen registry](../../outputs/biteclub_blueprint/registry/screen_registry.json) are the wire/action authority. The reviewed feature requirements are [F21](../../outputs/biteclub_blueprint/features/F21.md), [F22](../../outputs/biteclub_blueprint/features/F22.md), [F23](../../outputs/biteclub_blueprint/features/F23.md), [F24](../../outputs/biteclub_blueprint/features/F24.md), [F31](../../outputs/biteclub_blueprint/features/F31.md), [F40](../../outputs/biteclub_blueprint/features/F40.md) and [F42](../../outputs/biteclub_blueprint/features/F42.md).

All post/placement/media-access operations below require UserBearer and the actual registered `X-Device-Session`. The public invitation-preview exception is not public post access.

| Purpose | Exact operation / route | Important binding |
| --- | --- | --- |
| Today | `getToday` — `GET /v1/posts/today` | Optional circleId, cursor, limit 1–50; `200 PostPage` with items, nullable nextCursor and serverTime. |
| Plate | `getProfilePlate` — `GET /v1/profiles/{userId}/plate` | Exact authorized navigation userId; cursor/limit; `200 PostPage`. Visiting a profile grants no audience permission. |
| Story/post | `getPost` — `GET /v1/posts/{postId}` | Query is **surface=today/plate/detail**, not `placement`. `200 Post` plus ETag. STORY uses today; a retained grid uses plate. detail is not an expiry escape hatch. |
| Retention/audience/caption | `updatePost` — `PATCH /v1/posts/{postId}` | Exact narrow `PostPatch`, original Idempotency-Key and If-Match; `200 Post` plus ETag. No field-blind automatic replay authority. |
| Delete | `deletePost` — `DELETE /v1/posts/{postId}` | Original Idempotency-Key and If-Match; actual empty204, not local disappearance or a fabricated tombstone response. |
| Protected derivative | `getMediaAccess` — `POST /v1/media/{mediaId}/access` | Body requires postId, surface and variant. Photo uses thumbnail/display. Response is url, expiresAt, aclVersion, contentType. **No Idempotency-Key or If-Match.** |
| Server drafts | `createPostDraft`, `listPostDrafts`; `getPostDraft`, `updatePostDraft`, `deletePostDraft` | `/v1/post-drafts` and `/{draftId}`. Exact stable clientDraftId; mutation keys; update/delete If-Match. Do not create a server draft merely to render a local composer. |

| Choices/privacy | `listCircles`; `getPrivacySettings`, `updatePrivacySettings` | `/v1/circles`, `/v1/me/privacy`; future default is distinct from editing an existing post. Privacy write has key and If-Match. |
| Safety controls | `listBlocks`, `blockUser`, `unblockUser`; `listMutes`, `muteTarget`, `unmuteTarget`; `createReport`, `getMyReport` | Exact canonical names, not invented createMute/getReport aliases. Unblock/unmute require their original If-Match and key; report creation returns an owned receipt, not proof a moderator acted. |

Preserve canonical Post fields, including `author: ProfileSummary`, `status=published/hidden/deleted`, `aclVersion`, `capabilities`, independent `keepOnPlate`, `savePolicy`, attachment and exact timestamps. Do not introduce an `audienceVersion` wire field from prose. PostDraft wire status is draft/published/discarded/expired; local uploading/publishing/resolving phases belong only to client state. `Audience.bindings` are server-stamped membership generations, never a client permission claim. Parse versions as exact integers, and validate status/body/ETag correspondence without floating-point conversion.

### Decisions required before claiming complete ingress or client behavior

1. **Reviewed publication identity:** F31 requires the exact reviewed server draft/version, but canonical PostWrite currently makes draftId/draftVersion optional. Settle the supported client-draft-only protocol or centrally align the required pair. Do not silently widen the server or reject the optional branch while claiming complete canonical publication. Retain the exact consented body, clientDraftId and original key through unknown outcomes.
2. **Time observation:** PostPage has serverTime; individual Post read/update/publish responses do not. A post timestamp or transport receipt time is not current server time. Define a bounded server-time observation using a real page response and native monotonic continuity, including request latency/uncertainty; without it, hide an expiry-sensitive story until revalidated. A direct deep link must obtain that observation or show an explicit gate. Do not invent a Date header/API field or assume device wall time is authoritative. After process restart, an unproven monotonic anchor is unusable.
3. **Owner-only management:** F22 requires managing expired, nonretained owned posts, but canonical detail returns a full Post and there is no separate redacted management-summary operation. Specify which owner representation/capabilities detail may return, while denying ordinary viewer content/media when neither placement is eligible. Do not use author equality in UI to create a media grant.
4. **Attachment sources:** `Attachment` carries reference/personalRecipe options plus reviewStatus/rightsBasis claims; schema alone does not enforce exactly one source or verify redistribution. No general client capability converts a downloaded SavedRecipe into an attachable or cookable source. Add precise server eligibility/immutable-version handling before View recipe, Make Mine, community Save or attachment editing is enabled. Where catalog/list responses cannot express source eligibility, an explicit contract decision is needed rather than a fabricated client filter.
5. **Launch authority/policy:** require actual account/device/profile/community-terms integration; transaction-shared block/membership roots; signed cursor keys/lifetime; bounded cache/page/response/clock policies; object delivery, safety and moderation providers. Provider choice, credentials, deployment and release-policy approvals are not supplied by a source fixture. Proposed bounds/defaults in the features are not silently selected here.

## Placement, privacy and retained-state invariants

- Today: published and serverNow strictly before publishedAt +24 hours; order `(publishedAt DESC, id DESC)`, deduplicate overlapping circles by post ID. Viewed is an account-scoped local cue only, never ranking, telemetry dependency or an author-facing receipt.
- Plate: published and keepOnPlate, independently of Today expiry. Test Today-only, both placements, expired+Plate, and expired+neither. Removing Plate retention must explain that a still-live Today placement remains; deletion and retention are distinct.
- Both: current eligible author/viewer, active author-generation binding and viewer membership in any permitted selected circle, reciprocal blocks taking precedence. Author departure/rejoin cannot resurrect old grants. Cursors bind viewer/query/surface/filter/order and expiry, not an old authorization snapshot. Every page, detail and media issuance rechecks current authority.
- `CirclesStore.hasCurrentAudienceMembership` opens its own transaction. Add/reuse a **same-connection** shared authorization seam for the actual post transaction and locks; a successful helper preflight cannot certify a later publish/read/sign. Expiry workers and feed projections are derived, never access authority.
- Cache only bounded encrypted account-scoped metadata and discardable viewed markers, with exact source/surface/version/ACL/time observation. Never persist signed media URLs or private source bytes for offline replay. Historical labels must not turn cached capabilities into usable action grants. Known denial/deletion/expiry immediately hides affected content and cancels delivery; stale late replies cannot resurrect it. Missing current authorization is not proof of deletion.
- On boundary invalidation, synchronously redact all visible/cached-in-memory private fields and revoke operation/media generations before further suspension. Serialized dispatcher, exact access/store/origin, before/after-await fences and caller-return checks apply to storage, network and UI. Back is immediate navigation and cancellation of display work, not post deletion, publish cancellation or pending-command erasure. Close never closes the borrowed native session.
- Fresh media issuance must bind exact post/media/surface/ACL and actual existing sanitized derivative. Enforce approved HTTPS origins and bounded fetch/decode/cancellation, never arbitrary URL navigation. URL TTL is at most60 seconds and also bounded by Today expiry; existing URLs/started transfers have their disclosed residual lifetime. Hide/stop locally at expiry/revocation, without claiming downloaded pixels can be remotely erased.
- Block/delete/audience narrowing remain visibly pending until acknowledged; mute may additionally suppress locally without pretending access was revoked. A late401/403/412 after an uncertain submission does not prove the earlier write failed. Preserve original key/body/If-Match and explicit reconciliation; no rebase, replacement key or delayed widening on reconnect. A block or privacy-reducing pending fence must not disappear merely because its editor closes.

## Five small client implementation tasks

These are sequential, separately verifiable checkpoints, not a claim that the absent server prerequisites can fit into a UI-only change. Server work below continues the existing backend plan rather than creating another service architecture.

1. **Canonical projections and retained account owner.** Proposed files: `shared/mealflow/src/commonMain/kotlin/com/feedme/mealflow/social/SocialFlowModels.kt`, `SocialFlowController.kt`, `SocialClockObservation.kt`, and focused common tests. Use existing WireDocument/validation with typed projections, not a second wire schema or demo Plate. Construct through actual PrivateSessionAccess + AccountTransport, exact SessionBoundary/application dispatcher and explicit policy. Reject guest/DEMO, stale and offline network admission. Initial public actions: restore, openToday(circleId?), openPlate(userId), refresh, more, openPost(id,surface), back, close; expose immutable read-only StateFlow with loading/empty/ready/historical/offline/unavailable/error and separate issue. Construction/restore/Back must never publish, upload or issue a durable command. Test wrong access, immediate stale construction, cross-account redaction and cancellation at every return.

2. **Real Today/Plate paging and cache.** Add `SocialFlowRecords.kt` and controller tests for full PostPage binding, current query/surface generation, cursor loops/expiry, duplicate IDs, version/ACL conflicts, exact stable order, clock uncertainty/rollback/process discontinuity and bounded metadata eviction. Add local viewed markers only after actual authorized display. The paired server lane must first supply canonical post/draft persistence and configured `getToday/getProfilePlate/getPost` using the shared transaction authority above. Use its real publication path for test setup; do not embed seed posts or trusting IDs in production. Client acceptance at this checkpoint is real reading or truthful unavailable, not an operational public feed.

3. **Story lifetime and authorized photo display.** Add `SocialMediaAccessOwner.kt` with a required bounded native delivery adapter, absent by default; wire fresh getPost(surface) → getMediaAccess → exact sanitized derivative. Cancel on Back, foreground loss, selection change, denial, expiry and lease invalidation. Manual next preserves chronological traversal without autoplay/ranking. At Today expiry, clear content first and offer an explicit independently reauthorized Plate transition only when eligible; never reinterpret the same cached grant. The server prerequisite is the still-missing protected delivery route/signer and attachment association check. Missing media provider yields text/alt-text or unavailable state without fetching original uploads. Test a gated media return after block/expiry and exact no-new-capability boundary; clips remain excluded.

4. **Exact owner retention/deletion and pending recovery.** Add `SocialPostCommandController.kt` / `SocialPostCommandRecords.kt` and tests. Start with narrow keepOnPlate patches and confirmed owned deletion; maintain original consented Post/ETag/command evidence, pending visibility wording, unsent discard versus attempted uncertainty, exact receipt application and lost-ack recovery. Do not enable all PostPatch fields through one generic button. This needs a coordinated, purpose-fixed extension of the **existing** [MealKitchenComposition](../shared/mealflow/src/commonMain/kotlin/com/feedme/mealflow/MealKitchenComposition.kt)/[PrivateKitchenSession](../shared/kitchen/src/commonMain/kotlin/com/feedme/kitchen/PrivateKitchenSession.kt) queue hooks before code: current gates reject social commands. Keep one actual underlying journal and operation-scoped owner; no second autonomous queue, raw kitchen exposure, accepting callback or weakening of timer `matchesComposition`. Preserve original sibling cooking/cookbook intents and per-family FIFO; target a specific confirmed post command rather than draining unrelated work. The read-only checkpoints require no queue change. Audience/default/privacy/block/mute/report and composer commands need their own exact consent/policy gates in subsequent checkpoints, not a blanket social fallback. Server retention/delete transactions must exist before this checkpoint can pass end to end.

5. **Retained Compose routes and actual-host proof.** Add `shared/app/.../social/SocialFlowExperience.kt`, `TodayScreen.kt`, `PostScreen.kt`, `PlateScreen.kt` and narrow retained host/navigation wiring alongside the existing MealFlowExperience. Reuse FeedMeTheme, accessible controls and ordinary Back bridge; retain one controller across recreation, without copying Post into a second mutable UI authority or resetting private cooking. Add common presentation tests, configured real PostgreSQL/HTTP client integration, and actual Android host tests with exact action selectors, settled screenshots and positive fixture ownership/cleanup. Cover expiry while open, rapid filter changes, independent Plate retention, current denied access, original timeout retry, dirty composer exit, Back/recreation, lease invalidation and continued cooking when social is disabled. Synthetic identities/posts/providers used in tests or the isolated progress variant must be permanently labelled and retain exact outcomes across restart. No accepting production provider is added. iOS lifecycle/media/accessibility and release-device acceptance remain separate gates.

The server prerequisite work is concrete: continue the photo backend plan's canonical draft/single-publication and placement/lifecycle tasks, add explicit Post HTTP configuration to the existing dispatcher, and implement required F42/privacy persistence/adapters in the same lock/invalidation system. Reuse PgTransactions, DurableCommands, OutboxStore and processing cleanup intents; no old migration edits, independent authorization cache or second publication mechanism. Until those roots and safety controls exist, new peer-sharing remains unavailable even if a read-only UI checkpoint passes.

## Release and authority gates, not implied completion

`social.today.enabled`, `social.plate.enabled`, `social.publish.enabled`, `social.sharing.enabled`, `social.attachments.enabled` and `circles.invites.enabled` are purpose-specific controls from the feature requirements, not Boolean authorization supplied by UI. Disabling discovery/new grants must preserve owner deletion, privacy reduction, block, report/receipt access and private cooking. Current canonical `publicDiscoveryEnabled` is false; there is no public-follow graph or public feed fallback.

Before external social launch, verify actual account/device and moderation providers, exact circle/block lock-order races, source/attachment rights, stable signed cursors, current authorization at every media issuance, bounded residual URL disclosure, expiry/deletion cleanup and outbox delivery, report evidence purpose/retention, native permissions/privacy and both mobile platforms. Test token/caption/media URL redaction in logs and encrypted cache erasure on true session retirement. Passing configured synthetic tests is useful component evidence, not live-provider or whole-F21/F22/F23/F24/F31/F40/F42 completion.

Immediate assignment after cookbook removal: client owner can implement task1 and pure paging/lifecycle tests without waiting for providers; backend owner continues the existing post/draft/placement prerequisites and resolves the five contract decisions above; a separate reviewer audits queue/privacy/media boundaries. Gate each subsequent task on its actual prerequisite rather than manufacturing successful content.
