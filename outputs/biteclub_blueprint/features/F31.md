# F31 — Share Composer

## Strategy
Share Composer publishes an intentional food post with explicit audience, retention, and recipe-copy choices. It connects private cooking to optional social participation. Publication must have exactly-once database effect even though requests, workers, and network delivery are at least once. Ship after draft, media, authorization, and copy-grant contracts are stable.

## Experience and screen design
The sequence is `CAPTURE` → `EDIT_MEDIA` → optional `ATTACH_RECIPE`/`REVIEW_ATTACHMENT` → `AUDIENCE` → `SAVE_PERMISSION` when relevant → `PUBLISH_STATUS` → `POST`. Camera use is optional; the system picker and text-only posts work. The final preview states audience, “Today: 24 hours,” and the independent “Keep on My Plate” toggle. Default audience is Only you until explicitly changed. Publish is a deliberate final action. Cancel preserves or discards the draft according to the user’s choice.

## Production sequence
Saving a server draft is explicit: `POST /v1/post-drafts` returns an owned draft/version for the stable `clientDraftId`; `PATCH /v1/post-drafts/{draftId}` edits it using `If-Match`. Local editing does not require server Save. `POST /v1/media` issues a bounded owned upload slot; byte upload is followed by `POST /v1/media/{mediaId}/complete`. Workers verify object version/checksum/type, strip location metadata, scan, and transform media.

`POST /v1/posts` submits the complete deliberately previewed PostWrite and original idempotency key; it has no If-Match header. Both canonical publication branches are supported:

- When a server draft exists, send both `draftId` and `draftVersion`, alongside its stable `clientDraftId`. Lock that exact owned, editable, unexpired revision and require all reviewed fields to match: caption, altText, ordered mediaIds, audience choices, keepOnPlate, attachment, allowRecipeSaves, saveDisclosureVersion and sourcePostId. Preserve absent-versus-present optional choices; never silently fill them from another revision. Derive current audience membership bindings on the server. Missing confirmed disclosure must first be explicitly saved and reviewed.
- When no server draft or prior publication exists for that owner/clientDraftId, omit both fields and publish the complete reviewed local snapshot. An owned upload lifecycle root is allowed; text-only publication can reserve that internal root without implicitly creating a resumable PostDraft. Omission cannot bypass an existing draft, including an expired or discarded one: return a semantic conflict and require explicit review of the appropriate state. Supplying only one of the pair is a semantic422, even though the current JSON schema makes each field independently optional.

Both branches recheck current account/device, media, rights and audience in the same database transaction. Create one Post, its exact selected-media associations, durable owner/clientDraftId publication identity, original receipt and canonical `social.post.published.v1` fact. The saved branch also marks the exact draft published with its unique `publishedPostId` and next version. A committed root cannot accept new draft/upload/processing admission; its publication identity survives later post deletion and receipt expiry. The response opens that canonical post when the post-read integration is available; a publication component alone does not implement that screen.

## Data and API contracts
Canonical PostDraft status is `draft`, `published`, `discarded` or `expired`; local pending/unknown/publishing states are separate client journal states. Preserve the returned `expiresAt`; the proposed retention is thirty days since the last successful edit, with an explicitly configured service bound, not a client autosave or deletion timer. `Media(id,ownerId,draftId,state,contentHash,storageKey,version)` cannot attach to another account’s draft. Durable uniqueness for `(environment,ownerId,clientDraftId)`, at most one publication per supplied server draft, and original command receipts prevent duplicate publication in both branches. Same-key changed payload conflicts; a different key cannot reuse an already-published clientDraftId. `GET /v1/post-drafts/{draftId}` observes current state but is not an acknowledgement of a lost mutation. `DELETE /v1/post-drafts/{draftId}` discards only unpublished drafts.

## Permissions and lifecycle
Drafts and raw uploads are owner-only. Source media from another post is never automatically copied into a remix. Publishing validates audience membership at commit; failed validation returns the draft for review instead of widening its audience. Today expiry derives from server publication time and is independent of Plate retention. Grant disclosure is mandatory before enabling private recipe copies. Upload slots and delivery URLs expire; an uploaded object alone confers no read or publication rights.

## Failure and offline behavior
Keep local drafts encrypted and account-scoped. Uploads can resume through fresh authorized slots; stale slots do not cause a second media record. Exact prepare retries retain the original reservation/core Upload/ETag; ephemeral POST fields may be freshly issued only for that same unchanged awaitingUpload reservation after current authorization, no later than its original deadline. These bearer fields are not stored in durable command receipts. Status GET never renews. Changed/processing/deleted reservations reject old capability issuance, and an expired reservation returns410; a replacement upload requires a separate explicit intent. Lost signing/response acknowledgement retains the original key and reservation. Already-issued POSTs can remain usable until expiry after deletion, so exact quarantine cleanup must account for late uploads while tombstones immediately deny processing/publication. Upload clientDraft lifecycle reservation does not implicitly create a social PostDraft. If Publish times out, query the draft or replay the same key—never create a fresh draft automatically. Pending states survive app termination. Failed media processing leaves the draft editable. Cancel after committed publication routes to explicit post deletion rather than pretending publication never happened.

## Integration and dependencies
F24/F30 attachment policy, F38 video, F40 audience checks, F42 deletion, native photo permissions, private object storage, worker outbox deduplication, and notification fan-out.

## Execution plan
Build the state machine and publication transaction first, then media lifecycle and recovery, then the Compose preview and cross-platform background handling. Track time spent in publish states, upload failures, duplicate suppression, and orphan cleanup counts.

## Acceptance and release gates
Test double taps, crash after commit, retry after token refresh, draft-version conflicts, revoked circles, failed scans, expired upload slots, and exact Today expiry. `social.publish.enabled` disables publication while preserving drafts, deletion, and privacy controls. Release requires one post/outbox publication event per draft, with consumers idempotent to repeated event delivery.
