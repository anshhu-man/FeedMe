# F26 — Remix Trail

## Strategy
Remix Trail explains how a dish evolved across voluntarily shared takes. It provides useful cooking context and source credit, not a popularity leaderboard. It must remain understandable when some source posts are private, expired, blocked, or deleted. Ship after Your Take with a bounded read path rather than an unbounded social graph.

## Experience and screen design
`POST` exposes “See the trail” only when it has provenance. `REMIX_TRAIL` shows the current post, then accessible ancestors in order with author, owned thumbnail, and a short change note. The initial page includes at most 20 nodes. A missing segment uses “Earlier version unavailable,” with no name, picture, date, circle, or reason for unavailability. Tapping a visible node opens `POST`; “Make Mine” operates on the selected accessible recipe. The screen never implies that all historical versions are visible.

## Production sequence
`GET /v1/posts/{postId}/remixes?cursor=…` first authorizes the requested post. The server traverses immutable lineage edges under a depth bound and evaluates each candidate post against current audience, membership, block, retention, and expiry rules. It returns visible node DTOs and a collapsed gap marker, not hidden IDs. There is no viewer mutation. Publishing in F25 adds the edge in the same transaction as the child post; the outbox emits `remix.edge_created` for derived caches. Cache keys include viewer authorization state and must be invalidated on relevant revocation.

## Data and API contracts
`RemixEdge(childPostId,parentPostId,sourceRecipeVersionId,createdAt)` has at most one primary parent per child in this scope. Application validation plus a bounded recursive transaction check forbids cycles. The response is `TrailPage(nodes,nextCursor,truncated)` where node types are `VISIBLE_POST` and `UNAVAILABLE_SEGMENT`; only visible nodes include IDs. A signed cursor binds the viewer, start post, and traversal position. Descendant counts are omitted because hidden contributions could otherwise leak participation. `TRAIL_UNAVAILABLE` and `CURSOR_EXPIRED` provide safe recovery.

## Permissions and lifecycle
Seeing a child never grants access to its parent, its attached recipe, or its original media. Shared origin does not disclose a blocked or nonmember author. Current authorized recipe copies retain private provenance under F30; public trail identity may be removed independently for deletion obligations. Expired Today sources remain visible only if kept on Plate and still authorized. Removing a child’s post hides that node without rewriting surviving users’ owned media.

## Failure and offline behavior
Cache only the last sanitized structure, with account and authorization version. When offline, show already-owned saved-recipe provenance separately and suppress stale remote thumbnails. A source chip may become unavailable between trail render and navigation; handle this in `UNAVAILABLE`, then refresh the trail. Large or malformed graphs terminate safely at the depth limit and show a plain truncation message.

## Integration and dependencies
Depends on immutable variant provenance, post authorization, identity redaction, F25 publication, and F42 deletion/block events. Media delivery remains per-node and separately authorized. Catalog provenance can be shown only according to its distribution policy.

## Execution plan
Implement recursive traversal and DTO sanitization first. Add accessible vertical-list UI and lazy media reads, then revocation invalidation and deep-link recovery. Observe bounded traversal latency, depth-limit frequency, and sanitizer failures without collecting hidden author details.

## Acceptance and release gates
Test alternating visible/hidden nodes, hidden roots, deleted accounts, blocks, cycles, maximum depth, and cursor reuse by another account. `social.remix_trail.enabled` hides the trail without deleting provenance or disabling private adaptation. No release if a gap marker or cursor reveals an inaccessible post ID, identity, or media URL.
