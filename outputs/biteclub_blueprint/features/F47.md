# F47 — Signup, login and recovery

## Strategy
Make first access dependable and reversible. Start at AUTH_WELCOME with Create account, Log in, Apple, Google, guest cooking, and legal documents. Android and iOS use a public native client; no client secret ships in an app. Staff authentication is a separate workforce client. The initial adult-only launch is a proposed product decision requiring policy review before release, not an assertion of legal sufficiency.

## Experience and screen design
AUTH_SIGNUP collects email, password, confirmation, required consent and launch eligibility. AUTH_VERIFY shows masked email, code, resend cooldown and Change email. AUTH_LOGIN offers recovery and provider sign-in. AUTH_RESET and AUTH_RESET_CONFIRM use the same generic confirmation regardless of whether an email exists. AUTH_CALLBACK is a transient callback/error surface. Successful first signup proceeds to PROFILE_SETUP; a returning user goes to HOME or an authorized deferred invite. Passwords are never restored as draft fields. Show native password-manager/autofill support, accessible errors and non-secret input retention.

## Production sequence
1. Start a random state/nonce and PKCE S256 challenge for browser OAuth. Use the OS browser session and registered universal/app callback links.
2. Validate the callback state and exact redirect, exchange the code with the verifier, then validate the returned identity token's signature, issuer, audience and saved nonce before accepting the identity. For email/password use Cognito's supported native SDK operations rather than forwarding credentials through FeedMe.
3. Store refresh credentials in platform-protected storage; keep access tokens short-lived. API verifies JWT signature, issuer, configured client, token use, expiry and application account status.
4. Call `POST /v1/account/bootstrap` with a UUID `Idempotency-Key` for this logical command; account uniqueness is independently enforced by `(issuer, subject)`. Transactionally create account/profile shell and consent version receipts. Store returned `Bootstrap.sessionId` with this account's secure session state and send it as `X-Device-Session` on subsequent registered-user API calls. The server checks its account binding and revocation alongside the JWT, so revocation takes effect before token expiry. Guest calls use their explicitly scoped guest token and do not invent a registered session header. Never merge accounts because unverified email text matches.
5. If a guest has data, offer explicit merge; bind both identities and an idempotent merge receipt, then resume onboarding/deferred route.

## Data and API contracts
Cognito owns secrets and verification/recovery. FeedMe owns accounts keyed by immutable account UUID and a unique `(issuer, subject)` identity mapping, consent receipts, onboarding revision, app-session revocation state and guest-merge receipt. Native operations are SignUp, ConfirmSignUp, ResendConfirmationCode, SignIn, ForgotPassword, ConfirmForgotPassword and browser code exchange. Application routes include bootstrap, `/v1/me`, `/v1/guest-sessions`, guest merge and account-session management. Provider challenges are typed states; never treat HTTP 200 alone as an authenticated session.

## Permissions and lifecycle
Guest tokens only authorize their own private cooking data and approved catalog reads. They cannot publish, message, accept memberships, buy shared access or access another identity's objects. Signup consent is versioned; optional marketing/push is separate. Provider-account linking is outside this release: there is no linking endpoint or screen. Duplicate email/provider cases guide the user to sign in with the provider already associated with the account or use its recovery flow; they never silently merge identities. A future linking feature requires a separately designed proof-of-control and conflict-resolution workflow.

## Failure and offline behavior
Code expiry, provider cancellation, rejected state, clock skew, reset throttling and account suspension have distinct recovery UI without leaking account existence. Login/verification require network. An owner-scoped, previously verified pinned cook can continue locally with a visible last-sync time; the app cannot know about a later server recall or account change while offline. A locally known recalled recipe is unavailable. Logout/account switch clears the old account's cache; no new protected server action succeeds until authentication and the registered app session are valid. A lost bootstrap response is retried with the same identity and operation ID. Refresh-token failure stops retries and shows sign-in with a safe return route.

## Integration and dependencies
IdentityGate is shared Kotlin state; browser/auth/secure-storage adapters are native. Navigation consumes `Unauthenticated`, `Guest`, `PendingVerification`, `NeedsProfile`, `Member`, `Restricted` states. The backend requires account bootstrap before social commands. F49 defines account deletion; F53 defines safe link resumption. Primary platform guidance is recorded in architecture/11_Sources_Decisions.md.

## Execution plan
Configure dev/staging/prod identity pools, providers, app IDs and exact callback allowlists. Build native identity adapter and shared repository; implement bootstrap and transactional identity uniqueness. Add device/session revocation and rate limits. Implement forms/challenge routing, guest merge and native autofill. Run real-device provider and deep-link certification before enabling login to a cohort.

## Acceptance and release gates
Exercise complete signup/verify/login/reset on both platforms; unknown-email reset must look equivalent. Replay/tamper OAuth state and code, race two bootstraps, lose network after signup, cancel provider sign-in, revoke a session, and re-open an invite after login. No secrets may appear in logs, screenshots used for support, analytics or crash breadcrumbs. Roll back provider entry points independently while keeping email recovery available. Track aggregate completion, challenge failure and provider latency without emails or raw identifiers.
