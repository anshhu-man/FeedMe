# F50 — Purchases and entitlements

## Strategy
Use native store purchases for digital access and a server-owned entitlement ledger. Preserve useful free cooking and basic saved recipes. Purchase offerings are optional: household access, advanced personal organization and reviewed content packs. Prices and billing duration remain decisions informed by user testing and store configuration.

## Experience and screen design
PAYWALL shows localized store product details, the exact included capability, one-time versus recurring terms, restore and free continuation. PURCHASE_STATUS distinguishes pending, cancelled, failed and verified active. MANAGE_PLAN shows store origin, access duration and native management. PACK_DETAIL offers a free sample and current review status. No purchase success animation implies server authorization before reconciliation.

## Production sequence
Verified member UUID is the billing app-user identity. Fetch versioned offerings mapped to canonical product IDs. Native RevenueCat purchase/restore returns provisional transaction state. Client calls `POST /v1/entitlements/reconcile`; server verifies through the provider. Authenticated webhook ingress durably stores a unique provider event ID before acknowledging, then reconciliation computes effective entitlement from authoritative state rather than event arrival order. Capability checks occur at every paid API command and on cached bundle issuance.

## Data and API contracts
Entitlement record: accountId, capability, productId, sourceStore, sourceTransaction, status, validUntil nullable, providerObservedAt, revision. Immutable purchase events have unique provider IDs and redacted payload hashes. Product mapping separates offering labels from access capabilities. Household ownership and memberships are separate resources. OpenAPI covers entitlement reads/reconciliation and authenticated provider webhook ingress; native store operations are external contracts, not FeedMe payment APIs.

## Permissions and lifecycle
Provider secrets stay server-side. Webhook authenticity follows the verified current provider mechanism; verify the raw body before parsing when signatures are supported and require a configured ingress credential. Duplicate/reordered/refund/renewal events reconcile safely. Transfer/restore across app accounts must be explicit and follow the configured provider policy; never grant both automatically. On expiry, advanced writes stop while existing basic personal recipe reads remain available. Restore does not confer copyright/media redistribution rights.

## Failure and offline behavior
Pending store transactions show pending until authoritative resolution. A lost webhook is repaired by reconciliation and scheduled drift checks. Repeated client taps reuse the in-progress purchase context; they must not start a second charge. This API issues no signed offline entitlement lease. Offline access is limited to already cached permitted recipe content and basic personal saves, showing last verification time; known revoked content is unavailable. New premium tools, purchases and shared mutations require online server entitlement checks. `Entitlement.verifiedAt` and `expiresAt` describe the last server-observed state, not proof of an unchanged current subscription while disconnected. Billing outage does not block free cooking.

## Integration and dependencies
Kotlin common commerce interface delegates to supported native platform SDKs; validate current KMP/native interop support in a spike rather than inventing a cross-platform API. F44/F45/F46 gate capabilities; F49 handles account deletion and billing-retention obligations. Platform source links and choices live in architecture/11_Sources_Decisions.md.

## Execution plan
Create sandbox store products, offering maps, account-association policy and capability middleware. Implement native adapters, webhook inbox/reconciliation, typed pending states and restored/expired access behavior. Add immutable audit and periodic drift repair. Test in both store sandboxes with cancellations, pending transactions, renewal, refund and account switches before enabling a paid cohort.

## Acceptance and release gates
Forged callbacks/client flags never grant access. Duplicate events produce one effective transition; a delayed renewal cannot overwrite a newer refund without authoritative reconciliation. Existing free saves survive lapse. Verify localized price/terms and store-management routes on devices. Kill sales by offering/flag while preserving reconciliation, restore and purchased-content access.
