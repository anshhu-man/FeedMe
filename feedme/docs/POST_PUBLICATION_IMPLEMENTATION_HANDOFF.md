## Callable production seam

`PostPublicationStore(environment, transactions, authority, media, policy).publishPost(actor, key, body)` consumes a verified account/device, original UUID command key and exact PostWrite body. It returns the existing `CommandResult`; only acknowledged Applied/Replayed contain the canonical original `201 Post` plus ETag. No If-Match, automatic retry, inferred preview consent or implicit server PostDraft is introduced. `PostPublicationPolicy(maxResponseBytes)` is required, bounded to 1–262144, without a default provider or user-selected quota. HTTP is separately owned and configured; absent composition stays unavailable.

Request validation uses the actual bundled PostWrite schema and a 64 KiB transport/service profile. A half draftId/draftVersion pair is a semantic 422. Both fields require the exact owned live editable draft, generation, version and reviewed material. Neither is accepted only when no server draft or publication identity exists for the owner/clientDraftId. An upload root may exist without a server draft; a text-only publication reserves only the internal lifecycle. Saved-draft content compares absent/present optional choices and ordered media IDs, normalizing only canonical JSON numbers and established UUID fields. Client audience bindings never become authority. Missing saved disclosure is not inferred from the publish request.

## Atomic SQL effects and lifecycle

Append-only V010 registers seven new tables: `social.posts`, `post_publications`, `post_media`, `post_audiences`, `post_attachments`, `recipe_save_policies`, and `post_publication_discard_media`. V001–V009 stay unchanged. Root runs migrations explicitly; HTTP startup does not migrate.

Lock order is principal/device → original command receipt → owner draft-list head → stable client lifecycle → publication/optional draft → content/circle authority → UUID-ordered media and processing evidence. Callbacks use only the supplied connection; no network call, nested public-store transaction, commit or successful preflight substitutes for current authority.

One transaction creates the Post, exact selected-media position/version/derivative associations, current audience generations, optional verified attachment plus canonical recipe snapshot, original save policy, durable owner/clientDraft publication identity, original response receipt and the registered `social.post.published.v1` fact. The event data contains only postId, authorUserId, aclVersion and expiresAt. There is no fabricated feed delivery or notification. publishedAt is database time, expiresAt is exactly +24 hours, keepOnPlate stays independent, and reactionCounts is the actual initially empty set.

For a saved draft, the same transaction increments its version, retains original content/expiry, marks publishedPostId and increments the owner list head. It does not emit the draft/discard-only internal change event with an invented published state. Direct publication creates no resumable server draft.

The unique publication identity pins owner/clientDraftId, incarnation, postId, original key/request hash, original response hash, optional reviewed draft/version and original recipe-snapshot hash. It cannot be updated/deleted/recycled, including after seven-day receipt compaction or post deletion. Selected-media and original cleanup identity records are likewise immutable. The current attachment row rejects update/delete. A future approved post/account erasure implementation must deliberately reconcile these retention/lineage protections with content erasure; this package does not claim that lifecycle exists.

## Mandatory authority and real recipe material

`PostPublicationAuthority` has no accepting default. It supplies current verified author/profile, terms/kill switch, circle membership and reciprocal-block policy, source/read/redistribution/review/recall eligibility, source-to-plan/version resolution, exact changes and disclosure, capabilities and bounded evidence expiry. A private cookbook copy or cooking pin is not redistribution authority. The store verifies exact author ID, exact selected circle set, exact attachment and a paired canonical snapshot. Catalog/plan snapshots must validate as RecipeVersion with published review state; catalog recipeVersionId must equal the snapshot ID. Personal snapshots validate as RecipeDraft and exactly equal the selected personalRecipe with personal/creatorOriginal provenance. Plan-to-version resolution remains an explicit authority obligation, not an inference from schema validity.

`authorizeReadyMedia` returns an actual authority-expiry instant for each selected asset. The store intersects all media and content deadlines and checks freshness after subsequent waits and before new/replay completion. READY strings alone, expired safety proofs and unavailable moderation providers are not accepted grants.

The same-connection media helper checks exact owner, lifecycle generation, READY state/version, two immutable thumbnail/display derivatives, ready processing job/version, acknowledged derivative-intent object versions and absence of cleanup ownership/conflicting attachment. Existing editable-draft media validation remains distinct and may retain pending/rejected metadata; it cannot publish it.

## Unused uploads, late effects and replay

Selected media stay READY and become attached. Every unused exact-root upload is tombstoned with its existing immutable object/write-intent/cleanup lineage and original acceptance deadline; the whole-root discard helper is not called after attachment. Existing attached unselected media abort the transaction. Already-authorized late immutable writes may be acknowledged for cleanup only; they cannot create a READY/published effect. Late upload-event ingestion can create only a cancelled job with the already-retained cleanup targets. Observing cleanup rows does not claim external objects are deleted or provider settlement completed.

Publication identity fences are integrated into PostDraft create/edit, new upload preparation/completion/reference validation, and processing-effect admission. Direct text-only publication therefore also closes the root to subsequent upload/server-draft creation. Old acknowledged receipts remain historical responses where separately permitted, not new admission authority.

Exact original replay rechecks the current principal/device, immutable publication lineage, current unchanged published Post, saved-draft terminal lineage if present, content/privacy/recall authority, exact media associations/current readiness, every unused cleanup target and captured membership, audience rows, attachment hash and save policy. The recipe hash is independently pinned in the immutable publication identity: rewriting both current attachment/policy hashes cannot substitute a recipe. Missing or altered evidence fails closed without repair. Later hidden/deleted/edited Posts do not cause substitution of a new response. Receipt expiry remains explicit; new keys never recreate a used publication identity. Further post-edit/delete/access semantics remain separate work.
