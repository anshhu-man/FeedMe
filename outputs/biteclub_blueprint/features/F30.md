# F30 — Recipe Saving Permissions

## Strategy
The author decides whether others may keep a private recipe copy. A viewer understands what they are saving and whether it survives the post. This feature is a prerequisite for social recipe saves; it is not a monetization restriction. Existing basic saved-recipe access must never depend on buying library tools.

## Experience and screen design
`SAVE_PERMISSION` offers “View only” and “Allow private recipe copies,” defaulting to view only for user-authored social attachments. Its explanation states: “People who save can keep this recipe after you remove the post or turn saving off. Your photos and replies are not copied.” `REVIEW_ATTACHMENT` repeats the selected policy. In `RECIPE`, an enabled Save action explains the private copy; a disabled action says the author has not enabled saving. `DELETE_POST` repeats the persistence consequence before deletion.

## Production sequence
The author edits draft policy with `PATCH /v1/post-drafts/{draftId}` or active policy using `PATCH /v1/posts/{postId}` with `If-Match`. A viewer saves through `POST /v1/posts/{postId}/recipe-saves` with `recipeVersionId`, `grantPolicyVersion`, optional owned `collectionId`, and an idempotency key. The transaction locks the post’s active attachment policy, rechecks access/recall state, creates a grant receipt and immutable private snapshot, and writes `recipe.copy_created`. If revocation wins first, saving fails; if saving commits first, that authorized copy persists. `POST /v1/saved-recipes` handles permitted owned-plan/catalog saves. `POST /v1/collections/{collectionId}/items` only organizes an already-owned `savedRecipeId`; it never creates or bypasses a source grant.

## Data and API contracts
`RecipeSavePolicy(attachmentId,allowPrivateCopy,version,revokedAt)`; `RecipeCopy(id,ownerId,sourceRecipeVersionId,sourceAttachmentId,grantReceiptId,contentHash,createdAt,recallState)`; `GrantReceipt(id,grantVersion,authorizedAt,rights=PRIVATE_RECIPE_COPY)` form an auditable chain. Uniqueness on owner/source immutable version prevents duplicate snapshots while collection memberships remain many-to-many. Snapshots include structured recipe content and allowed provenance only: never original media, comments, audience membership, or private preferences. `SAVE_NOT_ALLOWED`, `SOURCE_UNAVAILABLE`, `RECIPE_RECALLED`, and `IDEMPOTENCY_CONFLICT` are typed errors.

## Permissions and lifecycle
Revoking future grants prevents new copies; it does not remove earlier authorized copies. Attachment replacement has its own grant version and cannot retroactively modify a saved snapshot. Ordinary post/account deletion removes public source identity where required and leaves the private recipe content available. Safety or legal recall is a distinct audited administrative operation that tombstones affected copies, cancels offline sync availability, and displays the reason permitted by policy. Viewing a private copy grants no right to reshare its source recipe or media.

## Failure and offline behavior
Saving requires online authorization; an offline tap creates a clearly pending intention only. If access expires before synchronization, the intention fails without creating a copy. Authorized copies already stored in encrypted local storage remain usable offline until a recalled state is learned; clients enforce that state on next sync and must not promise instant remote deletion from disconnected devices. Idempotent retries return the original copy.

## Integration and dependencies
F19 cookbook, F24 attachments, F25 takes, F31 composer, F42 deletion, F49 account privacy, and F51/F52 audited recalls. Saved copies become independent authorization roots for private cooking, not for source media.

## Execution plan
Build grant transaction tests before UI, then policy disclosures, save states, revocation, and recall synchronization. Observe save denial and recall propagation with receipt IDs, never full recipe text.

## Acceptance and release gates
Test save/revoke and save/delete races, duplicate requests, replaced attachments, offline retries, cross-account collection IDs, and identity redaction. `social.recipe_copy.enabled` stops new grants/copies while preserving existing authorized access and recall enforcement. No release without explicit disclosure and a demonstrably media-free snapshot.
