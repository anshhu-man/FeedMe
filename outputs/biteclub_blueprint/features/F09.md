# F09 — Something Else

Phase: first release. Owner module: planning.

## Strategy

Let a person reject a suggestion without explaining themselves or restarting the request. Alternatives should remain feasible and varied within the same constraints. Skipping a recipe is a session-level navigation action, not evidence of a lasting dislike.

## Experience and screen design

RECOMMENDATIONS includes Something else beside Make it easier. It replaces the primary card with the next eligible choice while leaving ingredients, time and energy summaries visible. Back to previous restores the prior candidate within the current plan. An optional brief reason can be offered without blocking the action; explicit Not my taste feedback remains a separate control. At the end of the bounded eligible set, show “No more matches for these choices,” with Edit ingredients, Edit effort and Return to a previous meal. Avoid endless loading or silently recycling a rejected card.

## Production sequence

1. Resolve the plan's immutable request and catalog snapshot.
2. Verify the continuation token belongs to that plan and revision.
3. Advance past already presented candidates, preserving deterministic order and all hard constraints.
4. Revalidate publication/recall status before returning a candidate.
5. Record the presented candidate set for the request lineage and return an immutable child plan plus an opaque next cursor bound to that lineage; do not write a taste memory unless the user separately submits feedback. Earlier displayed plans remain immutable for Back to previous and pinned cooking sessions.

## Data and API contracts

nextPlan: POST /v1/plans/{planId}/alternatives with Idempotency-Key and X-Device-Session. The canonical AdaptRequest carries current constraints, the owner-bound continuationCursor, and bounded excluded recipe-version IDs. The immutable parent plan and cursor bind the traversal; this operation does not accept an If-Match header.

    {"reason":"alternative","continuationCursor":"opaque_signed_cursor","excludeRecipeVersionIds":["00000000-0000-4000-8000-000000000021"],"constraints":{"ingredientIds":["00000000-0000-4000-8000-000000000011"],"energy":"assemble","equipmentIds":["bowl"],"servings":1,"hardExcludedIngredientIds":[],"maxTotalMinutes":10}}

Return canonical Plan fields including id, parentPlanId, recipeSnapshot and nextAlternativeCursor. Null nextAlternativeCursor signals the end of traversal; noMatch means no candidate is available. The cursor encodes or references server-side snapshot position and cannot authorize another user's plan. Duplicate requests with the same key return the same candidate instead of skipping two. A changed constraint set invalidates the old cursor and starts a new sequence. Previous candidates remain in owner-scoped lineage/client history. Optional skip reasons are session data, never automatically promoted into memory. Use typed stale/expired cursor outcomes with precise recovery actions.

## Permissions and lifecycle

Only the plan owner can traverse its alternatives. Store a bounded session history with operational plan retention; avoid building an undisclosed permanent list of rejected foods. Guest requests are rate-limited to a bounded session just like other helper operations. Alternatives never require a purchase merely because the person skipped a free recommendation.

## Failure and offline behavior

A failed fetch leaves the current recipe on screen and offers Retry. Offline navigation may browse already fetched candidates only, clearly ending when those run out. A recalled current candidate is removed from future selection; previously presented IDs remain in history solely as non-cookable references if retention permits. Concurrent taps are disabled locally while a request is pending, but server idempotency still handles duplicate delivery.

## Integration and dependencies

Consumes F02 plan creation and F04–F07 constraints. F17 explanation facts travel with each candidate. F15/F16 separate explicit dislike from ordinary browsing. F53 handles restoring a plan's current candidate after backgrounding.

## Execution plan

- Implement stable candidate ordering and signed/opaque plan-bound cursors.
- Add presentation-history storage and duplicate request handling.
- Build previous/next, exhausted and retry states with focus announcements for accessibility.
- Emit alternative_requested, alternative_exhausted and accepted_candidate_position without treating a skip as negative dietary preference.

## Acceptance and release gates

Test repeated rapid taps, request replay after timeout, a tampered cursor, changed exclusions between alternatives, exhausted catalogs and a recalled recipe in the pending sequence. A result must never loosen constraints or cycle indefinitely. Proposed usability review checks whether users understand the bounded alternatives. Rollout alternatives independently; disabling it retains the visible meal and lets users edit their request manually.
