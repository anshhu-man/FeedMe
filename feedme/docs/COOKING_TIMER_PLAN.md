### Implemented foundation and focused verification

[SessionCookingTimers](../shared/mealflow/src/commonMain/kotlin/com/feedme/mealflow/timers/SessionCookingTimers.kt) is a borrowed facade over the actual current runtime access and [PrivateKitchenSession](../shared/kitchen/src/commonMain/kotlin/com/feedme/kitchen/PrivateKitchenSession.kt). Construction requires the runtime's exact execution-policy instance plus identical current store/boundary and matching scope/origin. Those comparisons are composition checks, not an account verifier. The trusted application must supply the same serialized owner dispatcher, a real clock implementation, and a scheduler; no facade or test fixture substitutes for production authentication.

The explicit application bounds are 32 timers/private mapping slots, durations from 1 through 86,400 seconds, private mapping payloads from 1 through 16,000 bytes, epoch milliseconds from zero through 253,402,300,799,999, and a 2,000 ms epoch-versus-monotonic drift tolerance. These are implementation limits, not newly inferred canonical API limits. Pause rounds positive remaining milliseconds upward to whole wire seconds, adding less than one second; resume uses that remaining amount. Missing/discontinuous clock evidence yields `UNCERTAIN`, not a guessed countdown or silent restart. A canonical timer without private mapping stays visible with no alert authority.

The private mapping phases are `DESIRED`, `MAPPED`, `ARMED`, `CANCELLING`, and `QUIET`. Domain progress, original immutable cooking command, and the desired mapping are acknowledged atomically before runtime installation. Runtime `RESERVED` precedes an acknowledged exact ticket mapping, which precedes the scheduler call; runtime `INSTALLED` and a fresh mapping acknowledgement precede this facade's in-memory alert receipt. Failed or lost acknowledgements do not turn visible rows into permission, allocate replacement tickets, or claim delivered alerts. This batch's injected loss hooks run after actual SQLite commits; they are application response-loss tests, not new VFS or physical-storage failure proofs.

`timerExecutionCheck` verifies the real cooking action/body and the materialized queue's exact original intent, current phase, issue, and revision. Missing journal entries cannot be treated as unmaterialized permission. The execution policy rechecks domain/queue/recall evidence after the work registry's fresh CAS/readback; a final synchronous per-timer fence rejects a new desired change racing that acknowledgement. Closed or invalidated facades remain denied, and their policy cannot bind a successor.

Observation and cleanup do not reinstall an alarm. A newly constructed facade has no in-memory alert receipts, so persisted mappings are cleanup-only. `cancelAlert` retains and cancels the same exact ticket, with `CANCELLING` preserved across failure/unknown results. It neither changes canonical timer progress nor starts a replacement. Closing the facade only fences callbacks and releases its invalidation subscription; the application still owns actual runtime/stores, retirement, and cancellation.

## Exact action mapping

| Existing action | Required local behavior |
| --- | --- |
| `COOK.03` — Start step timer | Navigate with authorized pinned step context; navigation alone must not schedule. |
| `TIMER.01` — Start timer | Validate duration and eligibility; persist timer ID/deadline and scheduling intent before asking the owned scheduler to install an alert. |
| `TIMER.02` — Pause timer | Persist the remaining duration and non-running desired state, then cancel only the captured alert generation. |
| `TIMER.03` — Reset timer | Cancel the captured alert and restore the chosen duration without starting it or advancing a step. Use an explicit non-running representation; do not invent a wire status. |
| `TIMER.05` — Resume timer | Use persisted remaining duration, not the original full duration; persist a fresh deadline and generation before installing a new alert. |
| `TIMER.06` — Cancel timer | Remove the selected desired timer and cancel its exact alert; preserve sibling timers and cooking progress. |
| `TIMER.back`, `TIMER.04` | Navigate to cooking; do not pause, cancel, complete, or discard implicitly. |

`TimerState` permits only `running`, `paused`, and `done`; it requires `timerId`, `stepId`, and positive integral `durationSeconds`, with optional UTC `endAt` and nonnegative integral `pausedRemainingSeconds`. Reset can use paused/full remaining duration, subject to explicit reducer tests. Cancel must not serialize a new `cancelled` status. F12 mentions clearing expired timers, but the current registry contains no distinct clear-expired action: obtain a reviewed mapping before adding that control. Labels come from the pinned step, not OS extras or guessed content.

## Small implementation packages

### 1. Pure timer reducer and clock evidence — implemented shared foundation

Add a bounded shared timer model/reducer for the actions above, using exact existing wire documents and preserving unrelated timers, notes, and progress. Validate pinned step IDs, positive integral durations, remaining <= duration, unique IDs, supported bounds, and checked seconds-to-milliseconds/deadline arithmetic. Select and document an application duration/count bound rather than presenting it as an unstated canonical maximum.

Inject a narrowly defined monotonic reading and continuity marker alongside the existing epoch clock. During a verified continuous run, elapsed time comes from the monotonic anchor. Persist UTC deadlines plus private anchor/recovery metadata at meaningful transitions, not every display tick. A timezone change changes formatting, not the instant. A wall-clock jump, missing anchor, process restart without verified continuity, or device restart must produce an explicit uncertain-recovery state; do not silently restart a full duration or fabricate monotonic continuity. Native clock/boot API choice and conversion tolerances remain unverified and pending implementation review.

### 2. Durable desired state and exact alert mapping — implemented shared foundation

Extend the retained cooking controller through a trusted, session-owned timer facade, not a public raw scheduler or a cast of meal-flow access into a work binding. Keep the runtime/access and the facade on the same application-owned serialized lifecycle. Preserve `originMatches`, locally known recall, complete bundle, pending-command, and current lease checks; timer labels or a historical snapshot are not capabilities.

Before scheduling, acknowledge the actual repository timer edit and its immutable `updateCookSession` intent. Persist a private local scheduling record containing the exact session origin, cooking session/timer ID, desired generation, deadline, and local revision. Keep native tickets/clock anchors out of the canonical server body. The implemented purpose-fixed repository batch carries this mapping atomically; it is not a general extra-mutation API and does not substitute two independent writes while claiming atomic acknowledgement.

Invoke runtime `install` only after that durable intent. Its installer receives the fresh opaque ticket **after** the independent `RESERVED` write. Within the installer, persist and read back the exact generation-to-ticket mapping before native scheduling. Thus a crash after scheduling still leaves an exact cancellation target. The registry then acknowledges `INSTALLED`; a callback arriving while `RESERVED` cannot act. Do not call install again with a new identity after an unknown result. A failed reservation may leave no mapping; registry reconciliation still owns any exact retained reservation.

### 3. Pause, reset, cancel, and replay — implemented shared foundation

Persist the non-running/replaced desired generation first so domain callback eligibility closes before native cancellation. Use only the captured `NativeWorkTicket`; report alert cancellation pending/unknown until its acknowledgement succeeds. Repeated cancellation must retain the same ticket. A replacement starts only after exact predecessor cancellation is acknowledged; same logical-task duplicates are already rejected by the registry. Domain timer identity may remain stable while native alert generations must not be recycled.

Keep server synchronization separate: use the existing queue's original command ID/body, expected version, `deviceSequence`, FIFO head, and receipt application. A 412 preserves conflicting states for review; do not merge deadlines or infer cancellation from a newer server response. Local offline timing is permitted only through an already verified eligible private session; connectivity cannot upgrade access. No per-second network requests or remote alarm dependency.

### 4. Native scheduler and callback policy — foreground component in verification

The new `AndroidProcessCookingTimerClock` uses actual wall time and `SystemClock.elapsedRealtime`, with process-local random continuity; it claims no cross-process or reboot continuity. `AndroidForegroundCookingTimerAdapter` is both the scheduler and exact cancellation owner, and checks identity pairing with the actual runtime/facade. Its Handler callbacks route through `SessionCookingTimers.runLocalEffect`, distinguish queued/delivered/blocked/unknown states, and synchronously recheck foreground/owner identity at the final effect. Losing foreground after an invoked effect remains unknown, never resumable. Closing retains exact downstream cancellation obligations. Main code initializes no WorkManager or background receiver; explicit test setup does not become a production default. The remaining background/permission requirements below are still open.

Implement a trusted Android scheduler behind the session-owned facade. Reuse `timerIdentity(ticket)`: immutable explicit app-private component/action/package, opaque ticket-only URI, fixed request code, and exact opaque notification tag/id. Never put account IDs, recipe labels, session scope, tokens, or payloads in intent/tag/data. Notification text must follow an explicitly reviewed privacy policy; opaque identity does not make visible notification content private.

Every delivery treats `NativeWorkTicket.fromNativeIdentity` as parsing, not authentication. Route delivery through runtime `runLocalEffect` and a real `NativeWorkExecutionPolicy` that checks the independent retirement barrier and exact desired timer/ticket generation, running/due state, and current permitted domain state. The final effect is short and synchronous; it must not suspend, send HTTP, advance a step, or invoke retirement/runtime methods recursively. Design lock ordering so domain policy cannot wait on a controller mutex whose action is waiting for the work registry.

The gate requires a current verified runtime lease. A receiver waking a new process cannot manufacture one from OS extras or open normal stores as a recovery shortcut. Until a real startup/background composition contract exists, such delivery must remain fail-closed and recovery occurs through the trusted foreground owner. Scheduling an alarm does not prove that it will display while the process is absent.

Use the same exact notification identity for duplicate deliveries. This can support convergent replacement, but does not establish exactly-once sound/vibration: private storage and OS notification delivery are not one transaction. Native cancellation is an acknowledged command, not callback quiescence or rollback of an already delivered effect. Late callbacks still require all fences.

### 5. Recovery and permission presentation

On explicit verified restore, let the existing runtime reconcile incomplete reservations/cancellations before considering domain reinstallation. `reconcilePending` cancels uncertain entries; it does not reschedule them. An observed `INSTALLED` ledger row is not proof that the OS still has an alarm. Reconcile exact local mappings, desired state, deadlines, and permission/availability, preserving unresolved generations and sibling/newer origins. No broad cancel-all, directory cleanup, credentials read for timer identity, or automatic session restoration from a broadcast.

Ask contextually for optional alert permission at the first explicit timer start. Denial retains a working visible timer and offers an honest foreground-only/unavailable explanation. Distinguish local timer persistence, alert request acknowledgement, and actual delivered notification; never render all three as “alarm guaranteed.” Do not silently retry permission prompts or use test-granted permissions as a production default. New alerts can be disabled without discarding active timer/session state or blocking exact cancellation.

Alarm scheduling API, exact-alarm eligibility/permission, notification channel behavior, wake/reboot integration, and any foreground/background restrictions are **pending primary-platform verification and native acceptance**. The existing WorkManager dependency/cancellation hook is not evidence that workers meet timer precision. Do not add a fallback default provider, implicit WorkManager initialization, or a production receiver until trusted composition is supplied. iOS requires its own implementation and evidence; none is inferred from Android.

### 6. Acceptance before enabling timer actions

Use pure/JVM tests for every action and byte-preserving replay; overflow, fractional input, clock jumps, zero remaining, pause/resume/reset, multiple timers, known recall, origin change, queue conflicts, and lifecycle invalidation. Use real SQLite/native-store tests for failed/unknown domain, ticket-mapping, `RESERVED`, `INSTALLED`, and cancellation acknowledgements, with zero scheduling/effects before the required durable barriers.

Then add isolated Android tests with real private receiver/scheduler identities: two independent timers, sibling preservation, duplicate/late delivery, permission granted versus denied branches, cancellation of already delivered notification, old-origin retirement versus newer login, and retained same-ID recovery. Add actual witnessed process-interruption stages around acknowledged boundaries and separately test device restart and wall-clock changes once their native APIs are selected. A clean close/reopen is not process death; neither is physical power loss. Preserve denied/unavailable branches as limitations rather than fabricated delivery evidence.

Release remains blocked on actual Android scheduling/delivery integration, reviewed background startup authority, platform clock/permission validation, corresponding iOS work, native timer UI/accessibility, and the real end-to-end cooking server/provider integration. Existing cancellation, startup-owner, and injected-VFS receipts remain their own bounded evidence, not acceptance of these future timer guarantees.
