# F05 — Match My Energy

Phase: first release. Owner module: planning; shared input with profile.

## Strategy

Respect the amount of work someone can manage today. Energy is a user-selected preparation limit, not a health assessment. The product must count active work, waiting and cleanup separately enough to avoid suggesting a deceptively quick but demanding recipe.

## Experience and screen design

EFFORT contains three labelled choices: Assemble only, A little cooking, Happy to cook. Short examples explain the permitted activity rather than rating the person. The same screen offers total-time chips and a custom minute limit; advanced details allow an active-preparation limit and access to EQUIPMENT. Current selections remain visible in REQUEST and ADAPT. RECOMMENDATIONS explains a fit such as “One bowl; no heat; short slicing step.” If no reviewed option fits, show which bound prevented a match and let the user intentionally adjust it.

## Production sequence

1. Combine today's explicit choice with saved equipment; today overrides past effort preferences.
2. Validate numeric time bounds and ingredient preparation requirements.
3. Evaluate reviewed operation tags against a versioned energy policy. Assemble excludes heating and recipes flagged as substantial preparation; it does not merely mean fewer written steps.
4. Enforce total-time, active-time and equipment limits as hard constraints when selected.
5. Rank remaining results using cleanup and optional learned effort preferences; do not loosen a selected limit to increase result count.

## Data and API contracts

EFFORT contributes to createPlan POST /v1/plans and adaptPlan POST /v1/plans/{planId}/adaptations.

    {"mode":"assemble","constraints":{"ingredientIds":["00000000-0000-4000-8000-000000000011"],"energy":"assemble","maxTotalMinutes":10,"maxActiveMinutes":8,"equipmentIds":["bowl","knife"],"servings":1,"hardExcludedIngredientIds":[]}}

The server controls the applicable internal energy-policy version; a client cannot override policy. Transport energy values assemble, little and happy correspond to the three labelled UI choices. Recipe effort metadata includes activeMinutes, totalMinutes, operation tags, equipment, utensil count, cleanup and estimate provenance. Missing required effort metadata makes a catalog version ineligible for a strict effort request. Returned explanations use stable reason codes for matched and unmet limits. Plan writes use idempotency and version checks; changing energy creates a child plan with a new immutable snapshot.

## Permissions and lifecycle

Today's effort belongs to the private plan and is not a lasting personal trait. Save it as a default only after explicit choice; feedback about a specific recipe may influence later ranking without replacing the next explicit selection. Shared posts may display a creator-confirmed preparation description, not the creator's private energy setting. Guest effort selection requires no profile or health data.

## Failure and offline behavior

Invalid limits show inline validation before request. If updated equipment or recipe metadata invalidates a plan, offer a fresh match and preserve the former recipe for reference where allowed. Offline users can inspect cached effort metadata and choose locally known recipes, but unavailable server-reviewed variants are not invented. If a timer or cooking interruption increases elapsed time, do not relabel the user as failing their energy choice.

## Integration and dependencies

F11 renders effort honestly; F12 presents cooking steps from the same version. F08 retrieves a simpler supported variant, and F16 can rank previously manageable meals. F13/F51 require reviewers to validate preparation estimates and operation tags.

## Execution plan

- Define energy-policy evaluator and metadata completeness validator.
- Build EFFORT with keyboard/screen-reader-friendly controls and custom time validation.
- Connect current-day constraints to the plan snapshot and explanation renderer.
- Record effort_no_match and effort_changed_before_acceptance without inferring wellbeing.

## Acceptance and release gates

Test an apparently short recipe with long waiting time, hidden heating in assembly mode, missing equipment, stale saved energy and absent effort metadata. The chosen hard limits must survive every adaptation and Something else action. Proposed validation compares stated estimates with observed preparation during recipe testing. Roll out energy_matching by catalog coverage; if policy metadata is defective, withdraw affected recipes rather than silently broadening limits.
