# F54 — Telemetry, reliability and release control

## Strategy
Observe whether a person gets a feasible meal and whether the service behaves correctly, without recording their private diet or messages. Production readiness requires observable workflows, kill switches, tested recovery and traceable releases.

## Experience and screen design
Members see meaningful loading, queued, pending, failed and unavailable states, with trace-safe support receipts. ADMIN_INCIDENT shows aggregate dependencies, worker queues and runbooks. ADMIN_FLAGS stages and applies audited feature changes; ADMIN_AUDIT records who changed operational controls. Health data and internal technical detail stay out of the normal cooking flow.

## Production sequence
Each request accepts a trace context and returns a support-safe request ID. Allowed analytics contain screenId, actionId, featureId, coarse outcome, duration bucket, platform and schema version; no raw prompts, ingredient exclusions, captions, messages, emails or signed URLs. Database transactions write domain events to the outbox. Consumers deduplicate and expose retry/dead-letter state. Metrics and sampled traces feed service alerts; threshold breaches activate runbooks and scoped flags.

## Data and API contracts
Versioned telemetry schema, outbox/consumer inbox, idempotency receipts, feature flag revisions and operational audit. Staff endpoints cover health, staged flag changes, bounded replay and media-publication pause. Public configuration exposes only client-compatible capabilities and schema versions. Event contracts include producer ownership, aggregate revision, idempotency key, retention classification and allowed payload fields.

## Permissions and lifecycle
Member analytics follow approved consent/purpose settings; essential security and reliability processing is documented separately. Staff operational commands require on-call role and reason, with secondary approval where configured. Replays are bounded and cannot blindly re-notify users or recreate deleted resources. Secret/config rotations use managed server storage; no vendor secrets ship to clients.

## Failure and offline behavior
Telemetry failure cannot block cooking. Client analytics queues have size/age caps and drop permitted low-priority events rather than spilling private payloads. Outbox backlog means effects are pending; source transactions remain authoritative. When planning interpretation fails, use deterministic structured input/cached reviewed options where eligible. Media/billing outages isolate their features while free private cooking remains available.

## Integration and dependencies
All modules use one request/error/event envelope and one observability library. Proposed pilot sizing and SLOs, database backup/PITR and media/queue runbooks are in architecture docs. Metrics distinguish tapping Make Mine, accepting a plan, self-reported making and sharing; no tap is falsely counted as a cooked meal.

## Execution plan
Create telemetry allowlist and schema validation, instrument requests and critical workflows, deploy dashboard/runbook pairs, set incident ownership and review redaction. Implement flags with dependencies and kill switches, staged migrations, synthetic probes and scheduled restore/reconciliation drills. Add deployment checks for compatibility, data retention and saturation.

## Acceptance and release gates
Load test the declared pilot envelope, exercise process/worker/database/provider failures, restore a backup and replay deletion tombstones before reopening access. Confirm trace samples exclude user content and signed URLs. Targets are explicitly proposed, not measured: 99.9% API availability at pilot, bounded ordinary read latency, and no unauthorized disclosure in adversarial tests. A failed SLO test changes the rollout plan; it is not hidden by a dashboard average.
