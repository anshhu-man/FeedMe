## Runtime integration

One application-lifetime `PrivateSessionRuntime` owns the session boundary, credential writes and work registry on its serialized dispatcher. Call `prepareInterruptedSetupDiscard()` only from STARTUP, SIGNED_OUT, RESTORE_REQUIRED or RECOVERY_REQUIRED with no lease. Present its safe booleans (`hasCredentials`, `hasEmptyWork`, `hasEmptyPrivateStorage`) to the user, without exposing scope, keys, revisions, configuration or cleanup targets.

Suggested confirmation copy: “Discard this incomplete local setup? This removes its selected local sign-in details and empty setup storage. Saved meals, posts and scheduled work are not eligible. Your cloud account is unchanged. You will need to verify your identity again.” A canceled prompt does nothing. UI integration and wording review remain separate work.

Only a deliberate confirm calls `confirmInterruptedSetupDiscard(proposal, freshOperationUuid)`. A proposal is opaque, nonserializable and bound to its issuing runtime instance, lifecycle generation and immutable configuration. Recovering, composing, retiring, canceling verification or closing invalidates earlier proposals. Another runtime cannot consume it. A valid completed operation returns STARTUP, not a login or a global-empty assertion; run the normal recovery classification before explicit verified create/restore.

Prepare reads metadata only and does not read credential secrets, invoke a provider, generate a UUID, activate a lease, run key garbage collection, write any store or cancel native work. Both preparation and confirmation bracket repeated exact evidence with the independent control revision and bytes. Lifecycle/process retirement is checked after asynchronous observations. Confirmation refuses stale evidence before persisting cleanup authority; it never silently retargets the proposal.

## Eligibility and preservation rules

There must be at least one authenticated selected credential or work metadata anchor. Scope is derived from that selection, never supplied by a UI account string. If both selections exist, their exact scopes must agree. Work must be absent or nonretiring with zero entries. Private storage must be absent for that exact owner or have zero rows of any kind, including tombstones, unknown-schema rows and activation bindings. Any activation binding therefore makes this empty-only path ineligible, regardless of whether the binding is valid.

An absent activation binding alone never permits deletion. Unreadable/unauthenticated control, credential or work metadata, missing active private-data keys, unknown native inventory, scope mismatch, pending logout/discard or distinct `PendingCreate`, any saved row or any native ticket stops this workflow and preserves evidence. A credential CREATE plan uses its own recovery coordinator, never this workflow's ordinary credential/work/data cleanup. Data-only unknown owners are not enumerated or guessed. Other owners remain untouched. A guest may explicitly discard its own eligible local setup, but this never converts or merges that guest into an account.

Authenticated selected credential metadata does not prove its token key/blob is usable. An already-open native store may still permit exact local retirement of that selected incarnation when its key or blob is missing or undecryptable: no secret read, recreation, provider request or login is involved. A missing manifest/install-index key or unknown inventory does not provide that authority and remains blocked at the native factory. Missing private-data keys are different: empty-owner preparation requires the current owner key and will fail.

Unbound fragments have no trustworthy previous configuration digest. This flow does not claim they match the current issuer: it sends no credential to an issuer and grants no session. The proposal is bound only to the currently owning runtime configuration, and any actual activation binding is rejected by the zero-row rule.

## Durable execution and retry

The existing independent retirement-control protocol adds a distinct `setup-discard-pending` intent. It stores the operation UUID, selected scope and explicit optional credential incarnation, work origin and authenticated private-data target. Missing resources remain null, not fabricated IDs. At least one credential/work anchor is required. Only present targets produce required steps; a checkpoint cannot claim a step for an absent target. Normal logout's existing non-null protocol remains compatible.

After checking the exact expected control record and inactive boundary, the coordinator installs a non-cancellable process intent before its first barrier write. No cleanup happens before that independent durable barrier succeeds or an ambiguous commit is reconciled to the exact intended bytes. A failed barrier leaves artifacts intact and the process gated. Process memory alone cannot survive power loss before a successful barrier. Credential CREATE has a separate pre-write ownership protocol. Low-level data plan/selection is available; its separate existing-only abort component is now verified, but the runtime journal, work-origin planning and refresh recovery remain unfinished. This ordinary empty-discard protocol does not fall back to that planned-data capability.

Execution proceeds through present work, credential and private-data targets, checkpointing each success. Work uses an empty-only conditional CAS that never invokes native cancellation. Credentials retire only the captured incarnation. Data authenticates the original owner/generation/key target and checks all rows are still absent before a local fence or key deletion. Both empty checks execute under their resource's mutex; the application must retain exclusive native-store ownership and must not mutate credentials outside the session owner. This is not a cross-store transaction.

Before independent cleanup, a present private-data target is authenticated and checked empty. Independent typed cleanup failures remain visible in the pending progress; successful independent steps may continue. Restart/retry uses only the originally persisted optional targets and remaining checkpoints, never newly captured resources. Data recovery accepts an exact already-retired target or original target whose key disappeared during a prior interrupted retirement, but rejects a newer owner generation. Missing empty-only work capability is an explicit failure, never a fallback to populated-work retirement.

Every restoration, diagnostic, credential/private-data access and work-admission control gate recognizes ordinary logout, setup-discard and the distinct `PendingCreate` intent as blocking. Only idle/completed control permits normal access. Pending CREATE is never cast into ordinary cleanup targets or automatically aborted by logout/discard recovery. None of these intents bypasses authentication or reopens a lease.

## Implemented credential ownership and remaining native writes

The implemented [credential CREATE recovery handle](PLANNED_CREDENTIAL_CREATE.md) authenticates one previously durable plan and admits only its exact artifacts alongside an exact prior/selected/consumed manifest state. It is not a general orphan-repair API.

Credential CREATE now plans before key creation using a native-random incarnation, exact empty-slot/planned revisions, purpose, opaque target and HMAC-bound canonical payload. The runtime persists it independently before exact native writes. Explicit abort durably consumes an unselected plan before removing its artifacts; exact selected replay never regenerates missing key/blob material, and selected abort re-acknowledges selection durability before key-first deletion. Plan-qualified create/abort manifest temps are implemented. A global legacy `manifest.bin.pending` remains unattributable to the plan and blocked. Tests cover actual Keystore/files, controlled native interruption and explicit coordinator recovery, not hard-kill or power-loss proof.

[Planned private-data activation](PLANNED_STATE_ACTIVATION.md) supplies a low-level authenticated predecessor/key plan and exact selection commit. It returns only `Unit`: no private-store handle, retirement target, lease or durable journal-completion acknowledgment. The separate [planned state recovery](PLANNED_STATE_RECOVERY.md) code exposes only inspect/abort/close. Every empty-only abort commits an actually changed V2 receipt and consumed generation before exact key deletion, including ABORTED retries; same/foreign historical receipt references prevent candidate-key reuse. Source-bound shared/native verification passes for this bounded component. Planning, commit and restricted recovery run no GC; normal open/resume retain cleanup, and normal opening alone may migrate exact V1 to V2. Recovery requires API27+ and existing V2/files/lock/index, rejects existing journals and unknown children, and never initializes. Returned-handle close retries; failed construction plus failed cleanup close remains fenced until process restart.
