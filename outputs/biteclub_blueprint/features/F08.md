# F08 — Make It Easier

Phase: first release. Owner modules: planning, catalog.

## Strategy

Make “too much work” a useful input before someone abandons dinner. Simplification must reduce a documented burden—active preparation, equipment, cleanup or total time—using a reviewed version. Shortening instructions while leaving the same work is not a successful simplification.

## Experience and screen design

RECOMMENDATIONS, RECIPE and VARIANT expose Make it easier. A compact choice on ADAPT allows Less prep, Fewer dishes, Less time or Easier overall; the default can be Easier overall. VARIANT presents the proposed change beside the original effort: “Uses one bowl instead of a pan and bowl,” with any changed ingredients visible. Keep original remains available. When no easier supported version exists, show an honest empty state with Something else and Edit limits. During an active cook session, simplification opens a separate proposal and warns about already completed preparation; it never replaces active steps automatically.

## Production sequence

1. Authorize the plan and pin its current version plus user's simplification goal.
2. Search reviewed simpler variants first, then eligible alternative meals if the user permits a different dish.
3. Reapply hard constraints and availability checks.
4. Compare reviewed effort fields; require improvement on the requested dimension and disclose any regression on another dimension.
5. Persist an immutable child plan referencing parentPlanId; acceptance changes the client's selected plan, never the former plan's content. Starting a different recipe requires a new cooking session; preserve or explicitly abandon the former session.

## Data and API contracts

simplifyPlan: POST /v1/plans/{planId}/simplifications with Idempotency-Key and If-Match.

    {"reason":"easier","simplificationGoal":"lessCleanup","allowDifferentMeal":false,"constraints":{"ingredientIds":["00000000-0000-4000-8000-000000000011"],"energy":"little","equipmentIds":["pan","bowl"],"servings":1,"hardExcludedIngredientIds":[],"maxTotalMinutes":15}}

Return an immutable Plan with parentPlanId, recipeVersionId, recipeSnapshot, changes and reasons. The UI derives before/after effort deltas from the two pinned snapshots and shows authored reasons; it must not expect an undeclared effortDelta transport object. An accepted child plan ID is the source for POST /v1/cook-sessions; reading it alone does not mutate a running session. noMatch and the returned reason explain when no simpler supported version exists. Preserve before/after content versions for auditing. Reduced active time cannot compensate for exceeding a hard total-time limit.

## Permissions and lifecycle

The action changes the current request, not the user's permanent abilities. Only explicit feedback may create a recipe-specific effort memory. Original recipes and authorized saves remain available. The language provider can interpret “I don't want to chop” into a goal but cannot delete essential preparation steps or manufacture a reviewed shortcut.

## Failure and offline behavior

If catalog status changes between proposal and cooking, return RECIPE_UNAVAILABLE and refresh. Concurrent plan edits receive 412; do not apply simplification to a different unseen recipe. Offline, display already cached supported easier variants with their version labels; server-authorized new matching waits for reconnect. If the operation times out, retain the original and retry with the same key. Never replace an unsynced active cook state as a recovery shortcut.

## Integration and dependencies

F11 supplies comparable effort metadata, F13 owns reviewed variant relationships, F05 enforces limits, F12 manages session boundaries and F09 retrieves a different meal. F36 community shortcuts cannot enter this engine until reviewed through content administration.

## Execution plan

- Model simplification goals and validated before/after effort deltas.
- Implement candidate traversal with monotonic improvement on the requested dimension.
- Build comparison, Keep original and no-match states.
- Add active-session transition guard and emit simplification_offered/accepted with dimension codes.

## Acceptance and release gates

Test a variant with fewer words but identical work, a faster variant requiring unavailable equipment, an excluded replacement, two simultaneous plan changes and simplification after cooking begins. Every offered result must demonstrate a reviewed improvement and disclose tradeoffs. Gate simplify_plan on verified variant pairs; rollback disables new proposals but preserves original plans, saved variants and running sessions.
