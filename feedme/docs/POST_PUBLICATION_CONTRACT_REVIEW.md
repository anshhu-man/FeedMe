# publishPost: two supported draft branches

14 September 2026. Initially a read-only proposal during the tenth full-source freeze. After tenth acceptance, root approved the four-case branch interpretation below and clarified active F31 prose for the [eleventh implementation package](PARALLEL_SOCIAL_DRAFT_PUBLICATION.md). The API operation, headers and wire field set are unchanged. Implementation is now assigned; this review itself is not evidence of publication code, migration, HTTP, provider integration or release acceptance.

## Recommended interpretation

Support both canonical branches, while requiring an explicit, versioned reference whenever a server draft already exists. This needs a narrow central prose clarification, not another endpoint or wire field.

The [API JSON](/Users/LOCAL_USER/Documents/ChatGPT/Career/outputs/biteclub_blueprint/architecture/04_API_Contract.json) defines `publishPost` as `POST /v1/posts`, with UserBearer, registered X-Device-Session and Idempotency-Key, returning `201 Post` plus ETag. **There is no If-Match header for this operation.** PostWrite requires caption, mediaIds, audience, keepOnPlate, allowRecipeSaves, saveDisclosureVersion and clientDraftId. draftId and draftVersion are independently optional. Its example omits both. The [PUBLISH_STATUS.01 registry entry](/Users/LOCAL_USER/Documents/ChatGPT/Career/outputs/biteclub_blueprint/registry/screen_registry.json) repeats that required-field set and no-pair example, while requiring explicit Publish, a validated draft and ready sanitized media.

[F31](/Users/LOCAL_USER/Documents/ChatGPT/Career/outputs/biteclub_blueprint/features/F31.md) describes the server-saved path: publish carries the reviewed draftId/version, locks that revision, matches the previewed fields, and atomically records one publishedPostId. It also makes Save a deliberate action and distinguishes an upload lifecycle root from a social PostDraft. Reading this sequence as the saved-draft branch reconciles the contracts; reading it as an unconditional requirement contradicts the API and registry's no-pair example. Central prose should explicitly name the two branches before implementation claims full fidelity.

| Supplied pair and current root | Proposed behavior |
| --- | --- |
| Both draftId and draftVersion | Require the exact owned server draft, same clientDraftId/generation, live editable status, exact version and matching reviewed content. A foreign/missing draft remains non-enumerating; changed version conflicts; expired/terminal state cannot publish anew. |
| Neither; no server draft or prior publication exists for this owner/clientDraftId | Treat the complete submitted PostWrite as the explicitly reviewed local-draft snapshot. Validate every field and current authority in the publication transaction. An existing owned upload root is allowed; text-only publication may reserve that internal lifecycle under the same lock. Do not silently create a resumable PostDraft or claim a server revision was reviewed. |
| Neither; a server draft exists for this owner/clientDraftId | Reject as a semantic conflict requiring the client to refresh/review and send the pair. Do not look up and adopt the latest version, ignore a saved draft, or bypass its expired/discarded state. This is state-dependent validation, not rejection of the entire optional branch. |
| Exactly one pair field | Reject semantic input with the declared 422 response. Do not ignore draftId, infer draftVersion, or interpret a version without its resource. |

The last row is **schema-valid today**: PostWrite has no dependentRequired/all-or-none constraint, and neither field is required. Its semantic rejection is justified by F31's exact reviewed resource/version requirement and the meaning of this pair, not by pretending the current schema already rejects it. If the central contract later adds an all-or-none schema constraint, that is a separately reviewed validator change; it is not performed here.

## Exact reviewed material, not inferred consent

For the server-draft branch, compare all overlapping PostWrite choices with that immutable reviewed draft revision: caption, altText, ordered mediaIds, audience selections, keepOnPlate, attachment, allowRecipeSaves, saveDisclosureVersion and sourcePostId. Preserve absent-versus-present optional values and array order; normalize only established canonical UUID/JSON equivalence. Do not fill missing submitted optional choices from another revision. Strip/ignore client Audience.bindings for authority in both branches, consistent with its schema description, then derive current author membership generations at publish.

PostDraft defaults do not supply missing disclosure evidence. For example, PostWrite requires saveDisclosureVersion even though PostDraftWrite does not. Under exact saved-draft matching, a draft lacking that confirmed value must first be explicitly patched/reviewed; publication must not quietly amend the saved revision. Attachment eligibility must verify exactly one permitted source, actual review provenance, redistribution license, confirmed changes and current recall state. A private cookbook copy or cooking pin is not a redistribution grant. These requirements follow the [data model](/Users/LOCAL_USER/Documents/ChatGPT/Career/outputs/biteclub_blueprint/architecture/03_Data_Model.md), [F24](/Users/LOCAL_USER/Documents/ChatGPT/Career/outputs/biteclub_blueprint/features/F24.md) and [F30](/Users/LOCAL_USER/Documents/ChatGPT/Career/outputs/biteclub_blueprint/features/F30.md), not the truth of client rightsBasis/reviewStatus strings.

The no-server-draft branch has no historical server revision to compare. Its exact submitted body is the immutable publication request; the client must capture it only on the deliberate Publish action and retain it through uncertainty. Neither token validity nor a READY asset proves a person saw the preview. The server validates current account/device/terms, eligible content and audience, and the explicit requested choices; it must not invent a consent timestamp, synthetic confirmation, stronger professional-review label or new Boolean field to claim more evidence than this protocol carries.

## Same transaction and one publication identity

Use the actual [DurableCommands](/Users/LOCAL_USER/Documents/ChatGPT/Career/feedme/server/src/main/kotlin/com/feedme/server/db/DurableCommands.kt) protocol, with distinct new-execution and replay authorization. Bind the original body, including pair presence, to the original account-scoped command key; do not add If-Match. Preserve cancellation/unknown-commit behavior and validate the complete response size before commit.

Proposed lock order extends, rather than bypasses, [PostDraftAuthority](/Users/LOCAL_USER/Documents/ChatGPT/Career/feedme/server/src/main/kotlin/com/feedme/server/social/drafts/PostDraftAuthority.kt):

`current principal/device → command receipt → owner draft-list head → stable clientDraft lifecycle → publication identity / optional PostDraft → content and circle authority → media UUID order`

All callbacks use that same connection, with no network calls, nested public transactions or separate successful preflight as permission. Fresh database time and current eligibility must be rechecked after potentially waiting authority locks. Publish-versus-edit/discard/upload/worker/revocation races must serialize on the same roots. The current PostDraft public methods and MediaStore public methods each own transactions; do not call them from the new publication transaction. Add narrow same-connection helpers instead.

Persist a unique publication identity for **environment + owner + stable clientDraftId**, pinning lifecycle generation, postId, original command/hash and optional reviewed draftId/version. This is proposed internal persistence, not a wire field. Also enforce at most one publication for a supplied server draft. Keep this identity after post deletion, draft expiry and seven-day command-receipt compaction: neither another key nor a later media generation may recycle the same clientDraftId into a second post. A different key against an already-used clientDraftId conflicts rather than manufacturing another successful publication; same-key exact replay is the recovery path.

One transaction creates the canonical Post, selected-media associations with stable positions, current audience-generation rows, immutable attachment/save-policy material when applicable, publication identity, original201 receipt, and registered `social.post.published.v1` fact. The [event registry](/Users/LOCAL_USER/Documents/ChatGPT/Career/outputs/biteclub_blueprint/architecture/05_Events.md) defines its data as postId, authorUserId, aclVersion and expiresAt; no private draft payload belongs in it. Create additional registered facts only for their actual implemented effects, not a fake feed/notification. publishedAt is fresh server time, expiresAt is publishedAt +24 hours, and keepOnPlate is independent. Required author, capabilities, savePolicy and reactionCounts must be canonical, derived from actual current authority and effects, never placeholders to make validation pass.

For the explicit branch, mark the exact PostDraft published and retain publishedPostId, increment its version and update its owner list head atomically. Do not mutate its private content while marking the terminal state; V009 currently permits a terminal transition only with unchanged content/expiry and the next version. Publication is not another editable-draft event: the existing internal draft-change event admits only draft/discarded. The canonical published event is the publication fact; any additional draft-sync contract would require explicit review.

For either branch, exact cached response disclosure still needs the current verified owner/device, exact publication lineage and applicable current content/recall/privacy authority. A receipt is not renewed permission to publish, expand an audience or access media. Replays must never substitute a later Post response or re-run publication to hide an unavailable original result. Define historical receipt disclosure under later post editing/deletion/recall alongside the Post lifecycle implementation, preserving original-success semantics only where disclosure remains permitted. Existing receipt expiry remains explicit; absence/expiry never permits a replacement publication identity.

## Essential lifecycle integration, including the no-server-draft case

The current [MediaAuthority](/Users/LOCAL_USER/Documents/ChatGPT/Career/feedme/server/src/main/kotlin/com/feedme/server/media/MediaAuthority.kt) already requires shared draft/publication locks and actual unattached checks. However, [MediaStore.validateDraftReferences](/Users/LOCAL_USER/Documents/ChatGPT/Career/feedme/server/src/main/kotlin/com/feedme/server/media/MediaStore.kt) intentionally accepts pending/rejected editable metadata and is **not a publish-ready validator**. A new same-connection attach helper must lock selected assets and require exact owner/root/generation, READY state, actual immutable sanitized derivative/safety evidence, and no conflicting attachment. No object-store signing or mutation belongs inside the SQL transaction.

There is a concrete composition requirement for direct publication: `PostDraftLifecycle.requireEditable` currently sees an absent PostDraft as no server-draft restriction. The upload root stores generation but no published state. A unique Post row alone therefore does not stop later uploads, worker admission or a new PostDraft creation under that already-published root. All those admission paths must consult the new durable publication identity under the same lifecycle lock, including text-only direct publication. Close the root to new publishing/processing effects without pretending a resumable server draft was created.

Selected media become attached to the new post; they must not enter draft-discard cleanup. Unselected uploads and already-issued late writes still need exact purpose-fixed cleanup/retention under their original deadlines. Reuse V007/V008 immutable write-intent and cleanup lineage, and specify the bounded orphan-retention policy before enabling this composition. Do not call the existing whole-root discard helper after attachment: it deliberately rejects attached media. Ownership, provider settlement and later post deletion remain separate from merely observing a cleanup row.
