# F01 — Make Mine

Phase: first release. Owner modules: planning, catalog; integrates social and memory.

## Strategy

Turn a friend's shared meal or an existing saved recipe into an achievable version for the viewer. Success means the viewer accepts a feasible meal; a tap is not evidence they cooked it. Launch adaptation is restricted to published reviewed recipe versions and reviewed substitution edges. An unverified community recipe may be displayed with its provenance but cannot acquire a reviewed badge through adaptation.

## Experience and screen design

STORY, POST, RECIPE and COOKBOOK expose Make Mine when a supported source exists. ADAPT shows the source title and compact controls for available ingredients, time, energy and equipment; saved food exclusions apply privately. The primary action is Find my version. VARIANT compares source and result using explicit changes such as “carrot replaces cucumber,” preparation, utensils and missing ingredients. Buttons are Cook this, Save recipe, Make it easier and Back. Opening ADAPT does not publish preferences or notify the source author. If no source recipe is available, show Ask for recipe and a separately labelled related-recipe option; neither promises reconstruction from a photo.

## Production sequence

1. Resolve the source and authorize the viewer; check recipe publication and recall status.
2. Load an immutable constraint snapshot, applying hard exclusions before candidate generation.
3. Traverse only reviewed substitution edges compatible with the pinned recipe version. Recalculate every affected ingredient, step and effort estimate; reject an incomplete variant.
4. Rank feasible candidates by availability, effort and explicit taste preferences; return an immutable child plan with parentPlanId when adapting an existing plan. The original plan and active cooking version remain unchanged.
5. Revalidate on cook-session creation or saving. Save or optionally publish a later Your Take through their own explicit actions.

## Data and API contracts

Operation createPlan uses POST /v1/plans when no plan exists. adaptPlan uses POST /v1/plans/{planId}/adaptations with Idempotency-Key and If-Match for the current plan revision.

    {"mode":"auto","intent":"makeMine","sourcePostId":"00000000-0000-4000-8000-000000000031","constraints":{"ingredientIds":["00000000-0000-4000-8000-000000000011"],"maxTotalMinutes":15,"energy":"little","equipmentIds":["pan"],"servings":1,"hardExcludedIngredientIds":[]},"preferenceVersion":7}

The example is a createPlan request from a social source; choose at most one source reference. adaptPlan instead takes AdaptRequest with reason=makeMine and complete constraints. Return canonical Plan fields id, version, parentPlanId when applicable, recipeVersionId, constraints, recipeSnapshot, changes, reasons and catalogRevision. A materialized variant is represented by the pinned plan snapshot and substitution references; internal proofs can retain their own version IDs without inventing extra transport fields. Response status is ready, needsConfirmation or noMatch; an empty candidate set is not a server error. A source post ID is contextual authorization, never a bearer permission. The authenticated principal or bounded guest owns the plan; guests cannot bypass the social source-access rules.

## Permissions and lifecycle

Social source access follows current audience authorization. A permitted immutable recipe save can remain usable after its source post disappears, under F30; original media and conversation never travel with it. Preserve credit where allowed, anonymize when required, and revalidate a source grant before issuing a new save. Food exclusions cannot be relaxed automatically. Plans pin content versions and expire as operational caches; private feedback lives separately.

## Failure and offline behavior

For stale preferences or plan revisions return 409/412 with refresh_required. A withdrawn recipe returns RECIPE_UNAVAILABLE and an alternative action. No match names the actual constraint and asks the user to change it. Offline, a cached authorized recipe may be read; new server-reviewed adaptations wait for connectivity. Do not queue an adaptation that silently changes the displayed dish later.

## Integration and dependencies

Depends on F03–F13 constraint and catalog contracts, F19/F30 save grants, F25 attribution, and F39 private preferences. Kotlin shared planning models drive identical checks on both platforms; server matching is authoritative.

## Execution plan

- Implement source resolver and object authorization tests before connecting STORY.
- Add versioned substitution graph evaluation and a deterministic candidate fixture set.
- Build ADAPT and VARIANT with comparison rows and explicit no-match states.
- Connect session/save transitions; emit plan_adaptation_requested and plan_adaptation_resolved with reason codes, never raw dietary text.

## Acceptance and release gates

Test excluded ingredients introduced through substitutes, deleted posts with an existing authorized save, stale content revisions, replayed requests, inaccessible post IDs and an unsupported photo. Identical snapshots must yield the same eligible set and stable tie ordering. Cross-platform interaction tests must reach Cook this without social sharing. Enable make_mine only for reviewed catalog cohorts; disabling it removes new adaptation actions while preserving authorized saved recipes and active cooking sessions.
