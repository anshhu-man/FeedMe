# F27 — Reactions

## Strategy
Reactions provide a small, optional acknowledgement between circle members without turning meals into a contest. Launch with a reviewed set of food-neutral emoji and no public ranking, streaks, or reaction-based feed order. A person can remove their reaction as easily as adding it. Proposed evaluation focuses on successful, reversible interactions and abuse rates.

## Experience and screen design
`STORY` and `POST` offer a labelled reaction button and an accessible picker. A selected reaction is visibly distinct with a text label for assistive technologies; color alone is insufficient. In this scope, only the post author sees the aggregate and actor list, while each viewer sees their own reaction. The author opens this summary within `POST`; it does not require a new screen. Long presses must have equivalent labelled buttons. There is no automatic notification permission prompt.

## Production sequence
Selecting a reaction calls `POST /v1/posts/{postId}/reactions` with `{kind}` and an idempotency key. The canonical kinds are `heart`, `looksDoable`, `makingThis`, and `yum`, rendered with accessible labels and optional emoji. The transaction authorizes the visible post, upserts the viewer’s row, increments its version, and writes `reaction.changed`. Replacement never increments a total twice. Removal uses `DELETE /v1/posts/{postId}/reactions/me` with `If-Match`. The response reconciles optimistic state. Notification workers coalesce changes and recheck settings and blocks before sending.

## Data and API contracts
`Reaction(postId,userId,kind,version,createdAt,updatedAt)` has a unique `(postId,userId)` constraint. `GET /v1/posts/{postId}` returns a bounded reaction summary and actor list only to the author; other authorized viewers receive only their own row. The permitted kinds are versioned in the API contract. Errors include `REACTION_UNSUPPORTED`, `POST_UNAVAILABLE`, `VERSION_CONFLICT`, and `RATE_LIMITED`. Payload hashes bind durable idempotency keys so replay cannot change the originally requested reaction.

## Permissions and lifecycle
Reaction creation requires current post access, including valid Today or Plate placement. Private recipe-copy ownership is insufficient. A user may remove their own reaction through an owner-authorized cleanup path even if the post has become unavailable; no post content is returned. Blocking or account deletion suppresses the actor from summaries and pending notifications. Post deletion removes reaction visibility and queues cleanup; an expiry worker is not the source of permission enforcement.

## Failure and offline behavior
Offline reactions may show a pending local state but are not delivered until reauthorization. Keep only the latest intended reaction per post in the local queue; do not replay a series of obsolete toggles. A rejected retry rolls back to the latest server state and explains unavailability without revealing the cause. Request timeouts query current state or replay the same key.

## Integration and dependencies
Depends on F21/F22 post access, F41 notification preferences, and F42 blocks/reports. Reaction events must not feed personal food-preference memory: liking a friend’s picture does not establish a food preference.

## Execution plan
Implement the unique-row mutation and authorization first, then picker accessibility, optimistic reconciliation, and notification coalescing. Measure rejected reactions and duplicate-event suppression without recording private post text.

## Acceptance and release gates
Test rapid emoji replacement, multi-device removal conflicts, duplicate retries, expiry during a request, author-only lists, and blocked actors. `social.reactions.enabled` blocks new reactions and hides counts; own-reaction deletion remains available. Require deterministic single-row outcomes and no preference-memory writes.
