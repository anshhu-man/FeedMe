## Why an exact binding is necessary

Independent credential, data and work stores can all contain the same account ID while belonging to different logins. Joining their scope strings after a crash could associate newer credentials with older cached meals or timers. The runtime therefore persists one immutable version-1 record inside the exact private owner database, at internal key `session-activation/binding-v1`.

It binds storage scope, credential incarnation UUID, work-origin UUID, the current authenticated 137-byte data-retirement target, and an immutable trusted-configuration digest. Credential refresh revision is deliberately excluded: a valid refresh of the same incarnation does not rebind existing commands. The record has a 4 KiB limit, strict exact keys/Unicode/UUIDs, a 64-character lowercase configuration digest and exact lowercase target encoding. It contains no password, access token, refresh token, guest proof or executable URL. Structural decoding alone never authenticates the target.

The configuration digest must be generated by the trusted native configuration pipeline from the actual approved API environment, issuer, client/callback configuration and owner-mapping contract. It is not a user-selected environment label, permission to trust arbitrary endpoints or a substitute for provider verification. No production provider/configuration has been selected or deployed.

This active binding can live with private data because explicit logout first persists all exact cleanup targets in the independent retirement control ledger. Once that barrier exists, erasing the active binding cannot destroy cleanup authority. Interrupted initial setup without a complete binding is a blocked repair state; the runtime does not reconstruct the record by matching scopes, overwrite an existing guest, delete unknown keys, or invent an activation journal entry on restart.

## Application integration

The trusted platform root owns one serialized dispatcher, one `SessionBoundary`, the native credential store, independent control/work stores, private database, actual cancellation adapter, fresh UUID source and a reviewed domain execution policy. It opens one runtime and closes all native stores separately after closing it. No other component activates that boundary or writes the credential slot. UI receives presentation metadata; native repositories receive `PrivateSessionAccess`, never provider secrets.

`NativeSessionVerifier` is mandatory and has no default success implementation. Its `acquire` must finish actual provider verification, explicit FeedMe owner mapping and account bootstrap (or the genuine guest-session protocol) before returning credentials. Accounts without a registered device-session ID are rejected by this composition layer. F47's provider state/nonce/PKCE/issuer/audience checks, challenge routing and lost bootstrap response reconciliation are still the real adapter's responsibility. Bootstrap's current DTO does not provide an account ID: do not infer ownership from email or `Profile.id`; the owner-mapping contract still needs resolution before live use.

`restore` receives old secrets only after local binding/configuration/data/work checks pass. A configuration change must fail without handing old credentials to a verifier attached to a different provider or API. The verifier may return `OFFLINE_PRIVATE` only for explicitly permitted, previously verified local use. It cannot infer continuing server membership, recalls or account status while offline.

| Entry point | Actual behavior |
| --- | --- |
| `open` | Checks configuration digest, separate control/work objects, idle boundary and exclusive work-manager ownership; does not authenticate or activate |
| `recover` | Keeps outward access closed, finishes exact ordinary retirement and classifies signed-out/restore-required/recovery-required state; distinct pending CREATE remains gated for its own coordinator, never an automatic abort or lease restore |
| `create` | Requires signed-out and planned-credential capability, calls the real verifier, rejects occupied credential/work or existing active data, persists an exact credential CREATE plan independently before native commit, then creates data/work, commits the binding and captures retirement before publishing access |
| `restore` | Requires restore-required; checks binding scope/incarnation/configuration, active data resume and byte-identical fresh current data target, exact work origin, then verifier; reconciles incomplete work and captures exact retirement before publication |
| `cancelVerification` | Invalidates the current attempt and provisional lease immediately; late verifier results cannot write/activate; possibly committed initial writes become recovery, not guessed rollback |
| `retire` | Requires the exact published access and a fresh operation ID; closes admission, invokes the exact independent retirement barrier and retains pending cleanup on failure |
| `close` | Terminal in-memory closure and stale-handle fence, not implicit logout; closes its work registry while retaining durable state for a later verified restore |

The native stores are not one transaction. A failure after credential/data/work creation can leave evidence requiring user-visible repair. There is no automatic retry with fresh identity, silent guest conversion, compensating deletion of a current account, or proof of universal crash-safe initial setup. Same-process cancellation after a possibly committed write is conservatively fenced.

[Planned credential creation](PLANNED_CREDENTIAL_CREATE.md) implements the bounded credential-only pre-write gap: `PlannedCredentialCreateStore` is mandatory, with no legacy-create fallback. The runtime writes the authenticated plan into independent encrypted control and confirms exact durable readback before native material writes; it resolves that intent only after validating the exact returned credential snapshot. Data/work creation and activation-binding persistence follow afterward and still need their own integrated planned-write protocol.

[Planned private-data activation](PLANNED_STATE_ACTIVATION.md) provides `planActivation` and `commitPlannedActivation` at storage level, but the runtime has not adopted them. The commit returns selection-only `Unit`, never a private-store handle, retirement target, lease or durable journal-completion receipt. The separate [planned state recovery](PLANNED_STATE_RECOVERY.md) component is implemented as b.2b.2 IN_PROGRESS, with full/native verification pending. Every empty-only abort commits an actually changed V2 receipt and consumed generation before exact key deletion, including ABORTED retries; historical same/foreign-owner receipt references cannot be reused as candidate keys. Its restricted handle exposes only inspect/abort/close, not a new session capability.

The API27+ existing-only recovery factory rejects V1, existing journals and unknown children and never creates files/locks/keys/schema or runs GC. Normal opening alone may atomically migrate exact V1 to V2; normal open/resume retain their cleanup behavior. Returned-handle close can retry, but failed construction plus failed cleanup close remains a process-restart gate. Work-origin planning and a composite setup journal through binding/final lease publication are b.2b.3 TODO; no runtime/UI data-recovery path is added. A no-op selected replay adds no fresh sync, while the earlier post-successful-COMMIT exception represents a lost application receipt, not a proven original sync failure. Native syscall-failure verification is pending and whole-session power-loss proof remains absent; no universal extra-fsync rule or descriptor redesign is inferred.

Startup must inspect independent control before trying to open an ordinary credential store with partial inventory. A distinct `PendingCreate` blocks restore, repository/transport access, work admission and ordinary retirement/discard recovery. Its separate existing-only `CredentialCreateCoordinator` requires explicit abort confirmation or an already-confirmed durable abort request. It cannot decrypt credentials, create a lease, repair arbitrary orphan inventory or substitute ordinary cleanup targets. Exact native abort/durability, ABORTED inspection, acknowledged close and unchanged control are required before completion; completion is not automatic login.

## Private repository and effect gates

`PrivateSessionAccess` supplies an exact lease, origin, access mode, private-store facade and credential transport view. The private facade checks current runtime/lease and independent control before use, detaches mutation lists before suspension, blocks reading or mutating the reserved activation record and rejects unconditional erase. Explicit logout uses the captured retirement workflow. Its read/write result is rejected if the original access becomes stale while storage is suspended.

The transport facade is read-only and incarnation/lease-bound; it never exposes the refresh token. `OFFLINE_PRIVATE` rejects credential access for protected network transport even if an unexpired token happens to remain stored. This mode retains permitted owner data and timer operations, while refusing new background workers. The cooking repository still applies exact pin/recall/generation constraints; offline-private is not broad permission to perform social or purchase commands.

Work admission and callback policies read the independent control record directly and permit only idle/completed state. They recognize ordinary logout, setup discard and distinct `PendingCreate`; checking only the ordinary retirement subtype is insufficient. They must not call `LocalRetirementCoordinator.restorationAllowed()` while holding the work-registry mutex: that would invert the coordinator-to-work lock order during logout. Runtime/lease/origin are rechecked after asynchronous policy work. The domain policy must additionally validate the exact current desired ticket and recipe safety state. No native callback may directly display private data or dispatch a remote mutation merely because the OS delivered its UUID.

The retirement coordinator now clears its captured lease and registers its non-cancellable exact process latch before waiting for its own mutex. A suspended capture/restoration read cannot keep outward repository/transport authority alive during a newer logout request. Durable pending still precedes native cleanup. Its first-barrier/power-loss limitation remains unchanged: memory cannot survive process death if every durable barrier write failed.

The Android control-store factory now also requires this opener's successful creation of the previously absent directory before initializing a new idle file. Existing empty, lock-only or lost-all-state directories cannot reset a prior control revision even if all keys are absent. They are repair gates, matching the work-store provenance rule.

## Native evidence and limits

Android integration uses the actual public credential, control, data and work factories, AndroidKeyStore, private SQLite/files, AlarmManager and WorkManager inside `com.feedme.session.test`. The test APK explicitly targets SDK36; running on API35 is not API36-device, physical-device, real app UI or store-build certification. The storage test APK remains target26.

Public factories have fixed Keystore prefixes. Redirecting `noBackupFilesDir` does not isolate those keys. The integration sandbox therefore serializes one fixture, requires every exact fixed namespace to be empty beforehand, creates a new private UUID root, and only cleans the aliases/files it then owns after all store closes and exact native cancellations acknowledge success. Unexpected prior aliases or unacknowledged cleanup preserve the fixture; they are never wiped to make tests green. WorkManager databases and unrelated native requests are not reset or pruned.

Separate instrumentation invocations test explicit WorkManager initialization. Workers use the registry-supplied UUID as their actual WorkRequest ID, with one-day delays to prevent execution; timers are inexact one-day alarms. These fixtures prove exact identity wiring and cancellation, not a complete timer scheduler, foreground worker, reboot receiver or remote domain effect. Production timer receiver mappings must remain stable across upgrades while tickets exist, and worker chains must never cross origins.

Real provider signup/login/reset, account mapping, guest merge, refresh/bootstrap recovery, application UI, user-visible repair, iOS storage/credentials/work, API26-compatible credentials, device lock/restore/power loss, app hard-kill, physical-device and patched SQLite gates remain. No provider credentials, account setup, purchases, store upload or public deployment occurred.
