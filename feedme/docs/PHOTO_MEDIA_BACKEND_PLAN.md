# Photo media and composer backend plan

Status: design / implementation-ready task breakdown only. Written while the seventh [progress/cookbook/timers checkpoint](PARALLEL_PROGRESS_COOKBOOK_TIMERS.md) is running. No media implementation, provider configuration, migration, deployment or verification is claimed here. [BUILD_STATUS.md](BUILD_STATUS.md) remains the current evidence pointer.

## Product boundary

Preserve the original social concept: an intentional food photo or text post, shared with explicitly selected Kitchen Circles or Only you, can appear in chronological [Today](../../outputs/biteclub_blueprint/features/F21.md) for 24 hours and independently remain on [My Plate](../../outputs/biteclub_blueprint/features/F22.md). Private cooking works without posting or a social graph. My Plate is not the private recipe cookbook. A photo is not evidence of ingredients, quantities, food safety or a reviewed recipe.

The [Share Composer](../../outputs/biteclub_blueprint/features/F31.md) owns the explicit final Publish action and previewed audience, retention and recipe-copy choices. Upload completion and successful processing never publish automatically. Camera is optional; system selection and text-only posts remain valid. Default audience is Only you until deliberately changed. Publishing one's own photo does not authorize copying another post's media or redistributing a private saved recipe.

The next bounded implementation should begin with **owned quarantined photo upload, inspection and deletion**, then connect it to resumable drafts and an atomic photo/text publication transaction. This does not include deferred [F38 Short Clips](../../outputs/biteclub_blueprint/features/F38.md), avatar/profile editing, public discovery, automatic recipe inference, licensed music or face recognition. The common media schema includes clip/avatar values; unsupported kinds must fail explicitly, not be relabelled as photos. Later F38 prose informs the shared signed-delivery limitation, not permission to implement clips now.

## Exact canonical operations

The [OpenAPI](../../outputs/biteclub_blueprint/architecture/04_API_Contract.json) is the transport authority. Every operation below requires UserBearer plus the registered, currently bound `X-Device-Session`; none permits guest upload or guest social access. No multipart byte-upload endpoint is added to FeedMe: the canonical reservation supplies an external, restricted POST target.

| Package | Operation and route | Successful body / mutation controls |
| --- | --- | --- |
| Initial owned media | `prepareMediaUpload` — `POST /v1/media` | `201 Upload` + ETag; Idempotency-Key; `MediaPrepare` |
| Initial owned media | `completeMediaUpload` — `POST /v1/media/{mediaId}/complete` | `200 Upload` + ETag; Idempotency-Key; `UploadComplete`; **no If-Match** |
| Initial owned media | `getMediaStatus` — `GET /v1/media/{mediaId}` | `200 Upload` + ETag; owner status, not media delivery |
| Initial owned media | `deleteDraftMedia` — `DELETE /v1/media/{mediaId}` | `204`; Idempotency-Key + If-Match; unattached owned media only |
| Composer drafts | `createPostDraft`, `listPostDrafts` — `POST`, `GET /v1/post-drafts` | `201 PostDraft`, `200 PostDraftPage`; ETag; creation key; list cursor/limit |
| Composer drafts | `getPostDraft`, `updatePostDraft`, `deletePostDraft` — `GET`, `PATCH`, `DELETE /v1/post-drafts/{draftId}` | `200 PostDraft` + ETag for reads/edits; delete `204`; edits/deletion use key + If-Match |
| Publication | `publishPost` — `POST /v1/posts` | `201 Post` + ETag; Idempotency-Key; exact `PostWrite` |
| Post lifecycle | `getPost`, `updatePost`, `deletePost` — `GET`, `PATCH`, `DELETE /v1/posts/{postId}` | read/edit `200 Post` + ETag; delete `204`; edit/delete key + If-Match |
| Read placements | `getToday` — `GET /v1/posts/today`; `getProfilePlate` — `GET /v1/profiles/{userId}/plate` | `200 PostPage`; cursor/limit; Today additionally optional circleId |
| Authorized derivatives | `getMediaAccess` — `POST /v1/media/{mediaId}/access` | `200 MediaAccess`; **no idempotency key or If-Match**; fresh authorization on every issuance |

For `getPost`, the canonical query is **surface**, with today/plate/detail and default detail; do not implement the `placement=` name from older feature prose. `MediaAccessRequest` requires postId, surface and variant; photo variants are thumbnail/display, not clip. A media ID alone is never a delivery capability.

`MediaPrepare` requires kind, contentType, positive integer bytes, SHA-256 and clientDraftId; durationSeconds is optional. JPEG/PNG/HEIC are declared image formats. The schema does not itself constrain kind/type combinations, image dimensions or a maximum byte count. Those require an explicit disclosed photo-processing policy, with unsupported declared combinations rejected before reservation. The architecture proposes a 10 MB photo-input ceiling, not a proven provider limit; settle exact units and pixel/decode/response budgets before coding. Preserve exact integer/checksum validation without floating-point coercion.

`UploadComplete` requires only objectVersionId and sha256. It supplies neither a storage key nor proof that the upload is owned or safe. `Upload` requires id, version, createdAt, updatedAt and status; its exact status values are **awaitingUpload, processing, ready, rejected, deleted**. Optional uploadUrl/uploadMethod/uploadFields/uploadExpiresAt carry an upload capability. Storage keys, scanner reports, moderation evidence and raw provider errors are not additional response fields. Uppercase RESERVED/UPLOADED/FAILED states in feature prose must not leak onto this wire.

## Existing code to compose, and what is missing

- [PgTransactions](../server/src/main/kotlin/com/feedme/server/db/PgTransactions.kt), [DurableCommands](../server/src/main/kotlin/com/feedme/server/db/DurableCommands.kt) and [OutboxStore](../server/src/main/kotlin/com/feedme/server/db/DurableEvents.kt) provide real PostgreSQL transaction, exact command identity, replay and outbox foundations. Mutations and receipts must share the same commit. Unknown COMMIT/caller cancellation cannot be reported as definite noncommit or retried with a new identity.
- [SocialIdentityPolicy](../server/src/main/kotlin/com/feedme/server/social/SocialIdentityPolicy.kt) requires current account/device eligibility, active profiles and block-pair locking, with no accepting default. Community-terms/UGC eligibility, upload limits and purpose-specific processing authorization are additional mandatory integrations, not a Boolean supplied by the client.
- [CirclesStore](../server/src/main/kotlin/com/feedme/server/social/CirclesStore.kt) already persists circle membership generations and explicitly warns that `hasCurrentAudienceMembership` is only a foundation. That public helper runs its own transaction. It cannot certify a later publish, feed read or signed URL. Add a narrow supplied-connection authorization/binding seam sharing actual circle, membership, profile and block locks; do not call the current helper as an unlocked preflight.
- The configured [HTTP composition](../server/src/main/kotlin/com/feedme/server/http/FeedMeApplication.kt) and existing [SocialHttpRoutes](../server/src/main/kotlin/com/feedme/server/http/SocialHttpRoutes.kt) provide strict account/device, framing, schema, ETag, Problem and no-store patterns. A new explicit optional media configuration must preserve default closed product routes. Test authority fixtures are not a real provider.
- At this plan's original preparation point those components were absent. The ninth baseline implements configured media reservation/status/removal, processing/cleanup coordination and bounded photo decoding; the accepted tenth package adds PostDraft persistence and five configured HTTP operations, rechecked in the complete source-frozen run. See the [draft integration handoff](POST_DRAFT_INTEGRATION_HANDOFF.md) and [current package tracker](PARALLEL_RECALLED_COPY_DRAFTS.md). Actual private-object/safety providers, media-access signing, post publication, draft expiry writer and Today/Plate APIs remain unfinished. Existing SavedRecipe/Cooking stores do not grant social media or recipe redistribution rights.

Use the existing [data model](../../outputs/biteclub_blueprint/architecture/03_Data_Model.md) names and invariants: `platform.media_assets`, `social.post_drafts`, `social.posts`, `social.post_media`, `social.post_audiences` and the separately authorized attachment/save-policy tables. Add only the next expand-only migration after current history; preserve every earlier migration byte/checksum. Pin environment, actual account ownership, stable clientDraftId, server-generated media identity, expected bytes/hash and random quarantine key. Client filenames/URLs never choose a storage destination. A duplicate command is not a second media identity; different files under one draft must remain possible.

## Upload, processing and cleanup authority

Separate database decisions from external I/O explicitly:

1. **Reservation:** current verified account/device/terms/quota → original receipt → exact owner/draft lifecycle roots → reserve media/key/expiry and bounded response atomically. The mandatory signer can only produce a POST policy for that exact private quarantine destination, size/type/checksum restrictions and expiry. No arbitrary bucket/key/URL or public ACL is accepted. Avoid remote provider calls while holding long-lived database locks; local signing may use explicit configured credentials without exposing them in DTO diagnostics.
2. **Completion:** load the owned reservation and its exact key, inspect the immutable object version through a mandatory bounded object-verification adapter, then re-lock/revalidate principal, receipt, reservation version/expiry and draft state before committing processing plus `platform.media.upload_completed.v1`. Provider evidence must bind key, immutable version, actual size and hash; comparing the client's checksum with itself is not verification. Never HEAD a mutable key once and let a worker read whichever bytes later occupy it. Expired/replaced/foreign objects cannot advance state.
3. **Worker result:** consume the exact committed version with deduplication and an attempt/version fence. Independently sniff and fully decode in a resource-bounded process, validate size/dimensions, remove EXIF/location, scan, apply the actual moderation decision and re-encode allowlisted derivatives. Verify all intended derivative objects before an atomic ready transition/manifest version; incomplete results remain non-ready. A stale job after deletion, replacement or a newer attempt cannot resurrect access. Processing exceptions become bounded safe rejection codes, never provider details. No production all-clear scanner/moderator fallback exists.
4. **Removal:** exact owned unattached media version plus current attachment/draft checks → tombstone and durable exact-object cleanup intent in one transaction. Physical object deletion happens after commit, is idempotent, and retains retry/terminal evidence. Deleting a draft or an attached post uses its own lifecycle transaction; an unattached-media route cannot erase an active published attachment. An old retry cannot delete a replacement object or acknowledge a different incarnation.

Quarantine objects are never delivery origins. Serving originals because processing failed is forbidden. Raw upload completion, processing readiness and public publication are separate acknowledgements. Same-key replay rechecks current account/ownership/lifecycle before returning even a cached successful body. Response-byte admission happens before committing a success; bound capability fields and status/error projection through the same explicit service/HTTP policy.

The [event registry](../../outputs/biteclub_blueprint/architecture/05_Events.md), rather than abbreviated feature prose, defines `platform.media.upload_completed.v1` (mediaId, quarantineVersionId, checksum), `platform.media.ready.v1` (mediaId, derivativeSetVersion) and `platform.media.rejected.v1` (mediaId, safeReasonCode). A ready event updates composer status; it is never a Publish command. Captions, signed URLs/POST fields, object credentials, raw pixels, EXIF and moderation evidence must not enter general logs or domain events. Durable receipt storage must not accidentally retain an upload bearer capability through the generic `StoredReply` cache.

## Publication and current placement predicates

Following the media component, implement the composer boundary without weakening it to an automatic post-on-ready flow. Server draft state uses canonical draft/published/discarded/expired. Bind owner + stable clientDraftId; use exact revision preconditions for edits. Default self audience is a deliberate safe draft default, not fallback for invalid circles. A failed audience/media/rights check preserves the exact draft for review.

Publish locks current principal/terms, original receipt, draft, mutable audience/attachment rights roots and selected media in a documented deterministic order shared with removal/revocation. Require all media to be sanitized ready assets owned by the author and bound to the correct draft; no duplicate attachments, foreign original pixels or stale replaced versions. Derive author-membership generation bindings on the server; never trust supplied `Audience.bindings`. Commit one post per draft with the exact previewed fields, associations, ACL/save policy and outbox facts, then acknowledge. Retrying after uncertainty must preserve the exact client draft and original operation; committed publication can only be reversed through explicit post deletion.

Attachment `reviewStatus` and `rightsBasis` are assertions to verify against actual evidence, not evidence themselves. PrivateCopyOnly save/cooking rights do not permit full-card publication. A photo/text-only first implementation can keep attachment/sourcePostId/recipe-save enabling unavailable until those mandatory adapters exist, but must report that bounded limitation and not claim the whole composer or social recipe loop complete. Do not silently discard an attachment or true allowRecipeSaves.

Today requires published status and database time strictly before publishedAt + 24 hours. Plate independently requires published + keepOnPlate. Retention never extends Today or widens audience. For each query, detail read and media issuance, require current eligible author/viewer, valid author generation and viewer membership in at least one selected active circle, and no block in either direction; self is owner-only. Multiple matching circles return one post. An author who leaves/rejoins cannot revive old grants. Page cursors bind owner/viewer, surface, filter and stable `(publishedAt,id)` ordering, not an authorization snapshot. Delayed projections/expiry jobs never grant access.

`getMediaAccess` additionally verifies the selected media is actually attached to that authorized post and the requested derivative exists. Its signed URL is a bearer capability, with TTL at most 60 seconds and additionally bounded by the selected Today surface's remaining lifetime and any applicable grant lifetime. Plate availability must not extend a URL issued for Today. For detail, first resolve a valid placement; an expired nonretained ordinary viewer must not obtain media through a generic detail escape hatch. Owner-only management data is not implicitly a viewer media grant.

Audience narrowing/block/deletion prevents new authorized responses and capabilities after commit; already issued URLs retain their disclosed residual TTL and started transfers may finish. No immediate remote-pixel erasure claim is valid. Delete/retention/audience controls must remain reachable when new posting is disabled. Registered events are `social.post.published.v1`, `.audience_changed.v1`, `.plate_changed.v1`, `.expired.v1` and `.deleted.v1`, with their actual registry payloads; e.g. older F22 `post.retention_changed` prose is not a new event type.

## Internal decisions to settle before implementation

These are team contract/engineering decisions, not new requests for a user to choose a provider:

- **Expired upload capability versus exact replay:** prepare returns an expiring POST capability, yet its operation promises the original result on retry and F31 requires renewed slots without accidental duplicate media. There is no explicit renewal operation/mediaId in `MediaPrepare`. Freeze a reviewed renewal/capability-rendering contract before implementing it. Separate durable identity/result from bearer serialization, re-authorize every issuance and never return an expired URL as a usable retry or silently create another asset. Do not invent a route or change GET from status observation without review.
- **Draft binding:** `MediaPrepare` carries clientDraftId, not draftId. Local drafts precede optional server Save draft. Define owner-scoped upload-draft reservation versus a persisted PostDraft so ordinary photo selection does not secretly create a published/server draft or permit rebinding to someone else's draft. If a server draft exists, its terminal/expiry state must fence new uploads.
- **Reviewed publication revision:** `PostWrite.draftId` and draftVersion are optional in OpenAPI even though F31 requires exact reviewed server draft revision at publication. Resolve either an explicitly supported client-draft publication protocol or a reviewed required-pair alignment; do not silently reject a canonical valid request while claiming complete ingress, or treat the optional pair as permission to skip consent/version protection.
- **Bounds and status truth:** choose explicit photo byte/pixel/frame/CPU/time caps and capability/page response budgets. Unbounded mediaIds/draft/page arrays must not become truncated-as-complete responses or arbitrary total-post quotas. Draft-list ETag semantics need an owned collection revision. Unsupported formats and deferred kinds are honest policy failures, not schema substitutions.
- **Cleanup events and retention:** the registry has media completed/ready/rejected, not a dedicated media-delete event. Use a reviewed purpose-fixed transactional cleanup job or align a minimal event before producing one. The proposed 24-hour quarantine cleanup, 30-day draft expiry and derivative purge objectives require configured policy, exact references, deletion receipts and actual workers; they are not current guarantees. Legal/incident holds remain purpose-scoped and do not enable public viewing.
- **External verification race:** use immutable object evidence plus a second exact database fence, not slow remote I/O as an assumed atomic database lock. Specify signing/worker result acknowledgement and idempotent derivative/object writes explicitly; a readback of remote state is not proof a prior failed write was acknowledged.

Real identity/session/terms enforcement, licensed object storage and delivery credentials, tested image processing and malware controls, actual moderation/escalation staffing, account deletion/recall integration, privacy/retention approval and deployment are genuine external launch prerequisites. The architecture's S3/CloudFront names are a proposal, not authorization to purchase/configure them. This plan selects no provider or spend and adds no accepting production adapter.

## Five bounded implementation tasks

1. **Freeze four-media-operation SPI and invariants.** Resolve the capability-renewal/draft-binding decisions; add mandatory current-account/terms, private-object verification/signing and processing-result interfaces with no defaults. Add the next owned media/quarantine/attempt/cleanup migration and previous-checksum upgrade tests. Keep current publication/delivery routes closed.
2. **Build real PostgreSQL reservation, completion, status and deletion.** Use actual DurableCommands/outbox, exact immutable object evidence, typed expiry/mismatch, response admission and deletion-incarnation fences. Unit and real-PG tests cover account/device/environment denial, same-key replay and changed payload, verified-version overwrite races, size/hash/type mismatch, completion/delete races, lost commit receipt, cancellation and unchanged old migration history. External provider/sanitizer fixtures are explicitly synthetic; a test fixture returning READY is not moderation acceptance.
3. **Add configured four-operation HTTP and a real processor adapter boundary.** Test actual Ktor/CIO + PG, canonical headers/body/ETag/status, duplicated/framing/Unicode/bounds, no secrets in Problems/logs/receipts and default closed routes. Test worker redelivery, stale attempts, malformed/decompression-bomb inputs, EXIF removal, partial derivative failure and deletion before worker completion with a real decoder where available. No live storage provisioning or provider claim follows from adapter fixtures.
4. **Connect canonical drafts and explicit photo/text publish.** Implement the five draft operations and exact single-publication transaction, with same-connection audience generation bindings and positive owned READY evidence. Prove double tap/unknown commit, mismatched preview revision, revoked circles, upload replacement, retained self audience and no asynchronous auto-publish. Attachment/copy/remix capabilities remain separately gated until actual rights composition exists.
5. **Add current Today/Plate/post lifecycle and signed derivative ingress.** Implement the six post/placement operations plus `getMediaAccess` using the same authoritative predicates. Test all four Today/Plate combinations, expiry boundary, overlapping circles, author leave/rejoin, viewer removal, reciprocal blocks, audience/retention/delete races, stale cursors, foreign media/post substitution and capability TTL. Follow with actual recovery/purge workers, client capture/consent/accessibility and provider/device acceptance; do not call a fixture-backed configured component a shipped social release.

The initial deliverable is tasks 1–3 with a genuinely dependency-ready media store/HTTP boundary, not a replacement for the original social product. Tasks 4–5 connect that foundation to the intended Today/My Plate loop. No source, schema, runtime, provider or verification receipt is changed by this document.
