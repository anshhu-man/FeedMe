## Ownership and durable state

The registry has its own install-local encrypted database and Keystore namespace. It cannot rely on the retiring account's recipe database, command journal or credential key: cleanup must remain possible after those are erased. `AndroidSessionWorkStore` owns the fixed no-backup `feedme-session-work` directory and `com.feedme.session.work.v1` key prefix. These are internal development storage identifiers, not approval of permanent store application IDs.

The native factory shares the private-file, lifetime-lock and authenticated encrypted-SQLite implementation. New idle state requires this opener's successful creation of the previously absent directory, a fresh key namespace and new database. An existing empty, lock-only or missing-all-state directory fails closed; missing records/keys cannot be interpreted as idle or automatically repaired. Only the native factory can initialize it. The public wrapper exposes read/CAS/close, not owner activation, deletion or reset.

The version-1 record is at most 32 KiB. It has one idle state or one active/retiring origin containing exact storage scope, fresh origin UUID and at most 64 entries. Entries contain fresh ticket UUID, TIMER/WORKER kind, bounded logical ID and RESERVED/INSTALLED/CANCELLING phase. Logical IDs are private local identifiers, not executable configuration or recipe text. The codec rejects duplicate/unknown fields, malformed Unicode, future versions, coerced metadata, malformed UUIDs, duplicate ticket IDs and duplicate `(kind, logicalId)` pairs. Debug strings redact identities.

An origin is an exact login/guest incarnation, not just an account ID. The native composition supplies fresh cryptographic UUIDs and must never intentionally recycle them. This bounded ledger does not retain the history of every retired UUID or protect against whole-install rollback.

## Production integration contract

1. A single application-lifetime identity owner creates the serialized dispatcher and `SessionBoundary`. Open independent control first and route its exact intent before enabling private effects. Ordinary logout/setup discard and distinct credential `PendingCreate` block normal work; the latter uses its own explicitly confirmed existing-only recovery coordinator, not ordinary cleanup. Corrupt or absent initialized state enters explicit recovery, never a reset or synthetic login. A pending CREATE can explain a blocked ordinary credential factory only through its authenticated plan, not broad orphan adoption.
2. Initialize WorkManager explicitly through trusted startup composition. The session library removes only its default Startup initializer; other AndroidX initializers remain. Configure only trusted workers that independently respect the recovery gate. Initialization itself is not permission for an OS callback to execute private work.
3. Open `SessionWorkRegistry` with the durable work store, boundary, serialized dispatcher, exact native cancellation, fresh UUID source and mandatory admission/execution policies. Do not use always-true policies in production. Only one registry may own a given store; close the registry and its separately owned native store on shutdown.
4. After actual identity verification and durable retirement recovery, `createOrigin(lease, exactIdleRevision)` installs a fresh origin. The same origin must be used for that session's private command binding. `resume(lease)` only returns the existing matching origin; it does not initialize, authenticate, merge guests or repair an interrupted session setup.
5. Compose this registry as `SessionWorkRetirementPort` in the local retirement coordinator alongside the real credential and data adapters. Capture the exact original scope, origin, credential incarnation and authenticated private-data target. `PrivateSessionRuntime` now implements this bounded composition and adds an exact durable activation binding. The approved identity provider, platform root/UI and full application lifecycle remain pending; use its mandatory verifier/domain policy, not synthetic success ports.

Admission checks verified ownership and independent control, allowing only idle/completed state. Every gate must recognize ordinary logout, setup-discard and distinct `PendingCreate`, not only one retirement subtype; no ordinary cleanup fallback may consume a CREATE plan. Execution additionally checks current domain eligibility, generation and any locally known safety/recall restrictions. A persisted ACTIVE work record alone is insufficient: the independent coordinator can already be PENDING when a process dies before writing RETIRING into this separate ledger. No callback may bypass that control record.

The subsequent [planned private-data selection primitive](PLANNED_STATE_ACTIVATION.md) does not change this work lifecycle. It returns selection-only `Unit`, not a lease, private handle, retirement target or durable setup-journal resolution. The separate [planned state recovery](PLANNED_STATE_RECOVERY.md) component is implemented with full/native verification pending (b.2b.2 IN_PROGRESS). It exposes only inspect/abort/close; every empty-only abort commits a changed V2 receipt and consumed generation before exact key deletion, including ABORTED retries. Historical same/foreign-owner receipt references forbid candidate-key reuse. This protocol cannot cancel a native ticket or stand in for work retirement.

The API27+ existing-only data opener rejects V1, existing journals and unknown children, creates nothing and runs no GC. Normal shared-engine opening alone can atomically migrate exact V1 to V2 and retains ordinary cleanup. Returned-handle close retries; failed construction plus failed cleanup close remains a process-restart gate. The runtime still uses unplanned data/work creation; work-origin planning and a composite journal (b.2b.3) remain TODO. A no-op selected replay adds no fresh sync; the earlier AFTER-COMMIT test loses an application receipt after successful DELETE/EXTRA COMMIT. Native syscall-failure verification is pending and physical power-loss evidence remains separate, without implying a universal extra-fsync requirement or a descriptor redesign.

Expired credentials, a generic 401 or unavailable refresh are not implicit logout. Keep explicitly permitted, verified offline pinned cooking available according to F53; never auto-link identities or rebind an existing command origin. Actual logout/account switch does invalidate the old lease and block old private effects. Token revocation and server authorization remain separate work.

## Scheduling and cancellation behavior

| Event | Durable action | Native action / result |
| --- | --- | --- |
| Start a timer/worker | Persist domain desired state first; reserve a fresh exact ticket as RESERVED | Trusted installer receives only that ticket; callbacks remain denied until final INSTALLED commit |
| Installer succeeds | Exact CAS to INSTALLED, then recheck lease/process fences | Return the ticket; no detached or reentrant installer work permitted |
| Installer fails or identity loses eligibility | Preserve exact evidence and checkpoint CANCELLING where possible | Attempt cancellation of that one ticket; failure remains retryable |
| Installer coroutine is cancelled | RESERVED evidence remains | No automatic replacement identity; `reconcilePending` or retirement cancels the original ticket |
| Final install receipt is invalid or unresolved | Fence the ticket; read exact durable state and checkpoint/remove through compensation when possible | Attempt exact cancellation under non-cancellable cleanup; do not report successful installation |
| CAS acknowledgment is OUTCOME_UNKNOWN | Accept only read-back with a strictly newer revision and byte-identical intended payload | Otherwise remain OUTCOME_UNKNOWN; never invent a new task/key to hide ambiguity |
| Pause/cancel/replace | Domain first records its desired generation; registry fences the exact ticket and checkpoints CANCELLING | Exact cancellation acknowledgment allows entry removal; replacing later uses a new ticket |
| Restart with RESERVED/CANCELLING | Reopen without reinitialization; `reconcilePending` enumerates incomplete entries | Cancel exact tickets; never implicitly reschedule them |
| Logout/account retirement | Install process origin fence before first I/O/mutex wait, then persist RETIRING | Try every exact entry independently; retain failed entries and retry; commit idle only when all are removed |
| Old retirement after newer login | Persisted exact scope/origin does not match | No OS cancellation and no mutation of the newer origin |

`runLocalEffect` treats an OS ticket as an untrusted lookup, not an authorization capability. Native code can reconstruct its strict UUID/kind using `NativeWorkTicket.fromNativeIdentity`. The gate captures the exact current lease before its first read/wait, verifies the durable matching INSTALLED entry and mandatory policy, then rechecks that same lease and all process fences. Only a short synchronous local effect may follow; there is no suspension between the final checks and effect. The block must not dispatch detached work. Remote requests need additional transport/commit fences and exact domain idempotency; this registry cannot undo a mutation already accepted by a server.

Successful cancellation is an acknowledged native command, not proof an executing callback has stopped. Repeated permitted callbacks are not automatically exactly-once; notification identity and domain deduplication must make the intended effect safe. If the CANCELLING checkpoint fails before commit, an INSTALLED record can remain with only a process fence: retry exact cancel or retirement. `reconcilePending` does not scan installed entries. Restart safety in that case requires the independently persisted domain desired state and execution policy.

## Android exact identities

The Android adapter accepts an explicit same-application, non-exported receiver and an explicitly initialized WorkManager. It does not create a production receiver or domain worker. Every timer PendingIntent has a fixed explicit component, package/action, request code 0, immutable flag and `feedme-native://timer/<opaque-uuid>` data. No account, food, timer label, credential or command body appears in the Intent. Each identity call returns a fresh defensive Intent.

Cancellation uses `FLAG_NO_CREATE` with the exact matching identity, then `AlarmManager.cancel`, `PendingIntent.cancel`, and exact notification tag/ID cancellation, including when the alarm token is already absent. Never use `cancelAll`, app-wide tags or account-name matching. Extras are not a distinct PendingIntent identity. [Android PendingIntent reference](https://developer.android.com/reference/android/app/PendingIntent).

Worker cancellation uses the ticket UUID with `cancelWorkById` and awaits its operation, bounded to 15 seconds; timeout is OUTCOME_UNKNOWN and caller cancellation propagates. WorkManager may cancel dependent requests too, so requests must be independent or have only same-origin dependent work. Cross-origin chains are forbidden. Cancellation does not guarantee an in-flight worker has stopped. [WorkManager reference](https://developer.android.com/reference/androidx/work/WorkManager).

The worker installer must use the supplied ticket UUID as the actual `WorkRequest.id`, not just a tag or input field: cancellation of a nonexistent UUID can also acknowledge success. The original cancellation tests derive tickets from real request IDs; the subsequent four native integration tests use registry-supplied UUIDs as actual WorkRequest IDs. This proves that bounded identity wiring, not production scheduling. Timer receiver/action/package/request-code/data/notification mappings must stay identical across process restarts and app upgrades while tickets exist. The ledger stores UUID/kind, not a versioned receiver component. Renaming that receiver requires an explicit migration that can still cancel the old locator; silently switching components is not safe cleanup.

The adapter uses stable WorkManager 2.11.2, not the newer release candidate. This does not turn WorkManager into an exact timer scheduler. [AndroidX Work releases](https://developer.android.com/jetpack/androidx/releases/work).

## Feature boundaries and remaining tests

F12 remains responsible for persisted end time/duration/remaining time, multiple timers, pause/resume, foreground monotonic countdown and honest best-effort background alerts. Native scheduling comes after persistence. No alarm automatically advances a cooking step or claims that food is safe/ready. Reboot, clock changes, permission denial, Doze, killed process, device lock and known-recall behavior need real domain tests. The canonical timer status remains `running`, `paused` or `done`; this local work phase must not invent a `cancelled` API status.

F41 retains generic lock-screen previews and explicit permission UX. Denied notification permission or disabling alerts must preserve timer/session progress; neither triggers origin retirement. This component is not push-token registration, server token eligibility, quiet hours, delivery preferences or remote revocation. Full notifications and guided-cooking UI are still unfinished.

Remaining hard gates: verified application identity/startup composition, first-retirement-barrier failures, interrupted initial setup and user-visible repair, iOS work storage/cancellation, actual native receiver/worker policy, physical devices, hard-kill-in-transaction/power loss, independent OS callbacks after process restart, cross-process contention, backup/restore/migration, API26 credential compatibility and patched bundled-SQLite review. If every first durable barrier write fails and the process dies, a process-only fence cannot survive. No universal crash/logout guarantee is claimed.
