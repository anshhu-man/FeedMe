# F13 — Reviewed Recipe Library

Phase: first release; catalog expands through later packs. Owner module: catalog.

## Strategy

Provide the dependable content foundation for every automated recommendation and adaptation. Begin with a bounded library of recipes, additions, compatibility rules and substitutions reviewed for the intended everyday-eating use. Qualified nutrition review is a launch gate inherited from the concept; review does not establish medical suitability for every individual.

## Experience and screen design

RECIPE shows a clear content source, version-appropriate ingredient list, steps, equipment, estimates and save/cook actions. A compact provenance label distinguishes app-reviewed content from a creator's unreviewed report. RECOMMENDATIONS only claims supported matching for eligible reviewed versions. PACK_DETAIL later previews reviewed pack contents and ownership, while ADMIN_RECIPE, ADMIN_REVIEW and ADMIN_SUBSTITUTION are F51's editorial surfaces. Users encountering recalled content see UNAVAILABLE with the reason category and an alternative path rather than a blank screen.

## Production sequence

1. Draft recipes with canonical ingredients, component mapping, quantities, serving bounds, operation tags, step dependencies and effort.
2. Review nutrition language, preparation, substitutions and compatibility through role-separated editorial workflow.
3. Publish an immutable version and manifest in a database transaction with catalog_published outbox event.
4. Index only published eligible versions for matching. Pin chosen versions in plans, sessions and saves.
5. For corrections publish a new version; for safety/legal issues recall affected versions and propagate invalidation to plans, packs, caches and saved copies.

## Data and API contracts

GET /v1/recipes supports bounded catalog browsing with cursor and filters. GET /v1/recipes/{recipeId}/versions/{recipeVersionId} returns an authorized immutable bundle plus status. Bundles contain recipeId, recipeVersionId, contentKind, ingredientRequirements, steps with stable IDs, effort, sensoryTags, reviewStatus, reviewedAt, substitutionVersionIds, locale and contentHash. Catalog publication/recall changes use F51 admin operations and outbox, not client writes. A substitution edge is separately versioned but may only reference reviewed compatible content. Private/paid recipe access is authorized independently from knowing a recipe ID.

Recipe reviewStatus distinguishes draft, inReview, approved, published, retired and recalled; personal identifies unreviewed community content. Retired stops new matching while preserving existing authorized use, whereas recalled blocks cooking and can invalidate saved copies. An audited publication/supersession or catalog lifecycle operation changes retirement state; an ordinary client cannot set reviewStatus directly. This distinction honors immutable saves without retaining content that has been recalled.

## Permissions and lifecycle

Ordinary users cannot edit or self-certify catalog versions. Editorial authorization and audit are enforced server-side. Content downloads carry access scope and recall metadata; public cache keys must never include private saved recipes. Basic free help remains useful. Paid pack access follows server entitlement checks and explicit durable rights; content provenance never implies ownership of someone's photo or personal story.

## Failure and offline behavior

Download bundles atomically and verify contentHash before marking ready. An incomplete bundle is not cookable offline. Cached authorized content remains readable under its grant; recall awareness is bounded by last synchronization and enforced immediately when learned. Show last content check in relevant unavailable/offline details without cluttering normal cooking. If the catalog index lags publication, serve the authoritative version and retry indexing; never fabricate missing content with language generation.

## Integration and dependencies

All F01–F12 matching and cooking require this contract. F19/F30 saves use immutable content rights, F46 groups reviewed versions into packs, and F51 manages content/audit. Safety operations control recalls; platform outbox workers distribute changes.

## Execution plan

- Create immutable version/ingredient/step/substitution schemas and publish validators.
- Implement read authorization, cursor pagination and atomic mobile bundle caching.
- Add publication/retirement/recall propagation and dependency traversal.
- Build provenance/unavailable states and emit catalog_version_unavailable, recall_propagation_lag and bundle_integrity_failed.

## Acceptance and release gates

Require reviewer signoff and complete launch metadata before enabling matching. Test recalled substitute dependencies, retired saved content, unauthorized pack IDs, mixed-version bundles and index lag. Prove no unreviewed draft enters recommendation fixtures. Roll back a faulty release by selecting the previous eligible index and retiring affected versions; use recall, not ordinary rollback, when continued use must stop.
