## Exact existing contract

Use the current [API JSON](../../outputs/biteclub_blueprint/architecture/04_API_Contract.json), [F31](../../outputs/biteclub_blueprint/features/F31.md), and [approved publication review](POST_PUBLICATION_CONTRACT_REVIEW.md). | Item | Required behavior |
| --- | --- |
| Operation | `publishPost`, `POST /v1/posts`, actual ACCOUNT bearer and registered `X-Device-Session`. |
| Command identity | Original `Idempotency-Key`; **no If-Match**. The saved review version belongs in the request body. |
| Required PostWrite fields | `caption`, `mediaIds`, `audience`, `keepOnPlate`, `allowRecipeSaves`, `saveDisclosureVersion`, `clientDraftId`. |
| Optional PostWrite fields | `attachment`, `sourcePostId`, `draftId`, `draftVersion`, `altText`. Optional absence, explicit empty values and array order remain meaningful. |
| Success | Actual `201 Post` plus ETag. Validate the complete canonical Post; retain author, exact versions, timestamps, status, media, audience, savePolicy, aclVersion, capabilities and reactionCounts. |
| Server-derived facts | Audience membership bindings, Post identity, profile, timestamps, capabilities, ACL/save-policy versions and verified attachment material come from current authority. Client strings or a preview are not grants. |

Post does **not** echo clientDraftId/draftId/draftVersion. Bind its returned Post ID to the original local command through the actual operation-bound receipt and original request; do not require or manufacture absent response fields. Preserve raw original request bytes and exact integer/ETag representations without floating-point conversion. JSONB object-key serialization order is not a response identity; response optional presence, values and original ETag still must match.

### Preserve all four publication cases

| Request/current server root | Client and service behavior |
| --- | --- |
| Both draftId and draftVersion | Review the exact owned, live editable server draft and its same clientDraftId. Send its exact version and reviewed material. The server independently rechecks version, generation, authority and matching choices. |
| Neither; no server draft/prior publication exists | Review the complete local snapshot and submit it directly. Do not create a server PostDraft merely to support publishing. An owned upload root is not a server draft. |
| Neither; server draft already exists | Respect the service conflict. Obtain and deliberately review the actual owned server draft; never infer/adopt its latest version or retry with a replacement key. A partial/empty list page does not prove root absence. |
| Exactly one of draftId/draftVersion | Reject locally as invalid and retain the server's canonical semantic 422 defense. Never infer the missing half. |

A client that has never observed a server association may attempt the direct branch only for its explicit original local intent; it cannot certify global absence. A server conflict or unknown result must not cause automatic branch switching. Published/discarded/expired server roots and previously published direct roots cannot be recycled into another publication. Starting a genuinely new moment requires a deliberate fresh clientDraftId.

## Save, Review and Publish are separate actions

1. **Keep locally / Save privately:** retain current text or perform the existing explicit PostDraft mutation. Neither selects an audience for publication nor publishes. Back, rendering, restore, reconnect and processing completion remain non-submitting actions.
2. **Review publication choices:** show the exact caption/alt text, ordered photos, attachment/source, selected audience, independent Keep on Plate choice, recipe-save permission and the actual disclosure associated with its version. This produces a process/owner-bound review ticket, not a queued publication or reusable permission token.
3. **Save reviewed changes, when necessary:** an existing text-only server draft normally has no saveDisclosureVersion. Its current controller only patches caption/altText. Add an explicit, separately confirmed reviewed-content mutation using the existing `updatePostDraft` and original If-Match; obtain its acknowledged canonical response. Then present that actual resulting draft/version for final publication review. Do not quietly amend the server draft inside Publish, infer disclosure from a default, or pretend the old version was reviewed.
4. **Publish this reviewed moment:** consume only the current exact review ticket, persist the immutable original PostWrite and command ID, then explicitly dispatch that command. A second tap cannot allocate another command. A review/selection change before dispatch fences the ticket; a change after dispatch cannot rewrite the attempted original.

The disclosure text/version must be supplied by an explicitly configured, authoritative product-policy integration and accepted by the actual backend authority. The API does not currently define a new disclosure-fetch operation for this feature; do not invent one. Test values such as `save-policy-v1` are not approved production defaults. If the required disclosure/policy or source/audience/media integration is unavailable, show a truthful gate while private drafting remains available.

The reviewed server-draft comparison includes caption, altText, ordered mediaIds, audience choices, keepOnPlate, attachment, allowRecipeSaves, saveDisclosureVersion and sourcePostId. Preserve fields the editor does not own. Ignore client Audience.bindings as authority; the server stamps current generations. Omitted/empty/present altText must remain distinct, as established by the retained-draft receipt and GET-correlation regressions.

### Reviewed-content PATCH: preserve the text-v1 boundary

The current [draft codec](../shared/mealflow/src/commonMain/kotlin/com/feedme/mealflow/social/PostDraftRecords.kt) accepts only caption/optional-altText update originals. The [draft adapter](../shared/mealflow/src/commonMain/kotlin/com/feedme/mealflow/social/PostDraftAdapter.kt) correspondingly compares request keys with echoed response fields. Do not merely widen those allowlists: reviewed-content changes need a versioned, explicitly discriminated original-command representation, not broader authority for a restored text command.

1. **Add the reviewed-content variant and migration tests.** Keep schema-v1 text originals readable under their existing rules. Preserve their exact original body bytes, operation/key, path/If-Match, baseline, creation time and pending/apply evidence across upgrade and retry; never turn them into reviewed consent. A new variant pins the complete baseline, exact explicit PATCH, resulting-choice expectation and live review identity. Reject unknown versions/discriminators and invalid variant/field combinations before ID allocation. Prove v1 unknown-result retry after upgrade is byte-identical, v1 cannot carry reviewed-only fields, and a failed migration leaves the original recoverable.
2. **Implement response transformation, not universal echo comparison.** The existing [server PATCH transformation](../server/src/main/kotlin/com/feedme/server/social/drafts/PostDraftStore.kt) consumes `removeAttachment`; the flag is not a PostDraft response field. `true` requires attachment absence in the resulting document, while false/omission does not itself remove the baseline attachment. Reject attachment plus `removeAttachment: true`; do not manufacture `attachment: null` or erase unrelated source/disclosure fields. Correlate the canonical response with the transformed baseline, exact successor version/ETag, permitted server-managed changes and unchanged unrelated fields. Test true/false/omitted flag, attachment replacement, conflicting inputs, absent-versus-empty optional text, ordered media, unchanged source/disclosure, large exact version increments, and rejection of an echoed flag or retained attachment after removal. Matching GET correlation uses the same transformation but remains non-acknowledging.

## Specific production seams to implement

Names below are proposed new code, not existing callable APIs. Agree the additive signatures before different owners modify the shared files.

### One purpose-fixed publication borrower

- Add `PostPublicationCommandHooks` in shared/kitchen with the existing hook pattern: exact `executionDecision(lease, intent)` and `observeReply(lease, intent, reply)`, for **publishPost only**. Its optional composition input defaults to NOT_CONFIGURED. It grants no upload, post-edit/delete, privacy, circle or sibling command capability.
- Extend the existing MealKitchenComposition/bundle with a publication feature over the **same** actual access, fenced store/transport and command journal. Keep the old factories behavior-compatible. No second DurableCommandQueue, raw-store escape, accepting fallback or separate native session is allowed.
- The hook requires the exact active borrower/coroutine operation, ACCOUNT lease, scope/store/origin, review generation, persisted original command and local record revision. Do not recursively acquire the controller/composition mutex from a queue callback. Existing cooking/cookbook/draft gates and timer composition identity remain unchanged.
- [CommandPolicy](../shared/sync/src/commonMain/kotlin/com/feedme/sync/CommandPolicy.kt) already treats publishPost as a fresh-confirmation mutation in the social lane. Use explicit original-ID dispatch. Do not add it to automatic resumption, drain sibling work or bypass social FIFO. Preserve existing attempt/backoff/replay policy rather than selecting new production limits here.

### Immutable publication owner and draft handoff

Add proposed `PostPublicationController`, `PostPublicationModels`, `PostPublicationRecords` and a strict receipt adapter under shared/mealflow/social. They borrow the actual session; construction and restore perform no submission. Suggested bounded public actions are open review, dismiss review, confirm reviewed publication, inspect pending status, retry original, discard a proven zero-attempt command, Back and close. Do not expose arbitrary `execute(ApiCall)` or a Boolean “force publish.”

Retain these facts separately:

- Exact local client ID/revision and, where applicable, the complete reviewed server document/ID/version/ETag.
- Complete immutable PostWrite, original command ID, original creation time, scope/origin and branch presence. Never reconstruct a retry from currently visible controls.
- Opaque live review/confirmation proof, tied to this lease/owner/generation and the exact chosen fields. Restored bytes are historical, not recreated user consent.
- Pending transport/receipt/application/finalization state and the actual returned Post association. A cached Post or GET result is not a mutation ACK.
- Any newer unsubmitted edits and a durable published-root marker. Terminal client IDs must not be reused after receipt expiry, local discard or restart.

The existing PostDraftController owns its versioned draft record. A separate publication controller must not independently write that private namespace. Add a **narrow internal composer coordinator**, constructed once in the shared bundle, to pin an exact review snapshot and prepare the affected draft/terminal mutation under the same operation ownership. It must fence concurrent edit/save/discard/publication on the same root without disabling unrelated cooking work. The draft owner remains the only interpreter of its schema; publication does not forge a canonical PostDraft from a Post response.

Publication success needs a deliberately versioned local terminal/association representation that distinguishes publication from server discard. Existing draft completion records admit only draft operations; do not insert publishPost into them by accident or silently reinterpret their tombstones. Preserve older records and unresolved originals during any codec migration. Atomically apply the actual publication receipt, original queue archive, publication association/terminal evidence and the coordinator's exact affected draft mutations.

If typing races with an attempted publication, retain the original and newer text separately. An acknowledged publication closes the original root; it cannot make the newer text server-published or silently save it under that used identity. Offer an explicit action to retain newer work under a fresh draft identity after resolution. Do not silently drop it, replace the pending key or auto-create a second Post.

### Receipt, cancellation and original recovery

- Preflight local byte/capacity/schema limits before allocating an ID or making irreversible calls. Policy inputs are required and bounded; no production quotas are selected in this document. Use existing WireDocument, MobileRequestValidator and CanonicalResponseBinder.
- Atomically enqueue original request/domain intent before transport. Read-only review/list/get and READY observations cannot acknowledge, archive or clear that intent.
- Validate actual publishPost/201/content-type/schema/ETag and requested choices against the original before preparing application mutations. Preserve the full canonical returned Post, including server-derived fields; never manufacture author/capabilities/savePolicy/empty reaction evidence to satisfy the schema.
- Capture the actual prepared archive/domain batch through the publication borrower's beforeCommit proof. Apply through the real shared queue and require exact changed-CAS acknowledgement/readback. Do not equate HTTP success, APPLIED state or a matching GET with successful local delivery.
- A lost local apply ACK uses the actual same-lease archive/domain proof and another fresh acknowledged CAS, as in the retained draft foundation. Missing/mutated proof or reconstructed process state remains historical reconciliation; no synthetic receipt or new consent is created.
- Unknown dispatch, timeout or caller cancellation preserves the same original key/body/branch. Explicit retry rechecks current prerequisites and uses the original command. A later denial, changed draft, expired receipt or changed Post is not evidence the original never committed, and must not cause automatic rebase/branch switching.
- Fences apply before/after every storage, transport and dispatcher return, including the final StateFlow/caller-return ticket. Back/close/lease invalidation prevents late visible success and dispatch where still preventable; it does not cancel a committed server effect. Close never closes or retires the borrowed native session.
- A successful publication may leave review for a receipt view only if that exact review is still selected. Reconciliation from another route must not navigate backward or steal selection. Reuse the principle just reviewed for acknowledged draft DELETE/local finalization; navigation never supplies an ACK.

**Implement separate new-publication and attempted-original replay admission.** An editable, unused root and eligible unattached selections are requirements for a new publication, not unconditional requirements for recovering its already-attempted original. A committed saved-branch publication makes the server draft published at the successor version; either branch closes the stable root and attaches its selected media. Requiring that root to remain editable/unpublished or those media to remain unattached would block the recovery the service supports. Keep the exact attempted key/body/branch and queue age/backoff; permit only its original replay path under current account/device and replay-disclosure checks. A terminal observation is neither an ACK nor permission for a new key, branch switch, second Post or reconstructed local proof. The [current replay transaction](../server/src/main/kotlin/com/feedme/server/social/posts/PostPublicationStore.kt) independently checks original lineage, unchanged published material and current authority; a denied/expired original remains unresolved rather than being replaced.

Add paired direct-local and saved-draft tests: server commits but response is lost, the root/selected media are now terminal/attached, and explicit exact-key replay yields one Post/event only. Also prove fresh publication on that root is denied, later changed/deleted material or revoked replay authority does not trigger replacement, and an already-applied unknown local ACK uses exact local finalization rather than a new publication request.

## Photos, audience and recipes remain required V1 work

The first deterministic client gate may use an explicitly configured self-audience/text case, but the record, review and protocol must retain the complete canonical choices and both branches. No full composer acceptance follows until these required integrations are proved:

- **Photos:** native selection/permission and retained upload ownership must be scoped to the exact client root. Use the existing prepare/complete/status/cleanup media protocol and actual processing evidence. Media upload and signed-capability operations are separate workflows excluded from the generic mutation journal; do not add them to a publication hook. No automatic upload or Publish occurs on permission grant, selection, reconnect or processing completion. Absent provider/permission remains explicit; no sample image or READY fixture enters production.
- **Selection changes/cleanup:** keep media IDs in reviewed order and reject foreign/wrong-root/terminal/conflicting selections. Pending/rejected metadata that can exist in an editable server draft is not publish-ready. The server rechecks actual immutable derivatives and current safety deadlines. Publication already separates selected attachment from unused-upload cleanup; observing that cleanup does not prove physical object erasure or settlement of late authorized writes.
- **Audience and retention:** use actual circle choices/current membership integration and explicit selection. Keep self available where configured, without silently widening to circles. Keep on Plate is independent of the 24-hour Today lifetime. Future privacy defaults are not edits to this particular Post. Client membership labels/bindings never grant server access.
- **Recipe attachment and saves:** require exactly one actually eligible recipeVersionId/planId/personalRecipe source and exact confirmed changes/provenance. A private cookbook copy, cooking pin or user-provided rightsBasis/reviewStatus is not redistribution authority. Required source/recall/rights policy remains server-authoritative; unavailable source discovery or review must gate that capability, not invent a capability endpoint. Preserve the actual disclosure and explicit save permission; no attachment means no fabricated recipe-save grant.

**Explicit missing owner:** the shared client currently has no retained photo-selection/upload owner. Existing server MediaStore/routes and canonical operations do not implement that mobile workflow. Assign it as a separate bounded task before full composer acceptance: define a default-closed owner over the borrowed session and exact client-root generation, connect native selection/permission and actual signed-upload transfer to `prepareMediaUpload`, `completeMediaUpload`, `getMediaStatus` and `deleteDraftMedia`, and expose only verified ordered selection/readiness evidence to the review coordinator. Keep upload capabilities and provider transfer out of the generic mutation journal and publication borrower. Test permission denial, wrong root/lease, selection changes during transfer/processing, unknown completion, rejected/expired processing, late replies after invalidation, and selected-versus-unused cleanup. Provider-independent synthetic tests must be labelled; actual provider/native-byte evidence remains required and does not justify choosing an unapproved production provider.

These requirements preserve FeedMe's low-pressure healthy cooking/social concept, including the later connected Make Mine journey. They are not new feature cuts or a switch back to TasteEcho. Today/My Plate placement reads, protected media delivery, post editing/erasure, block/report/privacy controls and other included features continue through the [social client plan](SOCIAL_CLIENT_INTEGRATION_PLAN.md) and [release scope](V1_RELEASE_SCOPE.md). Do not synthesize a feed entry, signed URL or notification from the publication receipt.
