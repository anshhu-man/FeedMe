# F35 — Bring a Bit

## Strategy
Bring a Bit turns voluntarily contributed ingredients into a shared meal and a clear division of tasks. People choose what to bring, the group gets a reviewed recipe that fits the confirmed contributions, and claims prevent duplicate responsibility. This later feature includes withdrawal, replanning, schedule changes, and cancellation. It does not collect money or place purchases.

## Experience and screen design
`POTLUCK_CREATE` collects a title, date/time, selected circle, and optional location. Invitees preview basic details and explicitly join before seeing participant-only location and contributions. `CONTRIBUTION` records a selected canonical ingredient, quantity, and unit. `POTLUCK_DETAIL` shows the pooled ingredients, unavailable amounts, suggested meals, and who has claimed a contribution to bring or prepare. “Find a meal we can make” presents reviewed matches; the host confirms one. Contribution changes mark that plan as needing review. Members can release a claim, mark it brought, or withdraw their own offer.

## Production sequence
`POST /v1/potlucks` creates the event and invitations; `POST /v1/potlucks/{potluckId}/participation` records an explicit response. `POST /v1/potlucks/{potluckId}/contributions` commits an ingredient offer and increments `contributionRevision`. `POST /v1/potlucks/{potluckId}/plan` authorizes the group, snapshots confirmed contributions and deliberately shared constraints, and returns reviewed candidates. `POST /v1/potlucks/{potluckId}/confirm` locks the event and checks `acknowledgedContributionVersion` before storing the selected recipe. `POST /v1/potlucks/{potluckId}/contributions/{contributionId}/claim` atomically claims, releases, or marks brought; the collection-level `/claims` command invokes that same service with an explicit contribution ID. Each mutation writes its domain event to the transactional outbox before the UI shows success.

## Data and API contracts
`Potluck(id,hostId,circleId,scheduledAt,timeZone,locationText,contributionRevision,selectedRecipeVersionId,confirmedContributionRevision,state,version)` owns event state. `Contribution(id,potluckId,ingredientId,quantity,unit,volunteeredBy,claimedBy,status,version)` permits one active claimant and a positive quantity with compatible units. No silent splitting or unit conversion is allowed. `GET /v1/potlucks/{potluckId}` and its `/contributions` read authorize accepted participants. `PATCH /v1/potlucks/{potluckId}` changes host details; `DELETE /v1/potlucks/{potluckId}` cancels. `DELETE /v1/potlucks/{potluckId}/contributions/{contributionId}` withdraws an owned offer. Errors include `ALREADY_CLAIMED`, `CLAIM_CONFLICT`, `PLAN_STALE`, and `VERSION_CONFLICT`. Durable commands require idempotency keys.

## Permissions and lifecycle
Current unblocked circle members may accept an invitation; only accepted participants view contributions, plan, or claim. Only the host confirms or changes the gathering. Exact location is excluded from push payloads and analytics. Withdrawing a claimed contribution first presents the conflict and requires explicit acknowledgement; commit releases the claim and invalidates the selected meal. Significant time/location changes require reconfirmation. Circle departure releases claims and removes access without disclosing the privacy reason. Cancelled events retain eligible participant receipts for a proposed 30 days. Private dietary settings are not pooled unless separately and explicitly shared for this meal.

## Failure and offline behavior
Offline contributions are drafts, not confirmed inventory or reservations. Idempotency prevents duplicate offers and claims after timeout. A claim conflict returns the current authorized state. Confirmation racing an ingredient withdrawal fails with `PLAN_STALE`; it cannot certify missing ingredients. Cancellation and claims are serialized, and cancelled events reject uncommitted changes. Location and recipe selection require fresh reads. A failed group match preserves contributions and explains missing quantities without guessing or relaxing exclusions.

## Integration and dependencies
F23 circles, F24 recipe eligibility, F40 audience checks, F41 reminder preferences, and F42 blocking/reporting. Shared food notes are voluntary; private medical or dietary preferences are never copied into contributions. Personal recipe copies remain separately governed by F30.

## Execution plan
Implement contribution revisions and single-claim locking; build invitation and contribution forms; integrate deterministic pooled-ingredient matching and version-bound confirmation; then add withdrawal, reconfirmation, cancellation, and reminders. Observe claim conflicts, stale confirmations, and match failures without recording locations or private exclusions.

## Acceptance and release gates
Test two claims for one contribution, claimed-offer withdrawal, incompatible units, stale quantities, concurrent confirmation, event changes, circle loss, and cancellation retries. `coordination.potlucks.enabled` stops creation, new claims, and group planning while preserving withdrawal and cancellation. Release requires deterministic ingredient accounting, explicit recipient previews, and no automatic purchasing action.
