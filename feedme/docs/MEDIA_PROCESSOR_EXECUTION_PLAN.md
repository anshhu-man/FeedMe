# Media processor: next executable package

Status: implementation plan, not a worker, moderation, provider or deployment acceptance receipt. The current media source is under central verification. This document does not change that source or claim its tests have passed. It narrows the next package to processing an already-committed owned photo upload; no delivery URL, post, avatar, clip or automatic publication is added.

## Starting invariants

[MediaStore](../server/src/main/kotlin/com/feedme/server/media/MediaStore.kt) currently verifies an immutable object's metadata outside the database transaction, then re-locks current authority and commits `processing`, the original completion acknowledgement, and `platform.media.upload_completed.v1` together. [V007](../server/src/main/resources/db/migration/V007__owned_photo_media.sql) pins the reservation, object version, completion key/version/time and permitted transitions. It does not fetch or decode image bytes, scan, moderate or create derivatives. Its synthetic READY tests demonstrate SQL lifecycle behavior only.

The canonical [media sequence](../../outputs/biteclub_blueprint/architecture/02_Architecture.md), [F31 Share Composer](../../outputs/biteclub_blueprint/features/F31.md) and [event registry](../../outputs/biteclub_blueprint/architecture/05_Events.md) require independent byte/type/dimension validation, location-metadata removal, scanning, moderation and re-encoding before readiness. An event is a committed fact, not continuing authorization. [F48](../../outputs/biteclub_blueprint/features/F48.md) reuses sanitized media for a distinct avatar purpose; this photo package must not silently enable that purpose or block name-only onboarding.

Retain these public contracts without new routes or fields:

| Fact | Producer / aggregate | Exact required event data |
|---|---|---|
| `platform.media.upload_completed.v1` | `platform` / `media`, accepted version | `mediaId`, `quarantineVersionId`, `checksum` |
| `platform.media.ready.v1` | `platform` / `media`, newly committed version | `mediaId`, `derivativeSetVersion` |
| `platform.media.rejected.v1` | `platform` / `media`, newly committed version | `mediaId`, `safeReasonCode` |

READY/REJECTED changes current GET state, not the original completion response. Preserve V007's accepted processing key, version and timestamp through every worker transition. Same-command completion retry can still acknowledge the original `processing` result after READY/REJECTED under its current authority/receipt rules. A rejection is never permission to serve the original; readiness is never consent to publish.

Use a new `server/media/processing` package. These are proposed internal names, not new canonical APIs. Append a reviewed `V008__media_processing_jobs.sql` and register it; preserve all V001–V007 bytes after their accepted checkpoint.

|---|---|---|
| 1. Durable ingestion and leases | `MediaProcessingModels.kt`, `MediaProcessingStore.kt`, V008 and migration tests | Real PostgreSQL inbox-to-job insertion, exact source pin, bounded claim/renew/finalize fencing and duplicate handling |
| 2. Real JPEG/PNG transformation | `BoundedPhotoDecoder.kt`, `PhotoContainerValidator.kt`, `PhotoDerivativeValidator.kt`, `PhotoDecodeProcess.kt` | Actual byte fixtures decode, orientation is applied, fresh derivatives are re-decoded and independently verified metadata-free within explicit limits |

Task 3 can be an executable configured coordinator with explicit synthetic provider/safety adapters in tests and real local byte processing. It must remain unavailable without actual mandatory adapters; adding an accepting production stub is not completion. Do not enable a loop in `Main` or change health-only default composition in this package.

## Database execution and authority

1. Accept only a trusted internal `CommittedEvent` for the exact type/schema/producer/aggregate above. Validate required UUID/hash/version fields, bounded envelope, causation and media identity; never accept a client-supplied bucket, key, owner or arbitrary event type. Resolve exactly one matching row in the configured environment using media ID, completion version/key, immutable version and checksum; reject ambiguous/missing/corrupt lineage rather than selecting an arbitrary row. The public event does not carry an owner or environment grant.
2. Follow the existing [ConsumerInbox](../server/src/main/kotlin/com/feedme/server/db/DurableEvents.kt) database-only transaction pattern: insert the inbox marker and a durable processing job in the same transaction. Pin environment, owner, draft ID/generation, media ID, accepted media version, completion key, quarantine key/version/hash/size/type and the processing-policy/codec revision. Store the normalized accepted event fingerprint in the owned job/event receipt. Unique event ingestion and unique media-completion lineage prevent two event IDs from producing two jobs for one completion. **The current `ConsumerInbox.consume` skips its callback for a duplicate and stores no payload fingerprint:** it cannot be the complete validation wrapper unchanged. The new ingestion transaction must always load and compare the owned receipt, including a duplicate inbox key, or use a reviewed narrow same-connection inbox seam. Changed-payload duplicates fail closed; do not silently treat them as equivalent events.
3. A job claim uses a short transaction, bounded `FOR UPDATE SKIP LOCKED`, a random lease token, monotonically increasing lease generation, database expiry, attempt count and next eligible time. Lease renewal and every stage/terminal write require the exact token/generation and unexpired database time. Reclaimed leases may redo computation, not invent a new media identity. Store retry reasons as bounded safe codes. Attempts exhaustion quarantines operational work; it is not a content-rejection or READY verdict.
4. Add mandatory `MediaProcessingAuthority` with a same-connection worker-purpose owner/draft check. Do not construct a fake `VerifiedMediaAccount` or reuse a revoked user device to impersonate an asynchronous worker. Client admission already required a real registered device; background processing independently checks current account status, original draft incarnation/eligibility, deletion and applicable safety policy. No accepting implementation is provided. Policy invalidation/account deletion writers must share its locks.
5. Use a consistent order for effect-finalization: current principal/policy root → exact draft lifecycle → media → processing job → derivative intents in deterministic order. A short lease claim may lock only the job and commit; it must release that lock before waiting for authority/media. Do not hold a job row while acquiring roots in reverse order. Never hold a SQL transaction during download, decoding, scanning, moderation or object writes.
6. Re-lock all those roots after external work. Check the original immutable pin, current `processing` state, lease, current policy/safety evidence and exact durable derivative receipts before changing state. Commit the new media version, manifest or safe rejection code, job terminal receipt and one registered outbox fact atomically. A deleted/stale job has no media effect and arranges cleanup for its own recorded writes. An unavailable authority adapter produces no effect, not an automatic content rejection.

The [existing outbox](../server/src/main/kotlin/com/feedme/server/db/DurableEvents.kt) is a delivery ledger, not the long-running processing lease. Do not keep an outbox lease across decoding or mark it delivered before durable inbox/job admission. `OutboxStore.claim` currently selects across all event types: a media-only loop must not drain it and quarantine unrelated events as unsupported. The eventual trusted dispatcher/broker must route all registered consumers, or a separately reviewed selector is needed. Local tests may deliver retained real outbox events directly to ingestion without claiming a production broker exists.

## Bounded byte processing using available JVM APIs

[server/build.gradle.kts](../server/build.gradle.kts) targets JVM 17 and declares no image codec, metadata-extractor or scanning dependency; the [version catalog](../gradle/libs.versions.toml) has none either. A read-only cache inventory found no existing third-party image codec dependency to reuse. Use the JDK `java.desktop` Image I/O APIs for a first JPEG/PNG implementation and verify the actual selected reader/writer availability at configured startup. Do not add a codec download or native tool as an implicit runtime fallback. Java documents pluggable reader/writer discovery; production must pin/test the approved implementation set rather than accepting arbitrary newly installed plugins. [JDK Image I/O](https://docs.oracle.com/en/java/javase/17/docs/api/java.desktop/javax/imageio/ImageIO.html)

Require explicit `PhotoProcessingPolicy`: source-byte cap no greater than the existing 10,000,000-byte ceiling; width, height, pixel count and decoded-memory limits; bounded segment/chunk/metadata counts and bytes; thumbnail/display dimensions; permitted color models/output formats; output and combined-response/manifest byte limits; codec/policy revision; process time, concurrency and temporary-storage limits. No numeric operational defaults are selected by this document. Only JPEG and PNG are admitted by the first configured decoder; **HEIC must be removed from that configuration's advertised supported types**, and any previously accepted HEIC job fails closed with a safe unsupported-format result. Never relabel HEIC as JPEG or claim deferred clips/avatars work.

The implementation sequence is deliberately stricter than calling `ImageIO.read` on a URL:

- Fetch only the exact pinned private object key/version through a mandatory bounded stream port. Hash actual bytes while enforcing expected length and the hard cap plus one-byte overflow detection. Independently compare SHA-256/type; object metadata or a suffix alone is insufficient. Do not follow arbitrary URLs or redirects from job data.
- Validate bounded container structure/signature and supported single-image form before full allocation. Reject truncated/contradictory JPEG segments, invalid PNG lengths/CRCs, unexpected trailing payload, animation/multiple-image forms and unsupported coding/color variants. Sniffed format must match the accepted content type. A legitimate unsupported encoding is a safe validation result, not permission to use a permissive alternate plugin.
- Select the approved reader, query dimensions before raster allocation, and use overflow-safe pixel/memory arithmetic. Explicit memory-backed streams avoid Image I/O's optional implicit disk cache; memory buffering still counts against the job's total budget. Dispose readers/writers, streams and graphics in `finally`; private temporary files, if deliberately needed, use an exact owned directory and are never shared-cache artifacts. [ImageReader API](https://docs.oracle.com/en/java/javase/17/docs/api/java.desktop/javax/imageio/ImageReader.html), [MemoryCacheImageInputStream](https://docs.oracle.com/en/java/javase/17/docs/api/java.desktop/javax/imageio/stream/MemoryCacheImageInputStream.html)
- Parse only the bounded EXIF/TIFF subset necessary for orientation, including both endiannesses and orientations 1–8; bounds-check every offset and reject malformed/ambiguous orientation. Do not follow arbitrary IFD chains or copy GPS, thumbnails, maker notes or XMP. Apply orientation to pixels, convert through an explicitly supported color path into a new RGB/ARGB raster, then scale without enlarging beyond policy. Unsupported ICC/CMYK handling fails closed until separately tested; silently changing colors is not a verified path.
- Encode each derivative from the fresh raster with no source metadata or source thumbnails supplied. Set an explicit writer/output profile; use a hard-capped output stream that fails during encoding, not only after a large buffer is allocated. Java's simple writer path uses default metadata, so passing `null` alone is **not** the privacy acceptance test. [ImageWriter API](https://docs.oracle.com/en/java/javase/17/docs/api/java.desktop/javax/imageio/ImageWriter.html)
- Re-parse and re-decode emitted bytes independently. Allowlist only the required structural JPEG markers/PNG chunks and explicitly approved non-identifying color metadata; reject EXIF, XMP, comments, PNG text/eXIf and unexpected application/private chunks. Verify dimensions, decodability, output hash/size, absence of appended data and the exact derivative variant set. Test actual embedded GPS, description, camera serial and thumbnail sentinels; a raw substring search is additional evidence, not a metadata parser. The fresh output must not contain a copied source object or private URI.

A pixel cap is not a CPU/RSS sandbox. `ImageReader.abort` is cooperative, not proof arbitrary decoding stops by a deadline. For untrusted production input, execute the bounded codec in an owned child process with an actual timeout, capped heap/concurrency/private input-output protocol and deployment-level resource/network restrictions. Local process-kill and malformed-image tests are implementable; OS isolation/host configuration must be separately verified. No in-process `withTimeout` claim substitutes for a terminated decoder process.

## Safety, derivative writes and acknowledgement

Introduce mandatory purpose-specific ports, not accepting defaults:

- `ImmutableMediaObjects`: exact versioned bounded read; immutable conditional creation for a server-generated derivative intent; lookup/reconciliation by that exact intent; exact version delete and bounded same-key version inventory. It never grants public access or accepts a bucket prefix from an event.
- `MediaSafetyAssessment`: real malware/content-policy evidence tied to original hash, derivative hashes, assessment/policy revision and any validity deadline. Separate `Approved`, safe `Rejected`, `Pending` and `Unavailable`; transient scanner/provider failures keep work non-ready. Scanner success is not moderation success, and deterministic decoding success is neither. Raw provider messages/evidence remain restricted; events and owner errors contain only approved safe codes.
- `MediaProcessingAuthority`: the current same-connection lifecycle check described above, including whether obtained evidence is still valid for the final commit.

Before each external derivative creation, persist a write intent containing the exact job/media lineage, variant, unique destination, codec revision, expected hash/bytes/type and state. Use destinations compatible with V007's existing `derivatives/<environment>/<mediaId>/<bounded-token>` shape. Two variants are `thumbnail` and `display`; the durable manifest remains `{version, variants:[{variant,key,objectVersionId}]}`. Rich dimensions/hash/provider receipts belong in internal tables, not unreviewed additions that break the existing exact manifest validator.

The adapter must create immutable objects conditionally and return an exact object-version receipt. If the response is lost, reconcile that same intent/key and verify its actual immutable bytes; do not overwrite or allocate a replacement destination. Pin expected encoded hashes before I/O, so a codec/JDK change cannot silently recreate different output under the same intent. If regeneration differs, fail closed and require an explicit new internal processing attempt with recorded cleanup for the old intent.

All bytes may be locally transformed while readiness remains gated. An executable coordinator may commit READY only after current approved safety evidence and acknowledged verified derivatives. Tests can supply an explicitly synthetic assessment to exercise this branch, but that proves coordination, not real moderation. Human review availability, policy decisions and provider configuration are release prerequisites; they do not prevent implementing the codec, durable jobs, negative verdicts and crash-recovery machinery locally.

## Deletion, rejection and exact cleanup

V007 delete already records the known quarantine version and ready derivative manifest in an immutable-hash-pinned `media_cleanup_jobs` row. Preserve that receipt: appending newly discovered orphan derivatives to its manifest would invalidate exact delete replay. Also, derivatives written before a worker commits READY are not yet in `media_assets.derivative_set`, so the existing delete snapshot alone cannot cover them.

V008 therefore needs a separate durable object-write/cleanup ledger keyed by each derivative intent, plus purpose-fixed quarantine cleanup tasks for processing success/rejection where appropriate. A narrow same-connection delete hook marks matching processing work cancelled/fenced; every unfinished write intent remains discoverable even if the worker dies before acknowledging its object. Cleanup may act only on its exact stored key/version/intent after verifying that it is not the live committed derivative; it cannot sweep an account or bucket prefix. Do not erase the only manifest or mark cleanup finished before acknowledgement.

Required race behavior:

- Delete before claim or before final commit: no READY/REJECTED resurrection, no ready event, exact pending outputs remain cleanup-owned.
- Delete after an object write but before its receipt: reconcile that same immutable intent, retain the late result and clean it even if the old worker lease is gone. Lease expiry is not proof an external request never succeeded.
- Unknown final SQL COMMIT: re-read the exact job terminal receipt and matching media/outbox result under current locks; do not re-emit a fact or start new object writes. An acknowledged old result may be terminal even when a later delete has advanced the asset.
- Quarantine POST after deletion: tombstones deny processing/publication immediately, but final cleanup cannot be complete before the original reservation deadline. Re-scan bounded versions of the exact key after that horizon, including late versions. Backend derivative writes also need a documented provider late-acceptance/reconciliation contract; unresolved in-flight writes cannot be declared absent merely because a request timed out.
- Rejection after valid immutable upload: commit a safe rejection and durable cleanup purpose together; never serve the rejected original. Preserve the completion acknowledgement and only the bounded evidence required by an approved retention/incident policy. No speculative permanent evidence retention.

## Required proof before calling the package implemented

Use real generated/checked-in non-personal JPEG/PNG binary fixtures, real JDK decoding/writing and real isolated PostgreSQL. Keep provider/authority/moderation fixtures visibly labelled. The first acceptance suite must cover:

1. Inbox duplicate and changed-lineage rejection; two claimers, lease expiry/renewal, stale token, exhausted attempt and unknown ingest/final COMMIT. No media-only claim of unrelated outbox events.
2. JPEG/PNG orientation 1–8, palette/alpha and explicitly supported color paths; real EXIF/GPS/XMP/comment/PNG-text removal; source thumbnails not copied; malformed headers/chunks/CRC, truncation, decompression/pixel bounds, unsupported HEIC/animation and output budget failures.
3. Exact immutable object digest/version mismatch; source key overwritten with another version; missing original version; bounded read interruption; actual decoder child timeout and private temporary-file cleanup.
4. One derivative write, lost response/reconciliation, mismatched existing bytes, changed codec, process death between each durable intent/write/receipt boundary and stale lease returning late. No capability or private metadata in errors/outbox/logs.
5. Mandatory safety unavailable/pending/rejected versus synthetic approved; expired/revoked evidence/current owner/draft policy change before finalization. Only the approved branch can write READY.
6. Real-PG deletion at every external boundary, retained pre-READY output intents, late quarantine versions, bounded cleanup retry and immutable delete receipt replay. READY/REJECTED events occur once with exact canonical data; terminal completion replay still returns its original processing receipt while GET returns current state.

A final configured object-store/provider integration must prove versioned reads, conditional immutable writes, late acceptance and deletion receipts against the chosen service. An actual safety/moderation integration and operational ownership must prove the separate readiness gate. Neither is selected or funded here. Publication/current circle visibility, signed derivative delivery, avatar attachment, reports/appeals and public deployment remain outside this worker package and cannot be inferred from its local tests.
