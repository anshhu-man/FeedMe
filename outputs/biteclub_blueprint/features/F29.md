# F29 — Ask for Recipe

## Strategy
Ask for Recipe replaces vague social requests with an explicit, optional invitation to attach useful cooking details. It does not obligate the author to answer or permit saving. Ship after private replies and recipe attachments, with a low-frequency request limit to prevent nagging.

## Experience and screen design
On an accessible `POST` without a usable recipe, the viewer opens `RECIPE_REQUEST`, sees “Ask privately,” and may add a short note before sending. A pending request shows its status instead of another send button. The author sees a card in `THREAD` with “Send recipe reference,” “Add recipe to my post,” and “Decline.” Decline uses neutral wording. Direct fulfillment shows an eligible recipe card, not an automatic copy grant. Adding the recipe to the source post opens `ATTACH_RECIPE`, `REVIEW_ATTACHMENT`, and `SAVE_PERMISSION` with a separate audience/policy preview.

## Production sequence
`POST /v1/recipe-requests` with `postId` creates a request after authorization, recipient-setting checks, and rate limits. It resolves the permitted direct thread and writes `recipe_request.created` atomically with the request message. `POST /v1/recipe-requests/{recipeRequestId}/response` uses `If-Match`, `decision=fulfill|decline`, and an eligible `recipeVersionId` when fulfilling. The transaction validates redistribution rights and current thread eligibility, stores the terminal response, and emits `recipe_request.resolved`. Its direct card carries participant-scoped viewing only. An author separately changes the source post through `PATCH /v1/posts/{postId}` if they want its audience to see an attachment or receive save permission.

## Data and API contracts
`RecipeRequestRecord(id,postId,requesterUserId,authorUserId,threadId,status,expiresAt,recipeVersionId,version)` tracks pending and terminal request state. Enforce one pending request per requester/post pair and a proposed seven-day expiry. Direct fulfillment references an immutable eligible version and must reject a private-copy-only source: ownership of a saved copy cannot authorize redistribution. It copies no photo, comment, or private preference. Existing source-post or catalog save rights are evaluated independently when Save is selected; fulfillment alone creates no copy grant. Errors include `REQUEST_ALREADY_PENDING`, `REQUEST_CLOSED`, and `RECIPIENT_UNAVAILABLE`.

## Permissions and lifecycle
Creation needs current source access and messaging eligibility. Only the requester can cancel via `DELETE /v1/recipe-requests/{recipeRequestId}`; only the author resolves. Blocks, contact-policy changes, and loss of shared-circle eligibility stop delivery and responses. Expired source media never reappears in the thread. Direct card viewing requires continuing participant eligibility; private copies require an independent current grant or eligible catalog right. Previously authorized copies persist under F30. Changing the source post’s attachment/audience is a separate explicit action.

## Failure and offline behavior
Keep unsent requests as local drafts, not optimistic delivered messages. Retry with the same key; repeated taps resolve to the existing pending request. Expiry racing an answer is serialized under a row lock using server time; a closed request returns its terminal status and preserves the author’s draft recipe. Do not send reminders automatically. Offline request cards show last-known state and revalidate before actions.

## Integration and dependencies
F24 attachments, F28 threads, F30 grants, F39 request preferences, F41 notifications, and F42 abuse handling. Moderation can inspect a reported request under the same evidence controls as private messages.

## Execution plan
Implement the request state machine and scoped response contracts, then requester and author screens, then expiry jobs and notification deduplication. Track resolution and rejection reason codes without message text.

## Acceptance and release gates
Test double answers, expiry boundaries, cancellation, direct-card versus source-post rights, disabled requests, grant-off fulfillment, and attempted redistribution of a private copy. `social.recipe_requests.enabled` stops new requests while allowing cancellation and draft recovery. Release requires an explicit author response, no automatic audience change, and no implicit recipe-copy grant.
