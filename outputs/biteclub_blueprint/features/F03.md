# F03 — Use What I Have

Phase: first release. Owner module: pantry.

## Strategy

Make rough ingredient availability useful without requiring inventory work. A person can start with three ingredients, an existing meal, or a few staples. Availability is a statement about what the user reports having; it is never evidence of freshness, safe storage or an exact usable quantity.

## Experience and screen design

PANTRY opens from REQUEST or ADAPT. It has ingredient search, chips for this meal, and a separate Usually have section. Each chip can be removed or marked Not available. Selecting a staple for a current recipe may prompt “Still have this?” only when it is essential and unconfirmed. A clear Continue action returns the selected snapshot to the originating screen. RECIPE and VARIANT list missing ingredients before Cook this. Users can choose a supported substitute, edit availability or voluntarily add the ingredient themselves; no shopping service is assumed. Equipment remains on EQUIPMENT rather than being mixed into pantry stock.

## Production sequence

1. Resolve typed ingredient names through catalog aliases; present ambiguous matches for user selection.
2. Store account-level rough items separately from the current meal's confirmed snapshot.
3. On planning, include confirmed IDs and uncertain staple IDs with distinct states.
4. Match ingredient requirements against the snapshot. Ask about uncertain essentials only after narrowing a candidate.
5. Mark a cooking session's ingredients as reported used without decrementing pantry stock automatically; exact amounts were never captured.

## Data and API contracts

listPantry: GET /v1/pantry/items returns items and ETag. upsertPantryItem: POST /v1/pantry/items accepts ingredientId, Idempotency-Key and the current item version for overwrites. removePantryItem: DELETE /v1/pantry/items/{ingredientId} uses If-Match.

    {"ingredientId":"00000000-0000-4000-8000-000000000011","presence":"usuallyHave","confirmationStatus":"usual","confirmedAt":null,"staple":true,"expectedVersion":3}

A plan receives an immutable availability snapshot containing ingredientId, presence, confirmationStatus and confirmation time, not a mutable pointer alone. The first-release UI leaves optional transport quantity/unit fields unset; their presence in the schema does not enable exact-stock tracking. No expiry or inferred freshness is collected. Ingredient display labels come from catalog lookup rather than user-supplied authorization data. For a prepared dish, use PlanRequest.baseMeal with explicit description/preparationState and confirmed ingredient IDs; unknown composition cannot satisfy a hard-exclusion check. Return typed unknown-ingredient, concurrency or validation outcomes with safe field details.

## Permissions and lifecycle

Pantry items are private to the principal. Circle, post and household features never read or expose them without an explicit contribution/share action. Guest inventory stays in a bounded guest/local context and may be explicitly merged on account creation. Account deletion removes pantry records. A long absence does not create an obligation to reconcile everything; existing staples remain uncertain until needed.

## Failure and offline behavior

Allow ingredient selection and local drafts offline using downloaded ingredient aliases. Queue account pantry edits with per-item mutation IDs; reconcile version conflicts by showing both values, not by replacing newer confirmed data. Unknown items can remain draft text but cannot be falsely treated as verified catalog ingredients. If syncing fails, the current explicit meal snapshot still reflects what the user selected locally, pending normal server validation when planning resumes.

## Integration and dependencies

Catalog provides ingredient IDs, aliases and component relationships. F02/F01 consume snapshots; F10 offers supported replacements; F20 reuse remains optional. F35 later shares only specifically volunteered ingredients, never this entire pantry.

## Execution plan

- Implement ingredient alias selection and privacy-scoped pantry table with version columns.
- Build PANTRY chips, staple confirmation and explicit current-meal selection.
- Add Kotlin local queue with item-level conflict resolution.
- Emit pantry_essential_confirmation and plan_missing_ingredient counts without ingredient names in general analytics.

## Acceptance and release gates

Test a stale staple, two devices updating the same item, an unknown composite food, offline deletion followed by reconnect, and guessed ownership IDs. A result must disclose every missing essential before cooking. Confirm completing a meal does not silently subtract quantities. Release rough_pantry progressively; disabling sync preserves readable local selections and offers manual ingredient entry.
