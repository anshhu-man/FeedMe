# F39 — Private Cooking Preferences

## Strategy
Food exclusions, equipment, effort, memories, and pantry details should help the person cook without becoming social profile attributes. This feature defines a enforceable boundary between private personalization and deliberate sharing. It ships before social surfaces. It is distinct from F04’s preference-editing experience and F18’s memory controls.

## Experience and screen design
`PRIVACY` explains “Your cooking preferences are private” and links to `FOOD_PREFS`, `EQUIPMENT`, and `MEMORY`. It separately controls who may send private replies, recipe requests, and coordination invitations: current circle members or nobody. `PROFILE_PLATE` shows only intentionally provided profile information. `SOS_CREATE`, `PACT_CREATE`, `CONTRIBUTION`, and `CAPTURE` preview explicitly selected shared fields. A private adaptation summary does not automatically become a public caption. Users may write about their own preferences voluntarily, but the app does not infer permission from doing so once.

## Production sequence
`GET /v1/preferences` returns the owner’s private cooking settings. `PATCH /v1/preferences` changes them with `If-Match`, validates hard exclusions, and emits `preferences.changed` for private planning-cache invalidation. `GET /v1/me/privacy` and `PATCH /v1/me/privacy` read/update social-contact preferences. The privacy transaction increments `privacyVersion`, records `privacy.changed` in the outbox, and makes new request checks use the committed policy immediately. Social profile serializers read an explicit public-field allowlist rather than serializing the preference object with selected exclusions. The UI confirms the server policy and invalidates pending request eligibility.

## Data and API contracts
`CookingPreference(userId,hardExclusions,equipment,effortDefaults,tastePreferences,version)` is owner-scoped; sensitive free text is minimized. Private contact settings use `allowCircleMemberMessages`, `allowRecipeRequests`, and `allowCoordinationInvites`; false means nobody, never public access. `socialDiscoveryVisible` affects only the owner’s UI. Post, roster, reaction, pact, poll, and notification DTOs exclude private preference fields. Shared requests use a separate `SharedCookingContext` populated only from previewed fields. `PREFERENCE_INVALID`, `VERSION_CONFLICT`, and `CONTACT_NOT_ALLOWED` are typed errors; senders receive generic unavailability rather than a leaked policy value.

## Permissions and lifecycle
Only the owner and specifically authorized internal planning operations may read private settings. A circle membership, household membership, recipe save, or shared source post never grants this access; F44 requires separate explicit household rules. Changing a contact preference stops new requests and pending notification delivery, not historical participant-private messages. Hard exclusions are never relaxed by language interpretation or social suggestions. A block is stricter than an enabled contact preference and always wins.

## Failure and offline behavior
Local preference edits can guide on-device filtering immediately but remain visibly pending until synchronized. Privacy-reducing server effects require acknowledgement; offline toggles must not claim that other devices or senders are already restricted. Merge nonconflicting fields using versions; conflicting exclusions require explicit review, never an automatic union/removal that changes intent silently. Logout clears account-scoped caches and cancels queued contact-setting writes. The planning service revalidates constraints at execution even if its cache is stale.

## Integration and dependencies
F04 preferences, F16 memory, F18 editing, F28 replies, F29 requests, F32–F37 coordination, F40 audience controls, F42 blocks, and F49 account privacy. Telemetry uses reason codes and bounded aggregates; private preference text cannot enter event properties or push payloads.

## Execution plan
Create separate schemas and serializers, implement owner authorization and contact-policy checks, then privacy UI and shared-field previews. Add contract tests over every social response and telemetry event, followed by cache invalidation and cross-device conflict handling.

## Acceptance and release gates
Test profile, feed, exports, notifications, logs, and coordination responses for forbidden fields; test toggle/send races and hard-exclusion enforcement on stale plans. `social.contact.enabled` can stop all new contact requests while preserving private cooking and settings. Release requires zero unauthorized preference fields in serialization fixtures and clear pending-state wording offline.
