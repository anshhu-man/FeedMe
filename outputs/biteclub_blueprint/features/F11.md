# F11 — Effort Preview

Phase: first release. Owner modules: catalog, planning.

## Strategy

Make the real work visible before a person commits to a meal. Preview active preparation, total elapsed time, waiting, required equipment and cleanup. Estimates are tested editorial metadata, not promises about every kitchen or person; a friend's reported time must remain distinguishable from an app estimate.

## Experience and screen design

RECOMMENDATIONS shows total time and a compact effort summary. RECIPE and VARIANT expand to active preparation, waiting, utensils, required equipment and cleanup, with ingredient preparation exposed: “Requires slicing” is more informative than an unexplained Easy label. A small explanation describes estimates as approximate. Any missing ingredient or unusual equipment appears above Cook this. In comparison views, changed values are highlighted in words rather than color alone. A shared community recipe displays “Creator reported” for its time; an adapted reviewed version uses its own verified editorial estimate and provenance.

## Production sequence

1. Retrieve effort metadata from the exact immutable recipe/variant revision.
2. Validate completeness against declared operations, equipment and serving range.
3. Derive the display summary without summing parallel tasks twice. Total time comes from the reviewed preparation sequence, not simply active plus every timer.
4. Compare the user's limits against the same fields displayed by the client.
5. If adaptation changes preparation, materialize and review/retrieve a new estimate version rather than retain the original number.

## Data and API contracts

GET /v1/recipes/{recipeId}/versions/{recipeVersionId} returns RecipeVersion; GET /v1/plans/{planId} embeds it as recipeSnapshot. The preview reads these canonical fields from that object; the example below is a field projection, not a standalone response.

    {"activeMinutes":8,"totalMinutes":15,"waitingMinutes":7,"cleanupMinutes":3,"equipmentIds":["pan","spatula"],"utensilCount":2,"preparationTags":["someChop","onePan"],"estimateBasis":"reviewerEstimate","estimateNote":"Illustrative estimate; validate against the reviewed recipe."}

Catalog estimates include serving bounds and reviewer audit references, not publicly exposed personal reviewer data. Community estimates need creatorReported provenance and cannot satisfy a reviewed-compliance claim by themselves. Optional unknown values are omitted and display Unavailable; never coerce unknown into zero. Required active/total values must be valid before a recipe enters strict matching. Content-version identity versions the estimate; do not invent an independent transport revision field. Reads use ETag and principal-aware cache policy for private saved recipes.

## Permissions and lifecycle

Publicly available catalog effort is non-personal. Actual user feedback about effort remains private unless they share it. Displaying required utensils does not imply the user's equipment inventory is public. Historical saved variants retain their original estimate revision unless a recall or explicit update path requires action. Editorial estimate corrections create new content versions with an auditable reason.

## Failure and offline behavior

Cached previews remain available alongside their pinned recipe. If effort metadata is missing or corrupted, do not show an effortless badge or fabricate a duration; display Unavailable and prevent strict automatic matching until repaired. A changed server recipe version must not replace an active cooking preview mid-session. For recalled content, show the recall state before cooking while retaining allowed explanatory information.

## Integration and dependencies

F05 uses exactly these fields for limits; F08 compares them for simplification; F10 updates them for substitutes. F12 timers consume reviewed step durations, not the total-time label. F51 provides editorial review and estimate-testing workflows.

## Execution plan

- Define shared EffortEstimate model with nullable unknowns and provenance.
- Add server validation for required metadata and variant consistency.
- Build summary/expanded/compare components with scalable text and localization.
- Instrument effort_details_opened, estimate_missing and optional user-reported effort mismatch separately from recipe quality.

## Acceptance and release gates

Test parallel preparation, a recipe with overnight waiting, zero-heat assembly with chopping, missing duration, creator-reported estimates and a variant needing additional cleanup. UI values must exactly match matching-policy inputs. Catalog launch requires reviewer checks of effort completeness and practical recipe testing; proposed time accuracy targets must be established from that testing. A flag can suppress an unreliable badge while keeping literal steps and equipment visible.
