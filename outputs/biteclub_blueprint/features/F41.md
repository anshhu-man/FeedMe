# F41 — Notifications

## Strategy
Notifications support chosen cooking plans and direct social interactions with clear controls. They must be optional, bounded, and safe on a locked screen. Push permission, server subscription preferences, and in-app activity are separate states. Ship essential controls before any sender can trigger delivery; later coordination features add categories through the same policy.

## Experience and screen design
`NOTIFICATIONS` exposes toggles for replies, recipe requests, circle invitations, reactions, and coordination updates, plus optional quiet hours and time zone. `NOTIFICATION_PERMISSION` explains the selected benefit before the native permission prompt. Denial leaves `INBOX` usable and provides a device-settings route without repeated prompts. Activity cards show a safe summary, time, unread state, and a route to authorized content. The locked-screen default is “You have a FeedMe update,” with no meal details, names, pantry contents, location, or message body.

## Production sequence
`GET /v1/notification-settings` loads server choices; `PATCH /v1/notification-settings` validates and updates them with `If-Match`, then emits `notification_preferences.changed`. `POST /v1/devices` registers the current authenticated installation’s APNs/FCM token only after the platform supplies it. An outbox consumer processes an eligible domain event, checks category, block/mute rules, resource access, and quiet hours, then writes a unique `Notification` and delivery job. Immediately before sending, the worker repeats authorization and preference checks. `GET /v1/notifications` retrieves authorized activity, and `POST /v1/notifications/{notificationId}/read` marks one owned activity read idempotently; bulk UI acknowledgement iterates only explicit currently loaded IDs with bounded concurrency.

## Data and API contracts
`NotificationPreference(userId,categories,quietHours,timeZone,version)`; `Device(id,userId,installationId,sessionId,platform,tokenHash,encryptedToken,state,updatedAt)`; `Notification(id,recipientId,eventId,category,resourceRef,state,createdAt)`; `Delivery(notificationId,deviceId,state,attempt,nextAttemptAt)` define the pipeline. Unique recipient/event/category and notification/device constraints suppress duplicates. Push payloads contain only notification IDs and opaque references. `DELETE /v1/account/sessions/{sessionId}` revokes the owned session and its device-token eligibility. Token rotation rebinds the installation atomically; no token remains assigned to a previous signed-out user. `PREFERENCES_INVALID`, `DEVICE_CONFLICT`, and `VERSION_CONFLICT` are typed errors.

## Permissions and lifecycle
Only the recipient reads or acknowledges activity. Notification creation grants no content access, and opening always reauthorizes. Deleted posts, expired requests, blocks, revoked circles, and disabled categories suppress pending delivery. Reactions are coalesced instead of producing a notification for every toggle. Quiet hours delay eligible informational pushes; stale events are discarded rather than delivered as a morning backlog. Coordination reminders require an explicitly accepted plan and selected reminder, not merely viewing an event.

## Failure and offline behavior
APNs/FCM delivery is best effort; do not label an app event as read because a provider accepted it. Retry transient failures with bounded exponential backoff and provider guidance; invalid tokens are deactivated. Push send cannot be guaranteed exactly once externally, so stable notification IDs let clients deduplicate receipts. Offline preference changes remain pending, and in-app read changes queue with account-scoped IDs. Time-zone changes require recomputing quiet-hour instants and user-confirmed reminder times.

## Integration and dependencies
Identity sessions, native permission APIs, F23/F28/F29 social events, F32–F37 coordination, F39 contact policies, F42 mutes/blocks, and F53 deep links. Outbox order and event IDs are used for deduplication, never as authorization shortcuts.

## Execution plan
Implement preferences and installation binding, then unique notification records and provider adapters, then in-app read states, quiet hours, and expiry suppression. Test both platforms and record provider outcomes, queue age, suppression reasons, and duplicate rates without private content.

## Acceptance and release gates
Test token reuse after logout, denied OS permission, invalid tokens, preference/send races, deleted targets, quiet hours across DST, repeated outbox deliveries, and cancelled plans. `notifications.push.enabled` stops all push sends while in-app activity and settings remain available; category switches are separately controllable. Release requires no sensitive preview fields and no claimed exactly-once provider delivery.
