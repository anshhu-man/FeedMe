# FeedMe blueprint coordination contract

Status: historical authoring/coordination note retained for provenance. The completed [package guide](README.md), [OpenAPI contract](architecture/04_API_Contract.json), [screen registry](registry/screen_registry.json) and feature specifications supersede provisional conventions and the initial screen inventory below.

Scope: build-ready feature specifications, strategy, architecture, execution plan, screen designs, full screen/action registry, and an executable local navigation/architecture explorer. This is planning and a simulated prototype, not a production deployment. User selected FeedMe and confirmed Android + iOS with shared Kotlin. No existing Smart Kitchen implementation has been inspected.

Proposed stack: Kotlin Multiplatform shared domain/network/local storage, Compose Multiplatform UI with native platform integrations; Kotlin Ktor modular-monolith API; managed PostgreSQL; AWS ECS Fargate, RDS PostgreSQL Multi-AZ, S3 private media, CloudFront signed delivery, SQS workers, EventBridge expiry schedules; Cognito user-pool auth through browser authorization code + PKCE and email/password SDK flows; APNs/FCM; RevenueCat for optional purchases; provider-agnostic server-side structured language interpretation with deterministic reviewed-catalog matching. Verify provider details with primary sources before relying on them. Use an outbox in the same database transaction for asynchronous effects. Redis is optional, not a core dependency.

Canonical modules: identity, profile, pantry, catalog, planning, cooking, memory, social, circles, conversations, coordination, commerce, safety, platform.

API naming conventions: `/v1/me`, `/v1/preferences`, `/v1/pantry`, `/v1/recipes`, `/v1/plans`, `/v1/cook-sessions`, `/v1/feedback`, `/v1/memories`, `/v1/collections`, `/v1/posts`, `/v1/media`, `/v1/circles`, `/v1/threads`, `/v1/invitations`, `/v1/notifications`, `/v1/reports`, `/v1/blocks`, `/v1/mutes`, `/v1/sos`, `/v1/pacts`, `/v1/potlucks`, `/v1/shortcuts`, `/v1/polls`, `/v1/households`, `/v1/packs`, `/v1/entitlements`, `/v1/account`, `/v1/admin/...`. Reads are GET, changes POST/PATCH/DELETE. Include idempotency for durable actions, server-side object authorization, version/ETag checks for concurrency, and typed error responses. Guest cooking uses a bounded guest session, never a bypass of object authorization.

Proposed privacy semantics: recipe-save grants permit a private immutable copy of an explicitly saveable recipe version, not original media/comments. Revoking future grants stops new copies; existing authorized recipe copies persist unless recalled for safety/legal deletion, with creator identity removed where required. Explain this before sharing/deleting; media is not copied. Story removal from Today uses server time at expires_at, independent from Keep on Plate. Private original media is never included in a public/remixed audience automatically. Hard exclusions are never relaxed by the language model. No unsafe/unknown food-photo inference.

Avoid an unlimited free-user save cap that removes existing access. Paid library means organization/tools rather than withholding basic saved recipe access. Household purchases cover explicit memberships, never imply family store sharing without verification. Features use server entitlements; purchase UI alone does not authorize access.
