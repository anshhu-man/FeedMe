# F32 — Fridge SOS

## Strategy
Fridge SOS is an optional, time-limited request for practical meal ideas from a chosen circle. It complements the private Smart Meal Helper; it does not expose the pantry automatically or promise real-time help. Although scheduled for a later release, its data, delivery, expiration, and abuse controls must be built as a complete workflow.

## Experience and screen design
`SOS_CREATE` asks what the person has, time available, equipment, effort, and which circle should receive the request. Selected pantry entries are previewed individually; private exclusions and memories are not included automatically. The user sets an expiry between 30 minutes and 3 hours, default 2 hours, and confirms Send. `SOS_DETAIL` shows the request, remaining time, responses, and “I’ve got dinner” to close it. Each response can link an accessible recipe or provide a short practical suggestion. “Try this” opens `RECIPE` or `ADAPT`; it never marks a meal accepted without a tap.

## Production sequence
`POST /v1/sos` validates selected circle membership and explicit shared fields, then commits `SosRequest` and `sos.created` to the outbox. Delivery checks member eligibility and notification settings. `GET /v1/sos/{sosId}` authorizes current membership and returns active responses. `POST /v1/sos/{sosId}/replies` locks the request, checks `serverNow < expiresAt`, validates actor and recipe access, and commits one response plus `sos.response_created`. Trying a suggestion opens its authorized recipe or personal adaptation. `POST /v1/sos/{sosId}/resolve` with an empty body closes the owned request and emits `sos.closed`; its receipt updates the screen without publicly identifying a winning responder.

## Data and API contracts
`SosRequest(id,authorId,circleId,sharedIngredients,timeBudget,equipment,effort,state,expiresAt,version)` distinguishes open and terminal state. Shared quantities use structured units; photos cannot infer unknown food or safety. `SosResponse(id,sosId,authorId,text,recipeVersionId,version,deletedAt)` stores references, not third-party recipe copies. `PATCH /v1/sos/{sosId}` supports explicit corrections while open with `If-Match`; `DELETE /v1/sos/{sosId}/replies/{replyId}` removes an owned response. Resolving does not create a public ranking of replies. Durable writes require idempotency keys. Errors include `SOS_CLOSED`, `RECIPE_UNAVAILABLE`, and `VERSION_CONFLICT`.

## Permissions and lifecycle
The requester and current, unblocked members of the selected circle may view an open request. At closure or expiry, new responses stop synchronously regardless of worker delay. The requester retains a private receipt for a proposed 30 days; responders may manage their own text but cannot reopen request content after circle access is lost. Removing a member or dissolving the circle immediately ends shared visibility. Recipe grants remain independent, and no response unlocks original post media.

## Failure and offline behavior
An offline request is an unsent draft whose expiry starts only at server commit. Do not send a queued SOS hours later automatically: require reconfirmation if the intended send time is over 15 minutes old. Response retries preserve the original key; a closed request keeps the unsent response as a draft. If nobody replies, show a clear private-helper route without inventing activity. Cancelling during a response transaction has one serialized winner.

## Integration and dependencies
F02 private helper, F03 pantry, F23 circles, F24 recipe references, F39 privacy, F41 notifications, and F42 reporting. Private preference matching can filter a chosen response locally or through the authorized planning service without sharing those preferences with responders.

## Execution plan
First implement request/response state machines and expiry checks; then build creation, detail, and selection screens; then wire opt-in delivery and recipe adaptation; finally add cleanup, abuse limits, and metrics for expired-response rejection and successful selection. No later-phase step is an unspecified dependency.

## Acceptance and release gates
Test close/respond races, delayed expiry jobs, offline stale drafts, circle departure, inaccessible recipe links, and an unanswered request. `coordination.sos.enabled` blocks new requests while allowing owners to close or delete existing ones. Release requires explicit shared-field preview and zero automatic private-pantry or preference disclosure.
