# F17 — Explain My Suggestion

Phase: first release. Owner module: planning; memory and catalog provide evidence.

## Strategy

Make each recommendation understandable enough for the user to trust, correct or reject. Explanations must describe actual matching decisions: confirmed ingredients, permitted effort, available equipment and explicit past preferences. They must not invent reasons with a language model or dress an uncertain nutrition claim as personalization.

## Experience and screen design

RECOMMENDATIONS and VARIANT show a short Why this? disclosure. Opening it expands factual reasons on the same screen: “Uses the ingredients you confirmed,” “Fits your no-heat choice,” or “You saved this combination.” Each editable reason links to PANTRY, EFFORT, FOOD_PREFS or MEMORY_DETAIL. Missing ingredients and tradeoffs sit alongside positive reasons. A no-match state explains the blocking constraints with Change ingredients/Change time actions; it never suggests dropping an exclusion as the default. RECIPE keeps provenance accessible without crowding the cooking steps.

## Production sequence

1. During matching record the filter decisions, ranking contributions and their source versions.
2. Store a compact explanation fact set with the plan snapshot.
3. Render approved localized templates from reason codes and permitted values; no post-hoc freeform rationalization.
4. On disclosure, verify the plan owner and source visibility before exposing contextual details.
5. When preferences, pantry or catalog change, mark the explanation historical and offer Refresh match rather than claiming it reflects current conditions.

## Data and API contracts

getPlanExplanation: GET /v1/plans/{planId}/explanation returns a ReasonPage from stored decision facts; no new language-generation call is required. GET /v1/plans/{planId} carries reasons for the primary card, while the disclosure uses the dedicated authorized read. The page's serverTime is response time, not a claim that historical constraints were freshly reconfirmed.

    {"items":[{"code":"ingredientFit","label":"Uses the ingredients you confirmed"},{"code":"effortFit","label":"Fits your no-heat choice"},{"code":"likedBefore","label":"You saved this combination","sourceMemoryId":"00000000-0000-4000-8000-000000000061"}],"nextCursor":null,"serverTime":"2026-09-13T10:00:00Z"}

Internal facts retain eligibility/ranking category and source revision; transport Reason exposes code, approved label and optional sourceMemoryId. Navigation derives from recognized codes and authorized identifiers. No-match uses the typed error/plan status and returned reasons rather than an undeclared unmetConstraintCodes field. Unknown reason codes fall back to factual generic copy or are omitted. A deleted memory reference may yield historical wording only for the owner's plan, without resurrecting deleted details. API object authorization applies even to apparently harmless explanation data.

## Permissions and lifecycle

Explanations remain private when based on pantry, exclusions or memory. Share Composer must create separate public recipe context and cannot copy this block automatically. Household results later explain compatibility generically rather than reveal a member's private food requirements. Preserve decision facts only for documented plan retention; user data deletion must remove personal facts and identifiers.

## Failure and offline behavior

Cached plan explanations are readable with their snapshot label. If a deep-linked memory was deleted, show an unavailable detail and return to the recipe; do not fail the whole meal screen. If explanation rendering fails, the recipe can remain visible with its literal ingredients and effort, but suppress unsupported personalization copy. A mismatch between explanation and evaluation is an integrity incident and disables affected matching/ranking logic until resolved.

## Integration and dependencies

F02 records decisions, F04–F11 supply constraint facts, F16 supplies explicit memories and F18 handles corrections. F54 telemetry monitors explanation coverage without storing the sensitive explanation payload.

## Execution plan

- Define reason-code taxonomy and immutable decision-fact schema.
- Add filter/ranking instrumentation inside the matching transaction.
- Build localized disclosure rows and correction navigation.
- Add explanation-to-evaluator consistency checks; emit explanation_missing and explanation_source_stale.

## Acceptance and release gates

Test every visible explanation against recorded evaluation facts, a removed memory, changed pantry, unrecognized code, expired source and household privacy. No UI reason may claim a constraint was met if the evaluator rejected it. Roll out explanation_templates by version; disable a faulty template or memory reason while keeping literal recipe facts and manual correction controls available.
