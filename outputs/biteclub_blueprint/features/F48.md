# F48 — Profile and onboarding

## Strategy
Collect the minimum for identity and useful cooking, with optional kitchen/preferences steps. A user should reach a useful meal without adding friends, an avatar or a detailed pantry. Editing an existing profile returns to Settings; it does not replay first-run onboarding.

## Experience and screen design
PROFILE_SETUP has display name, unique handle, optional avatar and an explicit guest-save merge choice. FOOD_PREFS and EQUIPMENT offer Save and Skip. Native notification permission is deferred to NOTIFICATION_PERMISSION after an understandable social use case. Progress indicators refer only to the current optional setup, with no completion score. Empty Today and Cookbook states offer cooking and invite actions.

## Production sequence
Bootstrap returns `profile.onboardingStep`, `profile.version` and `requiredGates`. Client prevalidates normalized handle format; `PATCH /v1/me` reserves its canonical case-folded form under a database unique constraint. Profile writes are atomic and return the new `version` and ETag. Preferences are separate versioned writes; skipping records only that the prompt was skipped, not inferred dietary choices. Completing or skipping enters HOME when required gates are satisfied. A deferred invite then offers INVITE_ACCEPT rather than auto-joining a circle.

## Data and API contracts
Canonical `Profile` response fields are `id`, `displayName`, `handle`, optional `avatarMediaId`, `onboardingStep`, `eligibility`, `version`, `createdAt` and `updatedAt`, plus optional `bio`. Consent and restrictions are stored separately. `ProfilePatch` accepts the documented editable fields; it does not accept `accountId`, `handleCanonical`, `onboardingCheckpoint` or `revision`. `PATCH /v1/me` uses `If-Match`, `Idempotency-Key` and the registered `X-Device-Session`; `/v1/preferences` stores preferences/equipment. Avatar media uses the same sanitized-media pipeline with a distinct intended usage. Guest merge binds explicit source identity and handles duplicate cookbook entries deterministically.

## Permissions and lifecycle
Only the account owner edits a member profile. Public/circle display fields are separate from private cooking preferences. Handle changes update source attribution via account identity without granting old links new access. Profile deletion follows account lifecycle. Guest merge never transfers source grants beyond the rights originally held by that guest.

## Failure and offline behavior
Handle conflicts show a neutral inline choice without exposing private account data. Lost save responses reuse operation ID and return the committed revision. Concurrent edits show field-level changed values; avoid last-write-wins for consent or exclusions. Offline setup remains a local draft; user can use guest cooking if no authenticated operation succeeded. Avatar failure must not block name-only onboarding.

## Integration and dependencies
Depends on F47 IdentityGate, F04 preferences, F03 pantry, F24 media processing and F53 navigation. Shared forms produce domain commands, never raw arbitrary profile JSON. No contacts import or automatic invitations are an onboarding dependency.

## Execution plan
Define canonical handle validation and uniqueness migration. Implement profile repository with checkpoints, editable name/avatar UI, conflict recovery and guest-merge confirmation. Add separate entry modes for first-run versus Settings edit. Test server/client validation parity using shared fixtures and real native autofill/keyboard layouts.

## Acceptance and release gates
Test first-time provider account, guest conversion, skipped preferences, duplicate handle races, lost response, avatar rejection and editing from Settings. A user with no friends or saved meals must reach REQUEST from HOME. Avatar and optional setup can be disabled by flag without breaking completed identities. Measure time to first accepted meal separately from profile completion.
