# F18 — Editable Memories

Phase: first release. Owner module: memory.

## Strategy

Give people real control over what personalization remembers. A user must be able to inspect the specific basis, correct its scope, forget it and stop its future effect. Hiding a row while retaining the same ranking signal would fail this feature.

## Experience and screen design

MEMORY lists searchable readable preferences with an empty state explaining that feedback is optional. MEMORY_DETAIL shows the exact target, effect, source action and where it applies. Actions are Change preference, Forget this and Open source feedback when available. Editing may narrow a signal from an ingredient generally to a particular recipe context, but cannot convert it into a hard exclusion; that action links to FOOD_PREFS. A concise confirmation describes whether source feedback will also be removed or detached so the memory will not reappear. SETTINGS can turn personalization off without deleting saved recipes.

## Production sequence

1. Read the memory and current revision with all supporting sources the owner may inspect.
2. Validate the requested target/effect and ensure broader generalization requires an explicit choice.
3. Apply the edit, source retraction/detachment or deletion atomically; record a non-sensitive audit of the mutation and append cache-invalidation outbox events.
4. Recompute dependent memories where a source was shared. Use per-target contributions rather than deleting unrelated feedback wholesale.
5. Acknowledge only when the authoritative ranking read model no longer applies the forgotten contribution; queued client edits suppress it locally immediately.

## Data and API contracts

GET /v1/memories/{memoryId} reads detail. PATCH /v1/memories/{memoryId} requires If-Match and Idempotency-Key.

    {"enabled":true,"value":"show_less","context":{"recipeVersionId":"00000000-0000-4000-8000-000000000021"}}

DELETE /v1/memories/{memoryId} uses the mutation's Idempotency-Key and If-Match; source contribution removal is the operation's documented semantics, not an undeclared body field. Use the canonical success/error response rather than inventing removedMemoryId or affectedSourceIds transport fields. If retained feedback supports another memory, detach only this contribution and suppress its replay; purge linkage identifiers during account erasure. A new deliberate feedback event may recreate a similar preference, but an old event replay may not. Return 412 for concurrent edits and 404 for inaccessible IDs.

## Permissions and lifecycle

Only the principal can alter their memories; household organizers and story authors cannot. Deleting a memory does not delete a saved recipe by surprise, and deleting a saved recipe does not necessarily erase separate taste feedback—both screens explain the distinction and provide links. Guest preferences can be edited locally; account merge respects explicit local forget operations instead of reviving server copies.

## Failure and offline behavior

Offline edits show Pending sync and remove the effect from local ranking immediately. On revision conflict, show the current server state and the user's intended edit; keep stricter local suppression until resolved. If source recomputation fails, roll back the atomic mutation or keep the affected ranking contribution disabled with a recoverable operation state. A failed request must never show a definitive Forgotten confirmation while the server still actively uses it.

## Integration and dependencies

F15 source feedback, F16 projection, F17 explanations, F19 independent saved content and F49 export/deletion must share these semantics. Feature flags must not hide user deletion controls when personalization is disabled.

## Execution plan

- Add source-contribution links, suppression/retraction handling and revisioned mutations.
- Implement cache invalidation plus replay/rebuild correctness tests.
- Build edit/forget confirmation and offline conflict UI.
- Emit memory_edit_failed, memory_forget_applied and stale_memory_effect_detected without the removed content.

## Acceptance and release gates

Test forget then outbox replay/rebuild, one feedback source supporting multiple memories, guest/account merge, two-device edits and personalization disabled. Confirm new plans stop using the removed signal and exported data reflects the final state. Editing/deletion is a release gate for personalization. Rollback may disable new learning, but must retain working inspect/forget access.
