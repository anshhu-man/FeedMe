# F23 — Kitchen Circles

## Strategy
Kitchen Circles are explicit, invitation-based groups for sharing everyday food. They provide an understandable audience boundary without address-book upload or a public follower graph. Launch with a proposed maximum of 50 active members per circle, configurable server-side. Joining social spaces remains optional.

## Experience and screen design
`CIRCLES` lists memberships and pending invitations. `CIRCLE_CREATE` collects a name and optional description. `CIRCLE` contains recent posts and members; `CIRCLE_MEMBERS` exposes owner controls and leave actions. `INVITE` creates a limited-lived invitation link. `INVITE_ACCEPT` shows the circle name, inviter, and “Members can see posts shared with this circle,” then requires explicit acceptance. A forwarded or expired link produces `UNAVAILABLE` without exposing the membership list.

## Production sequence
`POST /v1/circles` atomically creates the circle and its owner membership. `POST /v1/invitations` with `{targetType:CIRCLE,targetId}` creates a hashed, single-use token expiring after seven days. `GET /v1/invitations/preview?token=…` provides the minimal join preview. `POST /v1/invitations/accept` with the token authenticates the account, locks the invitation and circle, checks capacity, then creates one membership and consumes the token in one transaction. Outbox events `circle.created`, `circle.member_joined`, and `invitation.accepted` drive inbox updates. `DELETE /v1/invitations/{invitationId}` revokes an unused owned invitation. Member removal or self-leave uses `DELETE /v1/circles/{circleId}/members/{userId}`; its transaction revokes effective access and emits invalidations before the UI confirms removal.

## Data and API contracts
`Circle(id,name,status,ownerId,version)` and `CircleMember(circleId,userId,role,state,joinedAt,version)` enforce one active membership per pair and exactly one owner for each active circle. Roles are `OWNER`, `ADMIN`, and `MEMBER`; explicit admins may invite and remove nonowners, never transfer ownership or dissolve. `Invitation(id,circleId,tokenHash,expiresAt,consumedBy,revokedAt)` never stores raw links in logs. Transfer ownership through `PATCH /v1/circles/{circleId}/members/{userId}` using `If-Match` and an explicit transfer operation that atomically demotes the old owner and promotes the target. An owner must transfer ownership or dissolve the circle before leaving. `DELETE /v1/circles/{circleId}` dissolves it without deleting members’ accounts or private recipe copies.

## Permissions and lifecycle
The owner controls roles, transfer, and dissolution; explicit admins can invite, remove nonowners, and edit circle details. Members can inspect active members and leave. A newly accepted member can see still-live Today posts and retained Plate posts shared to that circle; state this before joining and in audience selection. Membership removal and dissolution end access immediately at the authorization layer. Posts shared to other valid circles may remain visible. Invitation acceptance never overrides a block involving the inviter or owner.

## Failure and offline behavior
Join, leave, transfer, and removal require server acknowledgement. Idempotency makes repeated accepts return the same membership without consuming capacity twice. Two users redeeming one token yield one winner and `INVITATION_USED` for the other. Offline lists show their last-refresh state, but media access still revalidates. Stale role changes yield `VERSION_CONFLICT`.

## Integration and dependencies
Identity, audience authorization, social feed invalidation, notifications, and F42 blocks are required. Deep links preserve the invitation only through an explicit login flow; do not redeem during link preview.

## Execution plan
Build membership invariants and acceptance locking, then owner/member screens and native link handling. Add access-revocation events and delivery retries. Monitor failed redemptions, duplicate attempts, and propagation latency without logging tokens.

## Acceptance and release gates
Test capacity races, token reuse, expired/revoked links, owner transfer, dissolution, removal during viewing, and multi-circle access. `circles.invites.enabled` stops new invitations; existing member privacy and leave controls stay available. No release until server authorization tests prove a removed member cannot refresh content or signed media access.
