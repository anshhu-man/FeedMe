# F07 — Cook, Assemble, Improve

Phase: first release. Owner modules: planning, catalog.

## Strategy

Serve three real starting points through one helper: make a cooked dish, assemble a meal without heating, or improve food already prepared with one compatible addition. The app should recognize that a person who already has dinner does not need a replacement dinner. It should not imply every arbitrary base meal becomes nutritionally complete through an addition.

## Experience and screen design

REQUEST offers a compact optional “Starting with” control: Ingredients, Ready to assemble, or A meal already made. Automatic selection can be proposed from confirmed text, but the user can change it. Improve reveals a base-meal label and optional TASTE choice. RECOMMENDATIONS uses a meal card for cook/assemble and a smaller addition card for improve, with the ingredient, action and preparation requirement. RECIPE shows full steps for meals; addition instructions can be one short step with any necessary preparation. All routes retain Make it easier and Something else where supported.

## Production sequence

1. Resolve the explicit mode or confirm an interpreted mode when ambiguous.
2. Validate baseMeal information for improve; unknown composition is not treated as exclusion-safe.
3. Select catalog entries of the allowed content kind. Assemble enforces its operation constraints; improve requires a reviewed compatibility relationship to the reported base-meal type.
4. Apply the same exclusions, availability, effort and sensory filters across modes.
5. Return a typed result so rendering and cooking know whether they are presenting a whole recipe or an addition.

## Data and API contracts

createPlan POST /v1/plans accepts mode=auto/cook/assemble/improve and optional baseMeal. Modes are planning intent, distinct from energy.

    {"mode":"improve","baseMeal":{"description":"leftover rice bowl","preparationState":"alreadyPrepared","ingredientIds":["00000000-0000-4000-8000-000000000011"]},"constraints":{"ingredientIds":["00000000-0000-4000-8000-000000000012"],"maxTotalMinutes":5,"energy":"assemble","equipmentIds":["bowl"],"servings":1,"hardExcludedIngredientIds":[],"tasteTags":["crunch"]}}

The Plan result has a resolved mode=cook/assemble/improve, recipeVersionId and recipeSnapshot with ingredients/steps. The catalog internally distinguishes additions and reviewed compatibility relationships; improve identifies that presentation without inventing a separate wire contentKind field. PlanRequest.baseMeal uses description, preparationState and optional confirmed ingredientIds. A catalog addition has its own reviewed immutable version, not a free-text appendage. Unknown required composition yields needsConfirmation; no reviewed compatible addition yields noMatch. A changed explicit mode uses createPlan with the revised request; adaptations remain child plans and never mutate running sessions.

## Permissions and lifecycle

Base-meal labels remain private unless deliberately included in a story. No picture is needed, and a picture does not supply verified ingredients. A saved addition can preserve its compatible meal type without recording an entire meal diary. Reusing previously prepared food is always user-confirmed; the app does not determine storage safety from its age label.

## Failure and offline behavior

Keep all entered ingredients if the user switches modes. Invalid combinations, such as cook intent with assembly-only limits, surface a confirmation of intent or return an assembly candidate; do not silently enable heating. Offline cached additions display only their supported base types. If the catalog lacks compatibility information, show a general recipe alternative clearly labelled as such rather than claim to improve the user's specific dish.

## Integration and dependencies

F02 owns unified input, F05 energy rules, F06 sensory choice, F13 content variants and F12 preparation flow. F14 can save either a meal or an addition-plus-base combination. F17 explains why the content kind was selected.

## Execution plan

- Add content-kind and compatibility tables with editorial validation.
- Implement explicit/automatic mode resolver with deterministic fallback rules.
- Build mode-specific result layouts and preserve shared input state.
- Instrument mode_changed and mode_no_match; avoid counting an addition as a full meal outcome.

## Acceptance and release gates

Test prepared meals with unknown composition, incompatible additions, a no-cook mode with a heated step, mode changes after pantry entry, and a saved addition reopened without its original base. Release improve_mode only for reviewed compatibility coverage. Disabling a mode retains its saved readable content and directs new requests to supported choices without changing user constraints.
