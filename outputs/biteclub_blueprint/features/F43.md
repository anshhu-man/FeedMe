# F43 — Optional Participation

## Strategy
FeedMe must be useful to someone who never joins a circle, posts a picture, sends a message, enables notifications, or pays. The cooking and private-save journey is a complete product path. Optional Participation is a cross-cutting release requirement, not an onboarding checkbox. Evaluate time to a usable meal for people with zero social connections.

## Experience and screen design
`AUTH_WELCOME` offers “Try cooking first.” `HOME` gives meal help priority and provides meaningful cooking content when Today is empty. `MEAL_DONE` offers private save and Done as primary completion routes; sharing and feedback are optional. `TODAY`, `CIRCLES`, and `INBOX` show honest empty states with a return to cooking and no invented friends or activity. `PRIVACY` allows hiding social discovery shortcuts without deleting memberships or published posts; the explanation links to audience/deletion controls for changing actual visibility. Notification refusal and skipped profile extras never trap navigation.

## Production sequence
`POST /v1/guest-sessions` returns a bounded guest identity and capabilities for eligible catalog planning, cooking, and temporary private storage. Registered users read their account state through `GET /v1/me`; the guest is not granted that member endpoint. Guest social actions route to `AUTH_WELCOME` with a validated return destination, without broadened privileges. `PATCH /v1/me/privacy` updates `{socialDiscoveryVisible}` for an authenticated owner and emits `privacy.changed`. The UI preserves cooking, private saves, settings, and safety navigation. Account creation separately offers an explicitly authorized guest-data merge under F47.

## Data and API contracts
`GuestSession(id,capabilities,expiresAt,deviceBinding,state)` is a restricted principal, not an anonymous administrator. Proposed guest lifetime is 30 days with bounded storage and documented cleanup; the identity specification owns final operational limits. `ParticipationPreference(userId,socialDiscoveryVisible,version)` changes presentation only. `OnboardingCheckpoint(userId,step,state,updatedAt)` uses completed or skipped states; it does not infer consent. Public catalog recipes, owned guest copies, and member-social recipe grants have different access policies. `AUTH_REQUIRED`, `GUEST_LIMIT_REACHED`, `GUEST_EXPIRED`, and `VERSION_CONFLICT` expose a useful recovery route without granting unauthorized data access.

## Permissions and lifecycle
Guests can access only explicitly eligible resources under their scoped identity. Account-required features include circle membership, social publication, messages, and access to other people’s private posts. Hiding social discovery does not retroactively hide published posts or revoke grants; the UI must state this. Existing private recipe access does not vanish behind an upgrade prompt. Permission prompts are attached to user-selected actions, and choosing Skip does not re-prompt on every visit. Re-enabling social surfaces does not send invitations, publish drafts, or opt into push delivery.

## Failure and offline behavior
Previously authorized private recipes and cooking progress remain useful in `OFFLINE` according to their local eligibility and recall state. A guest with an expired session gets a clear recovery/signup route and a preview of any local recoverable data; do not silently discard it. Cross-account guest merge is explicit and idempotent, with the original data retained until a server receipt confirms ownership transfer. Social service failure removes only dependent surfaces and shows a small status, without blocking catalog recipes or current cooking sessions unnecessarily.

## Integration and dependencies
F02–F20 private cooking, F47 identity/merge, F48 optional onboarding, F49 data lifecycle, F50 paid tools, F53 navigation, and F54 dependency health. Feature flags are server-issued capability inputs, while server object authorization remains mandatory regardless of hidden UI.

## Execution plan
Build and test the zero-friends guest journey first; add capability-aware navigation and optional onboarding; then implement participation preferences and account merge recovery. Run accessibility walkthroughs for every Skip, Back, and Done route. Track completion/drop-off without interpreting nonposting as failure.

## Acceptance and release gates
Test first launch with no account, denied camera/push permissions, no friends, hidden social discovery, expired guest session, failed social backend, and cancelled purchase. Every optional path must return to useful cooking without unwanted publication or messaging. `social.discovery.enabled` and per-user hiding must preserve personal recipes, settings, and safety controls. Release requires a full usable guest cooking journey and no paid cap that removes basic existing saved-recipe access.
