## Gaps to resolve before enabling buttons

1. **The canonical bundle has no content manifest.** [F19](../../outputs/biteclub_blueprint/features/F19.md) and [F13](../../outputs/biteclub_blueprint/features/F13.md) require a manifest/content-hash download contract, but canonical `SavedRecipe` contains the recipe snapshot and metadata, not a signed manifest or independently supplied `contentHash`. The existing repository hashes bytes locally. That is local integrity evidence, not server-issued offline rights, review approval or recall freshness. Preserve this distinction; do not invent a wire field or declare the full offline-content release gate passed.
2. **A saved recipe is not a cook-start Plan.** Canonical `CookStart` requires `planId`, never `savedRecipeId`. `PlanRequest` does have `savedRecipeId` with source/intent constraints, but [PlansStore](../server/src/main/kotlin/com/feedme/server/planning/PlansStore.kt) currently rejects that source with `NOT_CONFIGURED`, and the manual meal builder does not create saved-source requests. Opening a save can be implemented now; Cook/Make Mine from that save need a separate authorized saved-source planning slice. Do not cast a SavedRecipe into Plan, reuse an expired origin Plan, or silently substitute catalog quantities for a saved materialized variant.
3. **The queue is not yet configured for cookbook effects.** [SavedRecipeRepository](../shared/kitchen/src/commonMain/kotlin/com/feedme/kitchen/SavedRecipeRepository.kt) implements `download`, `read` and bounded local-title `search` only. [PrivateKitchenSession](../shared/kitchen/src/commonMain/kotlin/com/feedme/kitchen/PrivateKitchenSession.kt) exposes it and the real queue, but its execution gate admits only cooking updates/completion and the explicit create-cooking hook. `saveRecipe` is scheduled as automatic-with-preflight by [CommandPolicy](../shared/sync/src/commonMain/kotlin/com/feedme/sync/CommandPolicy.kt), while `deleteSavedRecipe` requires fresh confirmation. Neither policy is feature permission.
4. **Basic search has no remote sort parameter.** `listSavedRecipes` accepts only `q`, `cursor`, `limit`; canonical `q` is at most 100 characters, cursor at most 2,048, and limit 1–50. Implement basic title search and server ordering. A local sort must say it covers the loaded/downloaded subset; it cannot pretend to globally sort an incompletely paged remote library.
5. **Real authority remains a required composition.** The current server provides [SavedRecipeStore](../server/src/main/kotlin/com/feedme/server/memory/SavedRecipeStore.kt) and six-operation [HTTP ingress](../server/src/main/kotlin/com/feedme/server/http/SavedRecipeHttpRoutes.kt), but requires actual [principal verification and copy authority](../server/src/main/kotlin/com/feedme/server/memory/SavedRecipeAuthority.kt), explicit response/cursor policy and signing keys. A historical Plan/read grant, paid status or successful client button is not a new-copy grant. The progress service does not currently implement these operations; any later preview implementation stays explicitly synthetic and separately tested.

## Exact operation boundary

| Action | Canonical request/result | Client rule |
| --- | --- | --- |
| Save selected app Plan | `saveRecipe`: POST `/v1/saved-recipes`, `SaveRecipeRequest`, original Idempotency-Key; 201 SavedRecipe + ETag | Send the exact selected `planId`; optional validated title. Omit `collectionId` for the server's concrete default cookbook. Omit `markMakeAgain` or send false explicitly. No If-Match. |
| Read one save | `getSavedRecipe`: GET `/v1/saved-recipes/{savedRecipeId}`; 200 SavedRecipe + ETag | Validate exact owned ID, canonical body, integer version/ETag and immutable recipe lineage. A read never finalizes an uncertain command. |
| Enumerate/search | `listSavedRecipes`: GET `/v1/saved-recipes` with exact optional `q/cursor/limit`; 200 SavedRecipePage | `items`, `nextCursor` and `serverTime` are all required; null cursor is terminal. No invented collection ID, ownership field or total count. |
| Delete one private copy | `deleteSavedRecipe`: DELETE `/v1/saved-recipes/{savedRecipeId}`, original key + exact If-Match; 204 with no body | Explicit confirmation bound to selected save/version. Delete the copy and memberships, not its source or another user's copy. Never rebase the original version silently. |

`SaveRecipeRequest` permits plan and/or reviewed-version references; both must agree when supplied. Prefer one exact `planId` from the current retained selection for the first UI integration. Server dedup preserves exact materialized content and first accepted provenance/title; a duplicate with a different explicit title is a conflict, not a rename. The canonical example containing `markMakeAgain: true` is not permission to perform that separate action: the current server explicitly returns unavailable for true.

## Five dependency-ready tasks

### 1. Establish one actual kitchen composition for cooking and cookbook

Owned files: new internal `shared/mealflow/.../MealKitchenComposition.kt`, narrow [CookingFlowController](../shared/mealflow/src/commonMain/kotlin/com/feedme/mealflow/CookingFlowController.kt) and `PrivateKitchenSession.kt` integration; focused composition tests. No new Gradle module or dependency is required: mealflow already uses kitchen/session/sync/contracts.

The cooking controller currently owns a private `PrivateKitchenSession`, whose store/transport wrappers check **that controller's active operation generation** and capture exact queue archive mutations for lost-ACK finalization. Simply exposing this object to an independently running cookbook controller would make its calls fail—or tempt removal of important fences. Extract a small internal retained kitchen composition with explicit operation ownership and feature-specific hooks. It must own exactly one real `PrivateKitchenSession`/`DurableCommandQueue`, pair the actual access/store/boundary/origin, and retain the cooking create/progress/recall/preferences/archive checks. Add a narrow save/delete-only gate and reply hook, default denied when absent; do not turn the create-cook hook into a generic accepting callback.

The internal composition must serialize feature mutation admission while allowing immediate nonmutating Back and synchronous lease redaction. Gate callbacks must not acquire a controller mutex already held across queue dispatch. Closing a borrower does not close the actual session/store or discard either feature's pending commands. Existing cooking lifetime, return-handoff, recall and finalization tests must pass unchanged. Get the exact seam reviewed before changing this shared ownership boundary.

### 2. Add retained Save and exact receipt finalization

Owned files: new `shared/mealflow/.../CookbookController.kt`, `CookbookModels.kt`, `CookbookRecords.kt` and common tests; narrow repository mutation preparation inside `shared/kitchen` with its own tests. Suggested public surface: read-only `states`, `restore`, `saveSelectedPlan`, `retry(commandId)`, `discardUnsent(commandId)`, `open(savedRecipeId)`, `refreshSaved(savedRecipeId)`, `close`. Construction uses the shared kitchen composition from task 1, actual authenticated access, explicit bounds/clock/connectivity and native UUID IDs.

Save captures the currently displayed, acknowledged Plan before suspension, rejects changed/dirty meal selection and known recall, and persists its immutable original operation/key/body/source proof with the queue's `enqueue(..., draftChanges)` atomically. Save is not positive taste feedback and must not alter cooking progress. Offline Save may be a truthful pending request, never “Saved” before the server verifies copy rights. A UI click may authorize one exact attempt; restore/render/Back must not send automatically.

Before accepting a receipt, correlate `commands.intent` with the exact domain command, origin, selected source, body and headers. Bind the 201 response schema/ID/ETag and exact recipe snapshot; retain its actual returned ID, never allocate a local SavedRecipe ID. Use a purpose-fixed repository seam to prepare/validate body, metadata, recall fences and index mutations, then apply those domain mutations together with `commands.applyReceipt`. Because 201 already contains the full SavedRecipe, do not unconditionally require a second GET; explicit download remains available and may be necessary if a future manifest protocol adds a separate bundle. If a GET is used, retain the validated 201 receipt and retry GET/finalization without a second Save POST.

Keep “server receipt retained”, “local bundle stored” and “queue/domain acknowledgement complete” distinct. Before applying, retain exact intended domain/archive evidence for a possible committed-but-unknown ACK. Retry may fresh-ack only the exact original state, never plain readback, a new key, a reduced request or arbitrary APPLIED metadata. Process-local proof loss must be a visible reconciliation gate unless a separately designed durable proof supports it. Canonical Problems after an earlier uncertain attempt never prove noncommit; auth/rights/recall/version failures retain the original command.

### 3. Add owner-scoped paging and honest downloaded search

Owned files: repository paging/cache primitives in `SavedRecipeRepository.kt` (or a tightly scoped sibling), `CookbookController` load/search actions and common/JVM tests. Extend `KitchenContext.fetch` only for the exact read/query signatures needed; it currently admits three fixed path-only reads. Do not add arbitrary URL access or a caller-selected principal.

Bind `SavedRecipePage` before use. Track query and cursor generations; distinguish absent `q` from an explicit empty query because the server cursor binds exact filter scope. Prevent duplicate IDs, repeated cursors, divergent same-version bodies and cross-query/stale-page merge. A changed/expired cursor requires explicit refresh of page one, not continued merging. Keep full saved bodies canonical and route recall/redaction compatibility through the existing repository rather than an independent card cache that can resurrect removed attribution.

Keep page observations separate from “downloaded and locally verified”: list enumeration alone is not automatically durable download. Remote page merging never infers deletion from absence. Local offline search uses the existing index and exact stored bodies, with historical/last-check disclosure and unavailable/corrupt cards. Preserve its current 512-entry **local index bound** as an explicitly handled implementation limit, not a free-tier save quota: remote enumeration and access beyond that bound must remain available. Before accepting another large response or queue intent, reserve actual byte/mutation/index capacity; expose a recoverable cache-capacity state instead of a permanently unfinalizable successful Save. Coordinate the explicit client response profile with `SavedRecipeServicePolicy.maxResponseBytes` (up to 262,144), page envelope and the queue's bounded atomic batch.

Default cookbook grouping can be represented by `listSavedRecipes` without guessing a collection ID. If basic collection reading is included, implement canonical `listCollections` and `getCollection` as a separate bounded read subtask, preserving `nextItemCursor` absent/null/value semantics and same-version item traversal. Do not enable custom creation, membership editing, manual ordering, paywalls or paid filters in this slice.

### 4. Add explicitly confirmed delete and local nonresurrection fence

Owned files: cookbook controller/records, narrow saved repository receipt/tombstone primitives and common/JVM tests. Proposed actions: `prepareDelete(savedRecipeId)`, `confirmDelete(exactTicket)`, original-command `retry`, and never-attempted discard. The ticket binds actual owner/generation, save ID, version/ETag and current displayed snapshot; dismissal, account change or later version invalidates it.

Persist a pending-delete intent and original empty-body DELETE/key/If-Match atomically in the same queue. Reflect pending removal immediately without claiming server deletion or erasing the original retry evidence. Dispatch through `dispatchConfirmed` under the existing fresh-confirmation policy; 412/409 is a visible conflict, not permission to fetch a newer ETag and resend the old confirmation.

After exact 204, atomically archive the command, remove this saved copy's local body/metadata/index membership and write an ID-scoped tombstone/revision fence. Stale downloads and list responses captured before deletion must fail CAS/checks instead of resurrecting it. Keep recipe-version recall markers and independent authorized cooking/other-save records; no recipe-version-wide purge. Server re-save after deletion produces a new SavedRecipe identity/generation and must not be blocked merely because its recipe version matches an old tombstone. An old Save or Delete receipt that now conflicts with newer lifecycle state stays unresolved, never recreated locally as success.

A 404 or omission from a page alone is not an acknowledged original DELETE. Bound local cleanup to exact owned records; do not sweep namespaces, collections, media, source grants, memory or unrelated pending commands. A lost apply ACK needs the same exact fresh-finalization discipline as task 2. Explicit unsent discard must not bypass retained finalization evidence.

Bind Save to the exact acknowledged selected Plan; preserve meal form and active cooking state when opening the cookbook. Show pending/server-receipt/download/finalization/unavailable states with explicit retry/discard availability. Search/Back/rotation never submit or erase. A saved detail can read offline; Cook/Make Mine remains precisely unavailable until the saved-source planning gap above is implemented. `MEAL_DONE.01` is explicitly **Make again**, not an alias for basic Save; leave it separate and unavailable rather than relabeling or silently sending `markMakeAgain: true`.

## Decisions and release gates

Engineering can implement the five bounded tasks without inventing provider choices or asking the user to select every DTO field. Required owner decisions before live enablement remain actual verifier/copy-rights/catalog/reviewer integrations, manifest protocol, response/cache policy and source-lifecycle/recall handling. Basic Save/read/search/delete must not depend on a paid organization purchase. The current server deliberately fails a page containing a recalled denied item until audited per-item lifecycle integration exists; the client must show a truthful unavailable/error state, not silently synthesize safe cards.

F30 social-copy entry, existing-copy attribution lifecycle, saved-source cooking/adaptation, basic collection reading not yet composed, F49 export/deletion integration and the missing manifest remain explicit follow-on work. F45 custom organization, F33 Tonight, paid packs, Save-as-feedback, Make Again, source media and sharing are not added by this plan. The 44-feature V1 scope is unchanged; this handoff prepares a real next vertical slice rather than claiming the whole feature is finished.
