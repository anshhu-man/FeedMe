# F20 — Use It Again

Phase: optional extension after the first dinner loop; no weekly planner required. Owner modules: planning, catalog.

## Strategy

Help one ingredient or a deliberately prepared portion support another meal with little additional thought. Offer one next use after the immediate meal decision. Reuse is optional and must disclose additional preparation; it must never infer freshness, storage safety or expiry from the ingredient's age, a photograph or a previous cooking event.

## Experience and screen design

RECIPE and MEAL_DONE can expose “Another use for this?” after the user has selected today's meal. REUSE displays one follow-on idea with the shared ingredient, what additional work it requires now, and what is needed later. Actions are Save next idea, Make this now and No thanks. If extra preparation changes tonight's recipe, show the reviewed quantity/step variant and ask the user to choose it explicitly. Saving creates a private recipe save, not a reminder or scheduled obligation. The later meal rechecks ingredients and current effort before cooking.

## Production sequence

1. Start from the chosen recipe version and user-selected ingredient or portion, not an inferred remaining quantity.
2. Retrieve reviewed reuse relationships and follow-on recipes compatible with current hard exclusions.
3. Show additional current work and later missing essentials separately.
4. If the user opts to prepare more now, select a reviewed portion/step variant within supported serving bounds and revalidate effort.
5. Save or start the follow-on recipe only through explicit actions. On later reopening, create a fresh plan snapshot and reconfirm availability.

## Data and API contracts

createReuseOptions: POST /v1/reuse-options with Idempotency-Key. ReuseRequest contains ingredientIds, complete constraints and optional preparedPortionPlanId. Include the prepared-portion reference only after the user explicitly reports that portion; it is not inferred from completing a meal.

    {"ingredientIds":["00000000-0000-4000-8000-000000000011"],"constraints":{"ingredientIds":["00000000-0000-4000-8000-000000000011"],"energy":"assemble","equipmentIds":["bowl","knife"],"servings":1,"hardExcludedIngredientIds":[],"maxTotalMinutes":10}}

Return ReuseOptionPage containing recipeVersionId, title, extraPreparationMinutes and sharedIngredientIds. Fetch the referenced RecipeVersion to show later ingredients and reviewed instructions; do not expect undeclared full-recipe fields in the option. The client's No extra work choice rejects options with extraPreparationMinutes greater than zero; no rejected option changes today's plan. A reported portion is not a storage certification. Internal reuse relationships pin source/follow-on versions. Saving uses F19 saveRecipe; starting later uses createPlan with savedRecipeId and intent=tonight. Unknown remaining amount requires confirmation and cannot trigger pantry decrement or invented scaling.

## Permissions and lifecycle

Reuse suggestions are private unless the user shares a chosen meal. No household member or friend sees presumed leftovers. A saved follow-on recipe follows its source grant and catalog rights; saving a linked suggestion does not copy the source story. Dismissing an idea leaves no task, streak or missed-day notification. The feature does not introduce a background expiry monitor.

## Failure and offline behavior

If no reviewed follow-on relationship exists, omit the invitation or show No supported next idea; do not generate a storage claim. Offline display is limited to complete cached linked recipes. If a follow-on version is retired, existing authorized saves remain subject to normal lifecycle; a recall blocks use. Conflicting current effort after extra-portion selection returns a tradeoff choice and retains the original current meal. No partial failure may silently change tonight's quantity.

## Integration and dependencies

F03 rough pantry, F05 effort, F13 versioned content, F19 saves and F33 Tonight support this feature. F51 reviewers must approve any scaling or handling notes. F41 notifications remain opt-in and are not created by saving here.

## Execution plan

- Model reviewed reuse relationships and supported portion variants.
- Implement read-only proposal plus explicit current-plan adaptation boundaries.
- Build REUSE with now/later effort separation and no-obligation dismissal.
- Emit reuse_option_viewed, reuse_saved and extra_prep_accepted; do not claim measured waste reduction from these events.

## Acceptance and release gates

Test unknown leftover quantity, declined extra work, reopened saved meal with missing ingredients, hard exclusion change, unsupported scaling and an offline stale follow-on. Confirm no reminders or pantry mutations occur without their own action. Validate usefulness through actual user reports of reuse, not saves alone. Gate reuse_suggestions by reviewed relationship set and disable invitations without removing existing cookbook entries.
