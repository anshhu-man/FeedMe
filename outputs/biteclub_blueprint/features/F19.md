# F19 — Private Cookbook

Phase: first release basic access; enhanced organization is F45. Owner modules: catalog, memory; commerce checks optional tools.

## Strategy

Keep useful recipes accessible after their moment in the social feed has passed. A cookbook entry is an explicitly authorized private immutable recipe copy, not a cache of someone else's story. Basic saving, opening, searching and removing recipes remain available without a paid library upgrade.

## Experience and screen design

COOKBOOK shows saved recipe cards with title, effort, provenance and a readable unavailable state. Basic search and simple sort help retrieve a meal; opening a card goes to RECIPE with Cook, Make Mine and Remove save. Empty state points to Help me make something without requiring friends. COLLECTION displays a selected grouping; custom organization is enabled through F45. A recipe saved from Today explains that its instructions can remain after the story leaves Today, but its original photo/replies are not part of the copy. Removing a save is explicit and offers to manage related memory separately.

## Production sequence

1. Verify catalog access or validate the current recipe-save grant against source version and viewer authorization.
2. In a transaction create a recipe-only immutable snapshot, attribution permitted by policy and a default-collection membership; deduplicate by principal/source version.
3. Return the stable savedRecipeId and content manifest. Client downloads the full bundle for offline reading.
4. Process source updates: future grant revocation does not remove established copies; identity deletion anonymizes attribution where required; safety/legal recall blocks affected content.
5. Removing a private save deletes its memberships and local content when no other authorized local reference needs it.

## Data and API contracts

GET /v1/saved-recipes lists owned saves with cursor; POST /v1/saved-recipes creates an authorized app-recipe save from planId or recipeVersionId with Idempotency-Key. GET /v1/saved-recipes/{savedRecipeId} reads private content. DELETE /v1/saved-recipes/{savedRecipeId} removes that owned private copy and its memberships with If-Match. GET /v1/collections lists groupings and GET /v1/collections/{collectionId} reads one collection with paged items. POST /v1/collections/{collectionId}/items attaches an existing savedRecipeId with Idempotency-Key and never creates source rights. POST /v1/posts/{postId}/recipe-saves creates a new social copy after locking the source attachment's save policy and atomically writes its membership. DELETE /v1/collections/{collectionId}/items/{savedRecipeId} removes that membership only; the recipe remains in the default cookbook unless the user separately removes the private copy. A default collection is a concrete owner-scoped ID, not a globally shared resource.

Internal saved-copy records track owner, immutable content/hash, source version/grant, authorization time, permitted attribution and recall state. The canonical SavedRecipe response maps these to id/version, snapshot, sourceType, optional sourcePostId/grantId/creatorLabel, recalled and contentLicense. Do not include sourceMediaId, comment bodies or private source-profile fields. Immutable recipe content is separate from mutable attribution/availability metadata. Use typed save-denied/recall outcomes; duplicate replay returns the established resource rather than a second copy.

## Permissions and lifecycle

Every read checks ownership; an ID or cached public URL is insufficient. Recipe copies are private by default and not automatically publishable; reposting needs the applicable recipe-sharing rights. F30 defines future revocation and existing-copy persistence. A purchase lapse cannot erase or lock ordinary access to established saves. Account deletion removes copies and memberships; source-author deletion affects attribution and content only under the defined grant/recall rules.

## Failure and offline behavior

Show downloaded status only after hash-checked complete content is stored. Offline search covers local metadata, and cooking uses only complete authorized bundles. Newly requested community saves remain pending until the server verifies the grant. Sync conflicts reconcile membership separately from immutable content, preventing duplicate copies. A received recall immediately marks the local entry unavailable and invalidates cooking; offline recall propagation has the limits documented in F13.

## Integration and dependencies

F14 creates repeat favorites, F30 controls copying, F13 manages versions/recalls and F45 adds organization. F33 Tonight later starts from an existing save. F49 export/deletion and F53 offline routing cover lifecycle details.

## Execution plan

- Implement save authorization, snapshot transaction and owner-scoped read/search.
- Build COOKBOOK cards, search, unavailable and delete states.
- Add atomic bundle downloads, deduplication and recall invalidation.
- Emit recipe_saved, cookbook_open_failed and saved_content_recalled without source social content.

## Acceptance and release gates

Test source story expiration, future grant revocation, source identity deletion, unauthorized IDs, paid downgrade, duplicate saves, offline bundle corruption and legal/safety recall. Assert snapshots contain no copied media/comments. Release only after F30 race tests pass; a save-write kill switch preserves existing readable recipes and deletion controls.
