# F22 — My Plate

## Strategy
My Plate gives a person a lasting collection of the food posts they deliberately keep. It is a social profile surface, distinct from the private recipe cookbook. Keeping a post is optional and does not change who can see it. Ship alongside Today; measure intentional retention and subsequent recipe actions rather than follower growth.

## Experience and screen design
`PROFILE_PLATE` contains an owner header, accessible grid/list toggle, and kept posts sorted by original publication time. Owners see “Only you” or the selected circles on each post; another person sees only authorized entries. `POST` displays the retained post and its attachment. An owner overflow action toggles “Keep on My Plate,” explains what removal does, and links to `AUDIENCE` or `DELETE_POST`. A post can remain in Today after being removed from Plate until its story expires. The UI must state that result explicitly.

## Production sequence
Profile opening calls `GET /v1/profiles/{userId}/plate`. Retaining or unretaining a published post calls `PATCH /v1/posts/{postId}` with `{keepOnPlate}` and `If-Match`. The service locks the post, validates ownership and status, updates its version, and writes `post.retention_changed` to the outbox. The response returns both placements and server time; the UI immediately renders the server result. Concurrent audience and retention edits receive `412 VERSION_CONFLICT` with the current safe representation for reconciliation.

## Data and API contracts
Use the canonical Post record from F21, plus `retentionChangedAt`. `keepOnPlate` is boolean and cannot resurrect `DELETED` content. Plate inclusion requires `keepOnPlate = true` and `status = PUBLISHED`; Today expiry is irrelevant to this predicate. A GET with `placement=plate` cannot be used to read a nonretained expired story. Collection queries use stable pagination and current authorization on every page. An owner can manage expired posts using an owner-only management representation; that representation does not issue viewer media rights.

## Permissions and lifecycle
Retaining a post preserves its existing audience; it never widens it. Current circle membership and block rules continue to apply even to old posts. Removing retention ends Plate access at commit; if Today has also expired, ordinary viewer access ends entirely. Existing authorized recipe copies remain private and usable under F30. Removing a retained post is not account deletion or recall of recipe grants. Before deletion, `DELETE_POST` explains media removal and recipe-copy persistence.

## Failure and offline behavior
An offline toggle may be stored as a local pending intention but must not claim that remote visibility changed. Privacy-reducing actions show “Waiting to update visibility” until acknowledged. When returning online, refetch the current version before applying; conflicting edits require an explicit choice, not last-write-wins. Clear cached private media access on logout, audience invalidation, and post removal.

## Integration and dependencies
Consumes publication, deletion, audience, membership, and block invalidations. The profile module supplies display identity but cannot infer permission from a profile visit. F19 owns personal recipe organization, and F30 defines why a saved recipe can survive disappearance from Plate.

## Execution plan
Implement placement predicates and owner management reads, then the retention mutation and explanatory UI. Add concurrent-edit recovery and test cross-device invalidation. Track retention update failures and stale-profile removals using IDs without captions or recipe text.

## Acceptance and release gates
Verify four states: Today only, Today plus Plate, expired but on Plate, and expired with no Plate. Test retention during expiry, deletion racing retention, blocked viewers with cached grids, and recipe copies surviving removal. `social.plate.enabled` can suppress profile discovery; owners retain deletion and privacy controls through `SETTINGS`.
