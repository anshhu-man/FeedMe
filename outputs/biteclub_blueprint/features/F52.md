# F52 — Moderation operations

## Strategy
Invited-circle sharing still needs operational safety, user reporting and appeals. Make cases resolvable by a small trained team before expanding audience or media formats. Queue capacity and reviewer coverage are launch gates, not future assumptions.

## Experience and screen design
Members submit REPORT from post/story/message/tip/member context and receive a private receipt through SUPPORT. ADMIN_REPORTS shows role-scoped priority queues and claim state. ADMIN_CASE shows minimized evidence, rule mapping, action history and separate appeals. STAFF action labels include Remove content, Dismiss, Restrict account and Review appeal with required reasons. ADMIN_AUDIT records both data access and decisions.

## Production sequence
Create a case from a server-resolved target and minimal immutable evidence snapshot. Protect reporter identity, classify urgency and queue via outbox. An authorized moderator claims a case using a lease/revision. An action checks target current state and actor role, records decision and audit in the same transaction, tombstones or restricts where appropriate, and emits delivery-revocation/notification jobs. Appeals are assigned to a different reviewer; evidence and past decisions remain auditable.

## Data and API contracts
Reports, report_evidence references, case_assignments, moderation_actions, account_restrictions, appeals and audit entries. Member `/v1/reports` and support routes expose only safe receipt/status fields. Staff `/v1/admin/reports/{reportId}/claim`, actions, appeals and account restrictions are role-scoped commands with target revision and reason. Media jobs consume moderation status and cannot publish quarantined/rejected assets.

## Permissions and lifecycle
Block is a user safety preference and does not require a moderation verdict. Content removal does not expose the reporter. Evidence access requires a recorded purpose; raw media lives in a separate staff-authorized location and follows approved retention. Sensitive/high-impact cases need specialist escalation and configured second approval. The service must not promise a particular outcome merely because a report was accepted.

## Failure and offline behavior
Lost report responses reuse the local report command UUID as the `Idempotency-Key` header to avoid duplicate cases. `ReportWrite` has no `clientReportId` body field; unknown payload fields are rejected. Evidence capture failure marks case incomplete and retains traceable target references; it does not claim evidence was preserved. Moderation outages pause new publication if review backlogs exceed configured risk gates. Existing user block controls stay available. Staff conflicts return the current assignment/decision and require refresh rather than silently overriding.

## Integration and dependencies
F42 supplies member controls; media/social readers enforce restrictions; conversations recheck blocks and membership before sends; notification workers reauthorize immediately before delivery. F49 defines evidence-retention exceptions and F54 queue/incidents. Current app-store UGC requirements are verified in the source register; policy owner approves the final community rules and escalation coverage.

## Execution plan
Write operational policy and severity matrix, staff permissions, evidence retention, on-call escalation and appeal runbooks. Implement report intake, queue lease, staff evidence view, transactional actions and revocation events. Add synthetic abuse/copy/share scenarios and red-team cross-circle leakage. Run staffed pilot before opening general invitations.

## Acceptance and release gates
Verify reporters cannot read other cases, targets cannot identify reporter through API or notifications, removed private media cannot get new URLs, and duplicate staff actions are idempotent. Test moderator conflict, appeal separation, restricted-user login and delayed media jobs. Proposed queue SLA is policy-specific and must match real staffing; breach pauses growth/media flags rather than silently accumulating unsafe work.
