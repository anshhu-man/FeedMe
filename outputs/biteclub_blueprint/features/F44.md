# F44 — Household Preferences

Phase: later optional paid capability; validate shared planning before monetization. Owner module: commerce for membership/access; profile and planning for private constraint composition.

## Strategy

Help people who actually share meals reuse household equipment and serving defaults while respecting each participant's own food requirements. Household membership is explicit and separate from a social circle or a platform store family. A purchase grants the configured household capability and explicit seats; it does not imply unverified cross-store family-sharing behavior.

## Experience and screen design

HOUSEHOLDS shows the selected household, membership role, access state and actions to create, open Members or edit shared defaults. HOUSEHOLD_MEMBER lists names/roles, pending invitations, Remove member and Leave household where allowed. Invitations use the native share sheet only after the user chooses to share; the recipient must accept. HOUSEHOLD_PREFS contains shared equipment and serving defaults plus a private “My requirements for household meals” consent section. Other members see only whether meal input is ready, not someone's exclusions or reasons. REQUEST identifies the selected household and participants; the result reports compatibility generically. PAYWALL explains exactly which shared tools require purchase, while individual meal help remains available.

## Production sequence

1. Verify server entitlement and account identity before creating a household and owner membership atomically.
2. Create scoped expiring invitations; accept under a membership/seat lock, validating token, inviter role, entitlement and existing membership.
3. Each member explicitly supplies or permits use of meal-relevant requirements. Shared defaults and private member settings receive independent revisions.
4. Planning snapshots selected participants, current membership, consented exclusions, household equipment and supported servings; hard requirements are combined server-side before matching.
5. Removal, leaving, entitlement changes and household deletion invalidate future shared-plan access through transactional outbox events. Existing private recipes and active individual cook sessions remain governed by their own rights.

## Data and API contracts

GET/POST /v1/households list/create; GET /v1/households/{householdId} reads authorized detail. POST /v1/invitations creates a targetType=household, targetId-scoped token; POST /v1/invitations/accept accepts it idempotently after checking seat capacity. DELETE /v1/households/{householdId}/members/{userId} removes a member or lets that member leave. GET /v1/households/{householdId}/kitchen reads shared equipment/serving defaults; PATCH /v1/households/{householdId}/preferences updates those owner-authorized defaults with If-Match. PATCH /v1/households/{householdId}/preferences/me updates only the caller's private requirements/consent. DELETE /v1/households/{householdId} is an explicit owner-confirmed dissolve action. No household read may expose another member's private requirement values; the planning service composes them through an internal authorized port.

Internal household records track the owner, entitlement source, role-scoped memberships and independently versioned defaults/consent; Household and HouseholdKitchen transport representations expose only authorized fields. Personal member requirements are separately protected rows. Invitations store token hashes, expiry, intended role and use state. Mutations require idempotency and ETags. Serving counts outside reviewed recipe bounds return noMatch.

## Permissions and lifecycle

Only the owner may edit shared defaults or invite a member in the initial household role model; invite acceptance cannot elevate the requested role. A member can withdraw their own requirements consent at any time. An owner must dissolve explicitly rather than leave an orphaned household; ownership transfer is deferred until its consent workflow is designed. Dissolving deletes household context but not personal memories/cookbooks. Expired paid access freezes new premium shared planning and membership expansion, leaves necessary management/removal/read access available, and never blocks individual cooking. Refund and access policy must be disclosed in the offering.

## Failure and offline behavior

Shared planning requires current membership/consent validation online; cached household names and defaults may be read offline but cannot authorize access. Private requirement edits are queued and suppress affected local planning until validated. Concurrent final-seat joins serialize; one receives SEAT_LIMIT_REACHED. A removed member's old deep link returns UNAVAILABLE, without revealing the current roster. Active cooking retains its pinned authorized recipe unless separately recalled.

## Acceptance and release gates

Test two final-seat acceptances, expired invite, withdrawn consent, owner dissolution, member removal mid-request, entitlement lapse, unsupported servings and cross-household IDs. Verify no result reveals which person caused a specific exclusion. Release household_planning to invited pilot groups only after access and consent tests pass; disable new group plans independently of personal cooking and membership cleanup.
