# F16 — Taste and Effort Memory

Phase: first release. Owner module: memory; planning consumes a read model.

## Strategy

Remember reliable meals and the specific qualities a person explicitly enjoyed or found manageable. Personalization should make a similar evening easier, with no obligation to log meals. It is a transparent soft ranking layer over feasible reviewed recipes, never a mechanism for inferring medical needs or silently changing food exclusions.

## Experience and screen design

MEMORY lists short readable entries grouped by meals, tastes and effort, such as “You liked this combination” or “You said chopping was too much.” Each entry opens MEMORY_DETAIL with its source feedback, scope, effect and edit/forget actions. RECOMMENDATIONS can show a short returning reason with a link to that detail. Recently saved Echoes appear in COOKBOOK, but memory entries and saved content remain distinct. The app welcomes a return after a gap without catch-up prompts or presumed deterioration in habits.

## Production sequence

1. Consume committed explicit feedback/save events from the transactional outbox.
2. Deduplicate by event ID and apply a versioned deterministic rule to the explicitly selected target.
3. Maintain a materialized memory with source links, current effect and projection version.
4. Planning filters hard constraints first, then uses matching contextual memories to rank feasible candidates.
5. Retraction or editing triggers recomputation from remaining authorized sources and invalidates the principal's recommendation cache.

## Data and API contracts

GET /v1/memories returns a paged owner-only list. GET /v1/memories/{memoryId} returns detail. Canonical Memory fields include id, version, kind, label, value, sourceFeedbackIds, enabled and timestamps, with inspectable context matching the editable MemoryContext contract. Rule version and per-source contributions remain internal auditable records. A complete base Memory example is:

    {"id":"00000000-0000-4000-8000-000000000061","version":4,"createdAt":"2026-09-13T10:00:00Z","updatedAt":"2026-09-13T10:05:00Z","kind":"taste","label":"You enjoyed a crunchy addition","value":"prefer:crunch","sourceFeedbackIds":["00000000-0000-4000-8000-000000000062"],"enabled":true}

Avoid pseudo-precise confidence scores in the UI. Effects are understandable rules such as prefer or show_less, bounded by recipe/context. An ingredient_unavailable plan event never becomes a dislike. Directly inferred signals from scrolling, missed days or another person's reactions are not inputs. Internal memory_updated events include opaque IDs and revision, not raw dietary text.

## Permissions and lifecycle

Memories are private and exportable. Guest memories stay local/bounded until an explicit account merge; duplicates are reconciled by source identity, not overwritten wholesale. Users may disable personalization while keeping their cookbook and feedback. Forgetting must remove the ranking contribution and prevent the same source from recreating it during projection rebuild. Source suppression/deletion semantics are specified in F18 and implemented consistently with account deletion.

## Failure and offline behavior

If projection is delayed, show current saved feedback with Personalization pending; recommendations fall back to unpersonalized feasible ranking. Offline devices can show cached memories, queue edits and conservatively stop applying a locally forgotten effect immediately. Reconnection resolves revisions before merging preferences. Historical plans retain their decision snapshot for explanation but must not claim a deleted memory is still active.

## Integration and dependencies

F14/F15 are explicit sources, F17 explains use, F18 edits, F04 owns separate hard exclusions and F19 owns recipe content. Planning must support personalization_enabled=false without disabling meal help. F49 deletion removes both source events and derived records according to the retention contract.

## Execution plan

- Define memory rule table, source provenance and deduplicated projection consumer.
- Add rebuild/retract paths plus cache invalidation.
- Build MEMORY/MEMORY_DETAIL from human-readable templates.
- Emit memory_projection_lag, memory_rule_error and recommendation_memory_applied using opaque target IDs only where justified.

## Acceptance and release gates

Test replayed events, withdrawn feedback, duplicate guest/account merge, forget followed by projection rebuild, no-feedback users and an explicit energy choice contradicting old memory. Hard constraints always win. Run deterministic ranking fixtures with personalization on and off. Release personalization behind a separate flag; rollback disables ranking effects while retaining inspectable, editable user data.
