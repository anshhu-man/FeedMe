# F04 — Food Preferences

Phase: first release. Owner modules: profile, planning.

## Strategy

Remember how someone wants to eat so each request begins closer to a useful answer. Separate hard food exclusions from soft likes and dislikes. Matching may honor declared exclusions, but the product must not claim that a filtered recipe guarantees allergy safety or individualized medical suitability.

## Experience and screen design

FOOD_PREFS is available from PROFILE_SETUP, SETTINGS and ADAPT. It has explicit sections for Exclude ingredients, Eating preferences and Taste dislikes, with a reviewable summary and Save. Ingredient selection uses a controlled vocabulary and clearly asks whether a choice must be excluded or is simply disliked. Prefer familiar labels over medical questionnaires. Applying a preset previews its ingredient exclusions before confirmation. Existing plans show “Preferences changed—check this meal” if their snapshot is stale. Guest users can set the same constraints without creating an account.

## Production sequence

1. Retrieve preference values and their revision.
2. Validate ingredient references and normalize alias/component relationships without expanding preferences beyond what the person chose.
3. Save all changes atomically, increment revision, and append a preference_changed outbox event.
4. Invalidate eligible-candidate caches for that principal. Recheck an old plan before a new cook session starts.
5. Apply exclusion closure before substitutions and ranking; a soft dislike can lower rank but cannot become a hidden prohibition.

## Data and API contracts

readPreferences: GET /v1/preferences returns revision and editable fields. updatePreferences: PATCH /v1/preferences with If-Match and Idempotency-Key.

    {"hardExcludedIngredientIds":["00000000-0000-4000-8000-000000000011"],"dietaryPatterns":["vegetarian"],"dislikedIngredientIds":["00000000-0000-4000-8000-000000000012"]}

Return the normalized selection, revision and any preset expansion requiring confirmation. Persist source=user_explicit, changedAt and scope=personal; memory-inferred preferences use separate records and cannot alter hard exclusions. Plan constraint snapshots include the effective exclusions revision and an ingredient-taxonomy version. Invalid references return 422; concurrent writes return 412 with a current summary. Interpretation output conflicting with a hard exclusion returns a field clarification, not a relaxed plan.

## Permissions and lifecycle

Only the account owner or current guest can read/edit personal preferences. Social APIs cannot return them in post payloads. Household matching later receives consented meal-relevant requirements through F44; it cannot mutate an individual's record. Deleting a learned preference never deletes a hard exclusion. Removing an explicit exclusion requires its own visible Save action and is immediately reflected in subsequent snapshots.

## Failure and offline behavior

Preference edits can be drafted offline, but new server plans must carry the latest locally explicit exclusions for validation. Until sync resolves, show Pending sync and never use an older permissive snapshot as a substitute. A failed save preserves the draft. If a recipe's component mapping is unknown, return constraint_unverifiable rather than asserting compliance. A locally cached active cooking session displays changed exclusions prominently without silently rewriting steps mid-cook.

## Integration and dependencies

F13 owns taxonomy and recipe composition; F01/F02/F08/F10 must apply the same shared constraint evaluator. F16 memory only supplies soft ranking signals. F39 covers privacy presentation; F49 deletion/export owns retention and access requests.

## Execution plan

- Create versioned preference schema and normalized ingredient closure tests.
- Build FOOD_PREFS selection/review interactions and accessible removal controls.
- Add cache invalidation plus pre-session revalidation.
- Instrument preference_save_failed and plan_exclusion_rejection by generic reason code only.

## Acceptance and release gates

Test allergens represented through compound ingredients, a substitute introducing an exclusion, preset changes, concurrent edits, offline stricter exclusions, and a language request to ignore existing exclusions. Confirm personal preferences never appear in social traces or public errors. Gate production on reviewed taxonomy coverage for the launch catalog. If preference matching is compromised, fail closed for affected recipes and disable new plans through a safety flag while preserving editable settings.
