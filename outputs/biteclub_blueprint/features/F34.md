# F34 — Dinner Pact

## Strategy
Dinner Pact lets a few friends commit to making a shared dish or theme, each in a way that fits their kitchen. It is an asynchronous coordination feature, not a compulsory live session. Acceptance, personal adaptation, and sharing a result are separate actions. The later release should support a proposed maximum of eight participants per pact.

## Experience and screen design
`PACT_CREATE` collects a title, eligible recipe or theme, selected circle members, intended date/time, and RSVP deadline. The preview identifies recipients before Send. `PACT_DETAIL` shows accepted participants, status, shared recipe context, and “Make my version,” “I’m cooking,” or “Leave.” The participant’s ingredients, exclusions, portions, and effort adjustments remain private in `ADAPT`/`TONIGHT`. “Share my result” opens `CAPTURE` voluntarily. Nobody is marked late or assigned a public completion score.

## Production sequence
`POST /v1/pacts` creates the host, participant invitations, and `pact.created` in one transaction after recipient checks. `POST /v1/pacts/{pactId}/participation` uses `decision=join|decline|leave`, optional owned `planId`, and `acknowledgedScheduleVersion`; a row lock and server deadline govern acceptance. Joining creates one participant and `pact.participant_joined`. `PATCH /v1/pacts/{pactId}` changes the host’s schedule with `If-Match`; a new schedule version requires reconfirmation while preserving private plans. `DELETE /v1/pacts/{pactId}` cancels the pact. Scheduled closure marks it completed or expired once. Responses update `PACT_DETAIL` from authoritative state.

## Data and API contracts
`Pact(id,hostId,circleId,title,recipeReference,scheduledAt,timeZone,rsvpDeadline,closesAt,state,version)` uses `OPEN`, `ACTIVE`, `COMPLETED`, `CANCELLED`, `EXPIRED`. `PactParticipant(pactId,userId,state,acceptedVersion,privatePlanId)` is unique per pair; `privatePlanId` is never serialized to other participants. Invitations consume capacity only on acceptance, with an atomic capacity check. The host is an active participant and cannot leave without cancelling in this scope. `GET /v1/pacts/{pactId}` provides permission-filtered details. Durable actions use idempotency keys and typed `PACT_CLOSED`, `CAPACITY_REACHED`, `INVITATION_UNAVAILABLE`, or `RECONFIRM_REQUIRED` responses.

## Permissions and lifecycle
Invitees must be current, unblocked members of the selected circle and have coordination invitations enabled. Pending invitees receive only the invitation preview; active participants receive the roster. A source recipe must be independently accessible to each participant or be explicitly attachable under F24; joining does not grant source-media access. Circle departure or blocking prevents further shared interaction and removes that participant from current roster visibility. Private authorized recipe copies and personal plans survive pact cancellation. The shared pact closes at the host-selected deadline, default twelve hours after its scheduled time.

## Failure and offline behavior
Accept and leave require acknowledgement; offline intentions remain pending. A stale acceptance after a host edit must show the new details and request reconfirmation. Duplicate requests return the same participation, not an extra seat. Late push notifications deep-link to a closed receipt. Failed adaptation does not undo acceptance; offer a different eligible personal version or leaving. The app never starts a camera, call, or message automatically.

## Integration and dependencies
Circles, F01 adaptation, F33 Tonight, F40 audience enforcement, F41 notification controls, and F42 blocks. Source and personal variants use separate authorization scopes throughout analytics and responses.

## Execution plan
Build lifecycle and roster transactions; implement host preview and invite response UI; integrate private personal plans and optional results; add expiry, cancellation, and notification coalescing. Measure RSVP conflict and stale-notification rates as operational signals.

## Acceptance and release gates
Test concurrent final-seat acceptance, host edit/accept races, duplicate invitations, changed time zones, departure, blocks, and cancelled pacts with existing personal recipes. `coordination.pacts.enabled` stops new pacts/invitations but retains decline, leave, and cancel. Release requires no participant access to another person’s private adaptation or dietary settings.
