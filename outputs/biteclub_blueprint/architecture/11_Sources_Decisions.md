These support feasibility and provider behavior; architecture, budgets, retention periods, feature limits and targets are FeedMe proposals unless explicitly labelled provider facts. Version numbers in example URLs are documentation versions, not dependency pins for a production release.

## Architecture decision records

| ADR | Proposed decision and reason | Tradeoff / review trigger |
|---|---|---|
| ADR-01 | Android+iOS share Kotlin domain, networking, persistence and Compose UI; native adapters handle OS integrations. Explicit user platform choice. | Shared UI still needs native accessibility/camera/purchases testing. If a specific screen fails required UX, keep its domain shared and implement that screen natively. |
| ADR-02 | Ktor modular monolith and one PostgreSQL cluster initially, with API/worker deployables. | Easier cross-feature transactions and smaller ops burden; isolate a module into a service only after measurable scaling/ownership pressure. |
| ADR-03 | Managed Cognito identity, no proprietary password store. | Multiple native/browser flows demand adapter tests and provider configuration. Revisit provider if selected launch region, auth UX or identity migration requirements cannot be met. |
| ADR-04 | PostgreSQL transactions + outbox + at-least-once workers. | Adds inbox/retention/replay machinery; avoids assuming a network call commits atomically with database state. |
| ADR-05 | Deterministic reviewed-catalog matching; model optional for structured intent interpretation. | Catalog/reviewer effort limits initial breadth. A no-match explanation is preferable to an unsupported claimed recipe transformation. |
| ADR-06 | Two post placements: Today expires after 24h, Keep on Plate persists under same audience. | Separate expiry and content deletion predicates increase query complexity but make the promised social behavior explicit. |
| ADR-07 | Quarantine uploads and sanitized private derivatives, 60s signed access. | Short TTL creates reauthorization traffic; bearer URL residual access remains. Stronger per-request edge authorization can be evaluated if threat model requires less residual exposure. |
| ADR-08 | Recipe-only private copy grants, distinct from media and redistribution licenses. | Deletion and source-rights handling is more nuanced; legal/account-erasure cases can recall copies. Screen disclosures and stored proof are mandatory. |
| ADR-09 | Server-stamped audience membership generation. | Leaving/rejoining does not silently restore historical creator audience grants; republishing/rebinding must be explicit. Adds a generation predicate to each authorization check. |
| ADR-10 | Small invited circles before any public discovery. | Useful initial social loop without a global feed; discovery/creator monetization require separate product, safety and scaling designs. |
| ADR-11 | RevenueCat adapter plus server-authoritative entitlements for optional paid tools. | Requires webhook/provider reconciliation, commercial plan and restore policy. Product prices/SKUs remain unconfigured. |
| ADR-12 | Household server matching uses member-consented inputs but exposes only own fields and neutral group compatibility. | Fewer explanations about why another person's restriction blocked a meal; privacy wins over convenient member-level inspection. |
| ADR-13 | Existing basic saved recipes remain readable after paid expiry. | Revenue focuses on organization/tools, household benefits and new reviewed packs rather than locking previously accessible personal meals. |
| ADR-14 | No automatic posting, message sending, shopping purchase or social invitation from inferred intent. | A final explicit action is necessary for remote social/purchase effects; this is part of product control, not an extra engineering approval dialog. |
| ADR-15 | Proposed adult invite-only pilot with configurable eligibility and country gate. | Does not settle age assurance, regional law or app-store category; named launch owner must finalize before opening access. |

## Decisions intentionally not invented

The implementation can begin with these contracts while the following inputs remain clear release gates: launch country and supported languages; legal operator and verified FeedMe name/trademark availability; qualified content reviewers and review throughput; applicable age eligibility/assurance; ownership/licensing of recipe text and media; configured AWS/provider accounts and region; selected Kotlin/Compose/Gradle/Xcode/SDK compatibility matrix; exact supported OS versions; store product IDs, prices, restore/transfer policy and household seat offering; analytics consent/retention and data residency; actual on-call/moderation coverage. No external deployment, third-party message, cloud spend or store submission is authorized merely because a plan includes it.

The initial Smart Kitchen discussion supplied conceptual direction (preferences, ingredient reuse and reduced effort), not inspected implementation evidence. This blueprint does not claim that an existing Smart Kitchen repository already contains these modules or integrations.

## How to use this evidence during execution

At sprint kickoff pin exact dependency/provider configurations and record them next to the release artifact. At integration spike validate claims against real sandbox behavior and retain test receipts. At launch recheck current store policy/provider product limits and refresh this register. Any change to copy rights, audience generation, household privacy, auth/token handling or entitlements requires coordinated API, data migration, screen copy and negative-test changes; it is not a standalone UI tweak.
