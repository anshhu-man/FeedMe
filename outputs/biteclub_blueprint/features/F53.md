# F53 — Navigation, offline use and deep links

## Strategy
One typed screen registry links product behavior, app navigation, diagrams and test coverage. Preserve the meal context across login, pickers, app backgrounding and retries. The delivered prototype simulates the registry; it is not evidence that production APIs exist.

## Experience and screen design
AUTH_WELCOME is the first new-user screen. Main tabs are Today, Cook/HOME, Cookbook, Inbox and My Plate. COOK/STORY use focused chrome. Pickers retain a typed `returnTo` and selection purpose; back/cancel return without changing saved data. UNAVAILABLE and OFFLINE are first-class screens. Deep-link landing rechecks current access before displaying source media, even if a notification was valid when sent.

## Production sequence
Native universal/app links parse an allowlisted route and bounded opaque resource ID. Store a short-lived pending route when authentication is needed; after bootstrap, resolve object access and route or show UNAVAILABLE. Screen ViewModels produce immutable UI states and domain intents. Repositories fetch versioned DTOs and maintain owner-scoped SQLite cache. Durable private cooking/feedback commands may use a local operation queue; social publish, audience changes, group coordination and purchases require online authorization and a server receipt.

## Data and API contracts
Typed route envelope: routeId, permitted parameters, source, returnContext and creationTime. No auth tokens, food preferences or raw invite secrets in analytics; sensitive invite tokens are consumed into protected temporary storage. Sync commands carry clientOperationId, account scope, base revision and payload schema version. Server replay responds with prior receipt or a conflict. GET screen hydration operations are documented alongside button commands in the registry.

## Permissions and lifecycle
Navigation is not authorization. Every server operation verifies object rights. Cached private data is scoped by account and erased/rekeyed on logout/account switch. Cached social images have short leases and cannot be treated as proof of continuing membership. Android Keystore/iOS Keychain protect keys/credentials; SQLite file access is app-private. Feature flags are checked for server commands as well as entry points.

## Failure and offline behavior
Offline cooking uses an owner-scoped, previously verified pinned recipe and local timer deadline. Display its last-sync time and explain that later server recalls or access changes cannot be known while offline; locally known recalled content is unavailable. There is no signed content or entitlement lease in this contract. New protected server actions require online authentication, current registered-session validity and current authorization. Never merge conflicting ingredient-exclusion choices with last-write-wins. If an audience/source changes during upload, retain draft and require confirmation. On app kill, restore only non-secret drafts and safe navigation context. Unknown/newer routes fall back to an update/unavailable screen with a useful path to HOME.

## Integration and dependencies
All feature modules depend on shared domain contracts, not on each other's UI classes. A navigation mediator owns cross-feature destinations and picker results. Platform adapters own browser login, media capture, share sheet, payments, local timer notifications and app settings. The generated screen registry includes these external boundaries explicitly.

## Execution plan
Define routes and action IDs from spec/model.mjs; generate typed Kotlin route declarations and API clients as an implementation task. Build shared navigation state, repository interfaces, local schema migrations and command queue. Implement per-feature loaders and safe picker return contexts. Add launch/deep-link/re-auth fixtures and network shaping to device tests. Keep docs/diagrams generated from the same registry in CI.

## Acceptance and release gates
Every target screen exists; every member feature has entry and safe exit; every mutation maps to a contract; native operations are declared separately. Test all signup paths, expired invites, deleted post links, interrupted Make Mine, composer picker cancel, two-account switches, app-killed timers and replayed offline commands. No action should silently discard work or claim remote success offline. Roll back individual entry points while keeping existing data readable and exit paths functional.
