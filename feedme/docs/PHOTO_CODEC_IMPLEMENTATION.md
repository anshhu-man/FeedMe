## Actual implementation

`server/media/processing/codec` contains an explicit resource/profile policy, bounded PNG/JPEG container parser, real JDK Image I/O conversion and a separate JVM child-process adapter. Production construction requires an absolute Java executable/classpath and explicit heap, concurrency, timeout and termination-wait limits. There is no Main registration, provider selection, default numeric operational configuration or in-process timeout presented as a sandbox.

Current input support is ordinary 8-bit JPEG (baseline/progressive, one/three color components) and PNG (supported grayscale/palette/RGB/alpha depths up to8 bits, including Adam7). Unsupported HEIC, animation,16-bit PNG, ICC/Adobe/CMYK or unrecognized coding/color forms return an explicit unsupported result. A configuration using this processor must advertise JPEG/PNG only; accepted old unsupported jobs fail closed rather than being relabeled. Output is the explicitly selected PNG RGB/ARGB profile with thumbnail/display variants, no enlargement and no inherited metadata. Broader color/format support remains a separately verified follow-on, not an accepting decoder fallback.

Before Image I/O allocation, the parser checks signatures, dimensions, pixel/memory estimates, bounded parts/metadata/EXIF offsets, PNG CRC/order and exact decompressed scanline/filter/zlib termination. JPEG entropy/marker structure is bounded and reader warnings are rejected. Orientation1–8 is applied to pixels. A sanitized decoding copy removes metadata before the reader sees it; a fresh raster is encoded, then independently parsed and decoded again. The derivative chunk allowlist is only IHDR/IDAT/IEND; comments, EXIF/GPS/XMP/text and source thumbnails are not carried forward.

Independent review additionally found JDK17's transparency comparison needs normalized PNG tRNS samples for depths below16. The sanitized copy masks unused high bits and recalculates the chunk CRC, leaving original source bytes unchanged. Run06 caught a further JDK mismatch: packed gray1/2/4 pixels are expanded before transparency comparison. The sanitized sample is now expanded too; its replicated low bits preserve the original PNG sample. Run07 passes gray8/RGB8 and all22 possible packed gray1/2/4 sample values in both derivatives. This follows the explicit masking rule in [PNG tRNS](https://www.w3.org/TR/png/#11tRNS).

The implementation uses the pinned JDK `java.desktop` JPEG/PNG reader providers and PNG writer. The JDK supports pluggable readers, so class/module checks and a verified production classpath are important; arbitrary fallback plugins are not selected. [JDK ImageReader](https://docs.oracle.com/en/java/javase/17/docs/api/java.desktop/javax/imageio/ImageReader.html). PNG container checks follow the structural/CRC and image-data rules in the [W3C PNG specification](https://www.w3.org/TR/png/).

Private bytes use anonymous stdin/stdout pipes. Child environment variables are cleared; no private temporary file, URL fetch, shell command, inherited credential or raw decoder log is created. The parent validates an exact bounded two-variant binary envelope. Timeout/cancellation terminates the owned process; a concurrency permit is retained until actual process exit, including a delayed reap. Java process termination and timed waits are distinct operations, and the code/tests require both rather than assuming a kill request proves exit. [JDK Process](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/Process.html).

The latest review fix transfers destruction, exit wait and pipe cleanup together to a retained daemon reaper before the bounded caller wait: JDK destruction itself can synchronously close a blocked pipe. The permit remains owned until exit and cleanup both complete. A deterministic Process contract double independently blocks inside destruction and cleanup; this tests ownership/bounded-wait branches, not an observed slow OS kill. All31 codec methods pass in `verification/cookbook-processor/focused/07-server-codec.log` as part of250 successful server unit tests; original XML retained in `07-results/`. This focused result does not replace final frozen worker/provider acceptance.

## Limits and required next evidence

The current resource calculation is conservative admission accounting, not an OS RSS/CPU/network sandbox. Heap caps and local termination tests do not prove deployment container/network isolation, codec vulnerability absence, malware scanning, moderation approval or physical-host behavior. One configured retained process owner must enforce concurrency; constructing arbitrarily many owners bypasses an instance-local semaphore. Deployment must bound aggregate resources and verify Java/classpath/codec revisions.

The media coordinator independently fetches the exact immutable object version and checks actual length/hash. It must pin codec revision/output hashes before external writes and require mandatory current safety/authority evidence before READY. Codec success does not authorize publication or erase a source. Real-provider late-write/version/deletion behavior remains an integration gate.

Further full acceptance must bind these focused cases to a frozen source/artifact and exercise replay/cancellation across actual worker/store boundaries, independent review findings and real PostgreSQL lifecycle races. All metadata and byte fixtures are synthetic, generated locally by tests; they are not user photos or production cooking content.
