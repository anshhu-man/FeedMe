# F45 — Expanded Personal Library

Phase: later optional paid upgrade. Owner modules: memory for organization, commerce for entitlements.

## Strategy

Offer additional organization tools to people who repeatedly save useful meals, while basic saved-recipe access remains free. The proposed paid scope is custom named collections, putting a recipe in multiple collections, manual ordering and richer filtering across existing effort/sensory metadata. Do not sell the right to reopen recipes a person already saved. A permanent organization upgrade is the initial product hypothesis; no price or live store product is established by this blueprint.

## Experience and screen design

COOKBOOK keeps basic search, opening, saving and deletion available to everyone. Create collection and advanced organization open COLLECTION_EDIT when entitled or PAYWALL before the user invests in editing. COLLECTION_EDIT shows name, selected recipes and an accessible reorder list; Save commits once, Cancel preserves existing state. COLLECTION exposes the resulting ordered recipes and Edit collection. PAYWALL states one-time versus recurring terms from the actual configured offering, included tools, Restore purchases and Keep using the free app. MANAGE_PLAN shows entitlement state and the store-origin management path. Existing custom collections remain readable if access changes.

## Production sequence

1. Fetch server entitlements and present only configured offerings with authoritative localized store metadata.
2. After explicit native purchase/restore, reconcile via F50; client success alone never unlocks server writes.
3. On create/edit, authorize collection ownership and required organization capability in the same request.
4. Write collection metadata, item memberships/order and revision atomically; never duplicate the underlying immutable recipe copy.
5. On access loss, preserve recipes, collection names/order and export/read access. Stop new paid organization operations while retaining deletion and basic retrieval.

## Data and API contracts

GET/POST /v1/collections list/create; GET/PATCH /v1/collections/{collectionId} read/update metadata. POST /v1/collections/{collectionId}/items adds an existing savedRecipeId; DELETE /v1/collections/{collectionId}/items/{savedRecipeId} removes that membership only. POST /v1/collections/{collectionId}/order updates a validated complete ordered set for the collection. DELETE /v1/collections/{collectionId} removes the custom grouping after explicit confirmation; it does not delete recipe copies. Default cookbook deletion is prohibited. Mutations require Idempotency-Key and If-Match where updating. Example reorder body:

    {"orderedSavedRecipeIds":["00000000-0000-4000-8000-000000000081","00000000-0000-4000-8000-000000000082"]}

Collection transport fields include id, version, name, description, savedRecipeIds and optional smartRule; owner/default-kind and membership ordering are authoritative internal records. Membership uniqueness is collectionId+savedRecipeId. Every supplied ID is checked for ownership and exact membership. CollectionOrder is bounded to 1,000 IDs per complete reorder; larger collections retain basic access and standard sorting, with manual-order limits shown before editing. This transport bound is not a cap on private recipe saves. Filtering uses reviewed metadata, never inferred health scores. Use typed entitlement/concurrency/item/default-collection errors. Server capability is library_tools; product mapping and access intervals belong to F50.

## Permissions and lifecycle

Collections are private; their existence does not grant permission to publish source recipes. A revoked future social-save grant does not erase existing permitted recipes. Downgrade/refund handling preserves established basic recipe access and readable organization, while new premium editing follows the disclosed rights. Existing saves must not suddenly hit a free-tier cap that hides content. Account deletion removes personal collections; export includes collection structure and recipe content only where allowed by the save rights.

## Failure and offline behavior

Offline users can read cached collections and reorder a local draft. Entitlement-dependent writes are marked Pending validation and committed only after current server authorization; do not promise the draft is synced. A 412 offers the latest order plus the user's proposed order for resolution, avoiding silent overwrite across devices. Purchase pending or canceled returns to ordinary cookbook access. A removed/recalled recipe remains a visible unavailable item until the user removes it, without corrupting order indices.

## Integration and dependencies

F19 basic saves, F30 copy rights, F50 purchases, F49 export/deletion and F53 offline conflict handling. F46 packs may be presented as virtual collections but purchasing a pack does not automatically grant every library organization tool.

## Execution plan

- Implement private collection membership/order schema and ownership checks.
- Add capability enforcement plus downgrade-safe read/delete behavior.
- Build collection editor, concurrent reorder reconciliation and contextual paywall return.
- Emit library_organization_requested, entitlement_write_denied and collection_conflict without recipe titles.

## Acceptance and release gates

Test unpaid direct API writes, purchase pending, refund, two-device reorder, duplicate membership, deleting a custom collection and saving beyond any previous free limit. Confirm basic recipes remain searchable/openable after access loss. Validate the paid value through repeated-use research before enabling offers. Rollback library_sales independently of library_reads; preserve existing entitlements and data if new sales are disabled.
