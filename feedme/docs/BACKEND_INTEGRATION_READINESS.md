# Supabase authentication proposal: integration readiness

Read-only source audit, 15 September 2026 IST. **Proposal only; no Supabase SDK, cloud project, production verifier, identity routes or connected login was added.** Existing synthetic/native tests are not provider acceptance. This audit does not change the 44 V1 features or ten deferrals.

## Bottom line

Reuse FeedMe's retained-session lifetime, encrypted credential/storage owners, canonical transport and operation-specific authorization seams. Supabase is not a drop-in token-string substitution: the missing critical path is verified account/bootstrap persistence, a coordinated refresh lifecycle, provider callback/recovery handling, and an intentional Cognito contract migration. Current server Main remains health-only/unconfigured for product operations.

## Contract changes that cannot be skipped

1. Edit canonical [04_API_Contract.json](/Users/LOCAL_USER/Documents/ChatGPT/Career/outputs/biteclub_blueprint/architecture/04_API_Contract.json), not only generated Kotlin: UserBearer currently says **Cognito access JWT**, with `client_id`, `token_use=access` and Cognito scope semantics. Replace with an explicit Supabase user-access-token profile; retain distinct GuestBearer/StaffBearer and device checks. Update corresponding HTTP verifier documentation/contracts, not merely relax checks.
2. Migrate eight Cognito-named actions in [screen_registry.json](/Users/LOCAL_USER/Documents/ChatGPT/Career/outputs/biteclub_blueprint/registry/screen_registry.json): AUTH_SIGNUP.01, AUTH_LOGIN.01, AUTH_VERIFY.01/.02, AUTH_RESET.01, AUTH_RESET_CONFIRM.01/.02, SETTINGS.12. Link/OTP reset semantics are not Cognito confirmForgotPassword. Update mirrored registries/exports intentionally. Review AUTH_CALLBACK state/nonce/PKCE and add the explicit Google route if approved.
3. **Existing bootstrap schema gap:** Bootstrap always requires Profile, and Profile requires displayName+handle, but BootstrapRequest accepts only installation/platform/appVersion plus optional terms/eligibility—not profile fields. Fresh email/Google authentication does not supply a unique FeedMe handle. The [engineering decision note](BOOTSTRAP_PROFILE_DECISION.md) recommends an explicit pending-profile representation preserving bootstrap → PROFILE_SETUP; the alternative collects the chosen profile before bootstrap. Neither is implemented. Do not fabricate a profile/handle to return 200; preserve genuine `requiredGates`, flags and entitlements.
4. Update architecture/security decisions, `scripts/contract-source.lock.json`, generated contract+receipt using `scripts/generate-contract-artifacts.mjs`, and exact canonical/binding tests including ContractCatalogTest's Cognito assertion. Do not overwrite historical verification receipts or widen unrelated operations.

## Provider semantics checked against current primary documentation

- Supabase supports Google OAuth/native sign-in; its returned Supabase tokens are distinct from optional Google provider tokens. Provider/client registration and redirect allowlists are external configuration work. Choose one reviewed native Google or PKCE system-browser flow with transaction-bound callback handling. [Google integration](https://supabase.com/docs/guides/auth/social-login/auth-google)
- With Confirm email enabled, Kotlin signup does not automatically sign in; an existing-account response can deliberately be obfuscated. A returned user object is not verified admission. Keep generic resend/reset feedback and verify authoritative confirmed-email/user state, not editable metadata. [Kotlin signup](https://supabase.com/docs/reference/kotlin/auth-signup), [retrieve user](https://supabase.com/docs/reference/kotlin/auth-getuser)
- Supabase rotates refresh tokens with documented reuse exceptions, so concurrent owners are unsafe. Its session UUID is separate from FeedMe's device record. Signed access JWTs can remain usable after logout unless the backend checks current session status; retain FeedMe's per-request device revocation. [Sessions](https://supabase.com/docs/guides/auth/sessions)
- JWT issuer/audience/role/session/anonymous claims differ from Cognito; configure trusted keys and rotation/cache handling, rather than trusting decoded claims. [JWT claims](https://supabase.com/docs/guides/auth/jwt-fields), [signing keys](https://supabase.com/docs/guides/auth/signing-keys)
- Reset is request-link → validated recovery callback → updateUser(password), not immediate login success. Sign-out scope must be explicit. [Kotlin reset](https://supabase.com/docs/reference/kotlin/auth-resetpasswordforemail), [sign-out](https://supabase.com/docs/guides/auth/signout). Kotlin initialization exposes automatic-loading/refresh options; verify the exact selected SDK configuration before granting it persistence ownership. [Initialization](https://supabase.com/docs/reference/kotlin/initializing)

## Approval and execution gates

The proposed provider replacement still requires technical-direction approval. Region, permanent project/app/API identity, budget, account access and deployment retain their separate approval gates. Within an approved stack, selecting compatible dependency versions and implementing the normal native/provider adapters are engineering tasks, not a request for the user to approve every technical detail. Resolve and document the Google flow, pending-profile representation, identity-linking and logout/recovery behavior before integration; raise product-policy choices only where they materially change the agreed behavior. Cloud Google/Supabase setup, SMTP/domain verification, redirect registration and secrets handling remain external work; no service-role or Google secret belongs in the APK. iOS secure credential implementation is not present in this session module despite declared iOS targets, so Android readiness must not imply iOS completion.

After approval, parallelize: (A) canonical contract + identity DB/bootstrap/JWT adapter; (B) native provider + runtime-owned refresh; (C) auth UI/callbacks against the approved states. Integration gate: wrong issuer/audience/anonymous/unverified denial; Google nonce/state/callback replay; duplicate/unknown bootstrap; fresh account without handle; one concurrent refresh and lost rotation reply; logout vs refresh/late callback; offline restore without credential refresh; credential CAS/readback failure; reset callback never granting publication; real configured Android Google+verified email journeys. Existing synthetic tests remain regression evidence only.
