# F28 — Private Replies

## Strategy
Private Replies let people discuss a dish directly with its author without creating a public comment section. P1 supports one-to-one text and permission-aware recipe references. P3 adds text conversations scoped to an accepted Dinner Pact or Bring a Bit group; arbitrary file attachments remain excluded. Reply permission is configurable, and cooking works without messaging.

## Experience and screen design
`STORY` and `POST` offer “Reply privately” when the recipient permits it. `THREAD` shows the two participants, a small source context card, messages, compose field, delivery state, mute, block, and report actions. `INBOX` lists conversations by the newest authorized message. Source context is rendered as “Post unavailable” when access ends; surviving private conversation text remains distinct. A sender reviews text before pressing Send. Suggested text is never sent automatically.

## Production sequence
`POST /v1/threads` with `{kind:direct,recipientUserId,contextPostId}` resolves the unique direct conversation after checking shared-circle eligibility, source access, blocks, and reply settings. P3 `kind=pact|potluck` supplies matching `contextType` and `contextId`, resolving a thread from accepted server participants. `POST /v1/threads/{threadId}/messages` persists a validated message and `message.created` in one transaction. A client-generated message ID plus idempotency key prevents duplicate delivery. The response changes a pending bubble to sent. Workers reauthorize each recipient before privacy-safe push delivery. `GET /v1/threads/{threadId}/messages?cursor=…` pages by server sequence.

## Data and API contracts
`Thread(id,kind,participantPairKey,contextType,contextId,status,lastSequence,version)` enforces a unique sorted pair for direct threads or unique context for coordination threads, never both. `Message(id,threadId,senderId,clientMessageId,sequence,body,sourcePostId,createdAt,deletedAt)` has unique thread sequence and sender/client ID constraints. Text is bounded, sanitized, and rendered without executable markup. Source cards contain authorized references, not copied photos. Use typed `MESSAGING_DISABLED`, `RECIPIENT_UNAVAILABLE`, `MESSAGE_TOO_LONG`, and `RATE_LIMITED`; do not disclose which blocking rule caused unavailability.

## Permissions and lifecycle
Only the two participants can read direct history. New direct messages require an active shared circle, neither-direction block, and the recipient’s current reply preference. Losing the last shared circle makes direct history read-only. Coordination history requires current accepted context participation; departure or cancellation closes sending, and loss of participation denies group history. A block suppresses interaction and blocked actors’ content within group views; no private dietary data enters the thread. Post expiry does not erase independent message text. Account deletion follows F49, and reporting uses bounded, restricted evidence receipts.

## Failure and offline behavior
Compose and draft text can remain locally encrypted. Queued sends clearly say “Waiting to send,” and recheck eligibility online; revoked access returns the text to a failed draft. On uncertain timeout, retry the same client ID. Never send an old draft automatically after the user deleted it, logged out, or switched accounts. Pagination tolerates tombstones and duplicate fetched rows.

## Integration and dependencies
Identity, circles, F29 recipe requests, F39 preferences, F41 notifications, F42 moderation, and F53 account-scoped local storage. This plan does not claim end-to-end encryption; transport encryption, protected storage, and restricted operational access must be documented accurately.

## Execution plan
Build transactionally ordered messages and per-send policy checks, then inbox/thread UI and delivery recovery, then notification and reporting integration. Observe queue delay, duplicate suppression, and policy rejections without logging message bodies.

## Acceptance and release gates
Test blocked sends racing commit, last-circle removal, account switching, replayed sends, unavailable source cards, and unread-count reconciliation. `conversations.send.enabled` stops new messages while preserving history, deletion, block, and reporting controls. Release requires no message delivery to an unauthorized recipient and no private text in push previews by default.
