# Client integration boundaries — M0.06

Status: interface foundation, updated 13 September 2026. These interfaces do not themselves implement providers. Subsequent standalone transport, encrypted private-state, Android credential and session components are linked below; real authentication, native timers and actual provider/backend/UI composition remain unfinished. The demo still uses memory-only fixtures. The later [read-only recovery diagnostics](SESSION_RECOVERY_DIAGNOSTICS.md) report bounded evidence from already-open resources; they never initialize factories, read credential payloads, run key cleanup or grant repair/activation authority. Missing/tampered credentials can still have coherent metadata, so actual verification remains necessary.

## Implemented seams

[Confirmed empty-setup discard](EMPTY_SETUP_DISCARD.md) is now a separate explicit runtime action with ephemeral confirmation, exact durable optional targets and conditional empty-only cleanup. It does not change the read-only diagnostic contract or implement unknown-orphan recovery, provider login or confirmation UI.

[Planned credential creation](PLANNED_CREDENTIAL_CREATE.md) adds a separate bounded CREATE protocol: mandatory planned-store capability, authenticated exact intent persisted in independent encrypted control before native credential writes, and explicit existing-only recovery. Structural plan decoding is not native MAC authentication. The distinct `PendingCreate` blocks restore, diagnostic progression, leased data/credential access and work admission; ordinary logout/empty-discard recovery refuses it rather than falling back to its cleanup targets. Inspecting a plan does not confirm abort or grant identity. Integrated data/work journaling, refresh repair, arbitrary orphan recovery and real provider/UI integration remain open.

[Planned private-data activation](PLANNED_STATE_ACTIVATION.md) adds low-level exact predecessor/key planning and selection, completing b.2b.1 only. Its `Unit` acknowledgment grants no lease, private-store handle, retirement target or durable setup-journal resolution. The separate [planned state recovery](PLANNED_STATE_RECOVERY.md) component is now implemented as b.2b.2 IN_PROGRESS, with full/native verification pending. Every empty-only abort commits an actually changed V2 receipt and consumed generation before exact key deletion, even when inspection already says ABORTED. Historical same/foreign-owner receipt references forbid candidate-key reuse. The handle exposes only inspect/abort/close, not private data or activation authority.

The API27+ existing-only recovery opener requires existing V2/files/lock/index and rejects V1, existing journals and unknown children without initialization, migration or GC. Normal shared-engine opening alone may atomically migrate exact V1 to V2; normal open/resume retain cleanup. Returned-handle close can retry, but failed construction followed by failed cleanup close remains a process-restart gate. The runtime still uses unplanned data activation; work-origin planning/composite journaling (b.2b.3) and UI remain absent. A no-op selected replay adds no fresh sync, whereas the earlier post-successful-COMMIT fault loses an application receipt. Native syscall-failure verification is pending; neither those tests nor readback alone establish whole-session power-loss safety or a universal extra-fsync rule.

Storage scopes include environment, actor kind and actor ID. A guest, a simulated demo and a registered account cannot share a namespace by matching their ID text. A scope is **not** a filesystem path; adapters must derive opaque internal keys. Do not include private identifiers in filenames or telemetry.

Credential variants distinguish a guest session/token from provider account credentials. An account may have no registered device-session ID before bootstrap. The real transport must omit `X-Device-Session` for guest/bootstrap calls and require the correct bootstrapped account session for subsequent user calls; it must not fabricate the header. The interface alone does not enforce request authorization or perform bootstrap.

`PrivateBytes` copies buffers entering/leaving the codec boundary. Secret/record/request/reply debug strings redact private material. This only reduces accidental logging: it does not encrypt bytes, securely wipe immutable strings, prevent a caller deliberately extracting/logging data or constitute a complete telemetry audit.

`SessionBoundary` protects client state from stale results. It cannot undo an already accepted server mutation, cancel transport automatically, authenticate a caller or replace server ownership checks. It also does not stop an adapter writing a cache after logout: durable adapters must enforce lease/generation-aware commits and logout-erasure ordering. A typed client ticket is not an authorization token. Provider adapter exceptions/cancellation propagate; they are never converted into successful replies.

HTTP errors remain typed replies so their complete Problem bodies can be decoded. ETag, bounded/redacted trace ID and Retry-After seconds are retained. A possibly accepted mutation has a distinct `OUTCOME_UNKNOWN` transport failure: keep its command key and reconcile/retry the same intent, never create a replacement command because the first response was lost.

## DTO mapping rules that must not be lost

Source: [canonical OpenAPI](../../outputs/biteclub_blueprint/architecture/04_API_Contract.json). The current demo `Recipe`, `CookingSession`, `SavedRecipe` and `AdaptRequest` are not wire DTOs.

- Production cooking starts with `CookStart.planId`, not a recipe ID. Preserve immutable recipe-version IDs separately from recipe IDs.
- Preserve stable step IDs, mandatory safety-step flags, ingredient IDs/amounts/units, device sequence, revision, timers and server timestamps. Resolve display labels without throwing canonical IDs away.
- `approved` is not `published`. Keep draft, personal, retired and recalled states distinct; unknown state must not become reviewed content.
- Preserve saved snapshot rights, source/grant references and recall state. `savePostRecipe` is a separate authorization transaction, not generic `saveRecipe`.
- `SaveRecipeRequest.anyOf` allows at least a plan ID or recipe-version ID, including both. Do not generate an exclusive union or silently choose precedence.
- Preserve required-nullable versus absent optional properties and conditional field-presence rules. DTO generation alone is not JSON Schema validation.
- Keep HTTP status, bodyless 204, ETag/version, problem code/trace, retry-after and pending/uncertain outcomes. Metadata coverage must be tested when the real transport is added; the current reply boundary is not yet the complete generated HTTP response model.
- Member/guest, staff and RevenueCat webhook operations need separate callable adapters and credentials. Generating 201 operation descriptors does not authorize calling all 201 from the mobile app.
- RecipeVersion has no image URL/key. Existing food images remain illustrative presentation assets, not recipe provenance.
