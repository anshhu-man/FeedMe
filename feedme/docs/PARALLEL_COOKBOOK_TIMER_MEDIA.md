## Media contract decisions

`prepareMediaUpload` retains one exact original reservation/core Upload/ETag under its original command key. Its short-lived POST capability fields are explicitly a rendering exception: same-key retry may reissue only for the same unchanged awaitingUpload reservation, under current account/device/terms/clientDraft locks, no later than the original reservation deadline. Target key, expected bytes/type/hash and owner remain identical; renewal never extends the reservation or allocates a second asset. GET status does not sign or renew. Changed/processing/deleted state refuses old capability issuance; expired reservations return410. An explicit new upload after expiry is a separate user intent, never an automatic replacement key.

Durable receipts never contain POST bearer fields. Bounded local signing under the current locks is a mandatory configured adapter. If the core reservation commits but signing/response fails, preserve it for exact same-key reconciliation; do not compensate by deleting it or imply definite noncommit. Actual response bounds must be admitted before a success is committed.

Unlike renewed prepare capabilities, completion retries return the original processing acknowledgment. The canonical operation explicitly promises the original result: a later legitimate processing→ready/rejected transition must not make an already committed command unreconcilable. The implementation now pins the completion key, accepted version and accepted timestamp immutably. The original200/processing body and ETag are reconstructed and compared under current account/device/draft/terms authority; GET returns the current status. Deleted/replaced/revoked access still fails, a fresh command does not repeat completion, and no replay refreshes the original receipt retention. These changes still require real database and HTTP acceptance.

First upload reserves an owner-scoped clientDraft lifecycle root, not an implicit social PostDraft. Mandatory supplied-connection authority fences existing server-draft terminal/expiry state and must use the same lifecycle lock in future publication/deletion. Completion takes an authorized reservation snapshot, verifies the exact immutable remote object version outside SQL, then re-locks the principal/command/draft/media and requires the full snapshot unchanged with fresh database-time expiry before committing processing plus the existing completed event.

Already-issued POSTs can remain usable until expiry after deletion/revocation. A tombstone immediately denies processing/publication, while purpose-fixed durable cleanup retains exact key/version work through the last possible upload deadline. No broad object sweep, new public cleanup event, physical-erasure guarantee or quarantine-original delivery is introduced.

Policy is explicit, not provider-selected: photo bytes must not exceed10,000,000; configured format subset, capability fields/TTL, request/response and processing bounds are mandatory. Clip/avatar, actual processing readiness, server drafts/publication/Today/Plate, media delivery and cleanup workers remain subsequent parts of the original social scope, not silently removed features.
