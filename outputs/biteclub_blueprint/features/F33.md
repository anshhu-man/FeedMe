# F33 — Tonight

## Strategy
Tonight turns a saved idea into a concrete personal dinner choice: a current recipe version, missing items, and the next useful step. It uses the existing private planning flow with a Tonight intent, not a separate calendar resource. It is a later feature with a complete implementation plan and does not require social participation or a subscription for basic recipe access.

## Experience and screen design
`RECIPE`, `POST`, and `COOKBOOK` offer “Tonight?” for accessible content. `TONIGHT` presents the chosen meal, confirmed ingredients, an editable personal checklist, effort preview, and “Start cooking.” The optional local date is context, not an obligation or scheduled reminder. Selecting another choice replaces the local selection only after a fresh plan succeeds. “Invite someone” separately opens `PACT_CREATE`; choosing dinner never sends an invitation. A linked recipe that becomes unavailable offers another choice; an authorized private saved copy remains usable.

## Production sequence
`POST /v1/plans` with `intent=tonight`, source reference, confirmed ingredients, and optional private date/context creates a fresh immutable plan receipt. The planning transaction validates source access and current constraints, writes the plan and `plan.created` outbox event, and returns its ID. The client atomically sets its owner-scoped Tonight selection only after that receipt. `GET /v1/plans/{planId}` revalidates a saved selection. Replacing dinner creates another plan through the same command; it never mutates an earlier recipe or plan. `POST /v1/cook-sessions` pins the selected eligible version and opens `COOK`; completion clears the local active choice after its receipt.

## Data and API contracts
`TonightContext(ownerPrincipalId,selectedPlanId,localDate,timeZone,localRevision)` is encrypted local presentation state pointing to an ordinary owner-authorized immutable Plan. `ChecklistItem(id,planId,label,quantity,unit,checked,source,localRevision)` is a local checklist, not a shopping order or inferred pantry update. Plan provenance distinguishes owned/private-copy recipes from revocable source references. Clearing Tonight removes the local pointer, not the plan or recipe. The canonical plan command uses stable idempotency keys; stale asynchronous responses cannot replace a newer local selection revision. `SOURCE_UNAVAILABLE` and `NO_SUPPORTED_MATCH` leave the prior choice intact.

## Permissions and lifecycle
Plans and checklists are owner-only. Source-only references revalidate access before detail retrieval or cooking; only authorized copies persist full recipe content independently. The local checklist is device-specific in this release, and the UI does not promise cross-device checklist synchronization. A local-date change does not create reminders or publish activity. Older plans remain ordinary private plan history until their retention rules apply; Today and My Plate never include them. Adding Tonight is not saving a third-party recipe under a new grant.

## Failure and offline behavior
Owned/private-copy meal context and checklists can be edited offline in encrypted local storage. A fresh server-recommended plan remains pending until connection returns; an already cached eligible version can still be cooked. Local checklist edits use revisions to avoid overwriting a newer edit within the app. If a source-only story expires, preserve user-written checklist entries but remove inaccessible derived content on sync. Failed replacement or app termination preserves the previous selected receipt. No queued invite is generated from an offline choice.

## Integration and dependencies
F02 planning, F11 effort preview, F12 cooking, F19 cookbook, F30 grants, F34 Dinner Pact, and F53 local storage/deep links. Pantry updates remain explicit: completing a checklist item does not infer that an ingredient was consumed or purchased. Coordinated reminders belong to a separately accepted pact.

## Execution plan
Add the Tonight intent and private context to the existing plan request schema; build the local selected-plan/checklist store; implement replacement and cooking recovery; then add source invalidation and optional pact entry. Instrument stale response suppression, inaccessible sources, and plan-to-cook transitions without collecting grocery text.

## Acceptance and release gates
Test duplicate submissions, out-of-order replacement responses, app termination, account switching, recalled copies, expired source posts, and offline checklist edits. `planning.tonight.enabled` disables new entry points while retaining private plan and recipe access. Release requires no unintended social delivery, no ungranted recipe persistence, and no implied calendar or cross-device checklist capability.
