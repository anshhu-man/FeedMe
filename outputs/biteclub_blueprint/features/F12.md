# F12 — Guided Cooking

Phase: first release. Owner module: cooking; native notification integrations.

## Strategy

Keep a person oriented while their hands, attention and app lifecycle are interrupted. Guided cooking uses pinned reviewed instructions, step-specific quantities and explicit timers. Progress records navigation and user actions; it does not certify that food was prepared safely or that a meal was completed exactly as instructed.

## Experience and screen design

Cook this on RECIPE/VARIANT opens COOK after confirming missing essentials and content eligibility. COOK shows one step, its ingredient quantities, a step count, Back/Next and an always-accessible Ingredients summary. Applicable steps offer Start timer; TIMER supports multiple labelled timers with pause, resume, cancel and clear expired status. Leaving the app preserves progress. On returning, Resume meal names the dish and last step. MEAL_DONE asks whether the user is done, with optional Make again, Feedback and Share; none is required to finish. Abandon session is explicit and separate from closing the screen.

## Production sequence

1. POST creates a session pinned to an immutable plan with its recipe version and materialized variant/constraint snapshot after authorization and recall/exclusion checks.
2. Download the complete permitted cooking bundle atomically before entering reliable offline mode.
3. Persist step changes and timer operations locally before updating UI; sync versioned mutations to the server.
4. Schedule native local alerts when permission allows. Timer elapsed state derives from persisted deadlines/remaining duration and monotonic time while running, never from a per-second network request.
5. Completing writes session state and an outbox event once. Optional feedback, recipe saving and publication are distinct durable actions.

## Data and API contracts

createCookSession: POST /v1/cook-sessions with Idempotency-Key.

    {"planId":"00000000-0000-4000-8000-000000000021","deviceSequence":0}

updateCookSession: PATCH /v1/cook-sessions/{sessionId} with If-Match, Idempotency-Key and deviceSequence supports currentStepId and timers. completeCookSession: POST /v1/cook-sessions/{sessionId}/complete is idempotent. GET /v1/cook-sessions/{sessionId} restores a session. CookStart references only the immutable plan; the server resolves its pinned recipe/variant instead of trusting a client-supplied replacement. Store status, currentStepId, completedStepIds, version, updatedAt and timers with timerId, stepId, status, durationSeconds, pausedRemainingSeconds and endAt. Derive timer labels from pinned step context, with an internal monotonic anchor for foreground recovery. Absolute timestamps are UTC. A deadline is an estimate across device clock changes; surface uncertain restoration honestly. No server timer automatically advances a cooking step.

## Permissions and lifecycle

Sessions belong to their authenticated or bounded guest principal. Notification permission is optional; denied permission retains visible timers. Ask contextually when starting the first timer and explain that alerts depend on device settings. Background execution, silent mode and exact delivery are platform-dependent and require native validation. Only explicitly completed sessions produce meal_completed; viewing the last step does not. Account deletion clears server sessions and cached personal data according to F49.

## Failure and offline behavior

Offline step navigation and timers work after a full bundle is cached. Store commands with mutation IDs and expected revision; replay in order after reconnect. If two devices changed progress, return 412 and offer Choose progress, preserving both states without merging timer deadlines arbitrarily. A content recall blocks starting new sessions and warns active connected sessions; offline devices receive it only on reconnection, a disclosed technical limit. A missing bundle returns to RECIPE with Download incomplete. App termination must not erase local progress; native alert reconciliation runs on resume. No timer is presented as a guarantee of food readiness.

## Integration and dependencies

F11 supplies effort context, F13 pinned steps/recalls, F14/F15 optional post-meal actions and F41 notification settings. F53 owns route restoration. Kotlin shared state and persistence drive both clients; Android/iOS adapters own alert scheduling and accessibility behavior.

## Execution plan

- Implement session state machine and atomic local bundle/command persistence.
- Add versioned session endpoints and complete-plus-outbox transaction.
- Build COOK/TIMER/MEAL_DONE with interruption recovery and multiple timers.
- Implement native scheduling, cancellation and resume reconciliation on both platforms.
- Emit cooking_session_started, cooking_session_resumed, timer_recovery_uncertain and meal_completed without step content or dietary data.

## Acceptance and release gates

Test app kill, device restart, timezone and wall-clock changes, two simultaneous timers, denied alerts, offline completion replay, two-device conflicts and catalog recall. Verify pause/resume preserves remaining time, completion emits once and cancel removes alerts. Run native device tests rather than relying solely on the navigation simulator. Roll out guided_cooking separately from timer_alerts; disabling new alerts must not discard active timers or sessions.
