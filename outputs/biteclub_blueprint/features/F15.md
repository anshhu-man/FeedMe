# F15 — Optional Feedback

Phase: first release. Owner module: memory.

## Strategy

Learn what tasted good and what was manageable without adding a meal diary. Feedback is explicit, optional and attached to a particular meal, ingredient, sensation or preparation burden. Declining feedback has no penalty and does not reduce core help.

## Experience and screen design

MEAL_DONE offers small Make again, Too much prep and Not my taste actions plus Done. FEEDBACK opens only when a response needs clarification: “Was it the meal, an ingredient, or the texture?” and, for effort, “Which part felt like too much?” with optional prepared choices. A plain text note is optional, bounded and private. No calorie, body or public health score appears. Show a brief confirmation describing the scope, such as “We'll show this meal less often.” Include Edit feedback and access to MEMORY_DETAIL after a preference is applied.

## Production sequence

1. Accept a selected signal and validate its target against the actual recipe/session/plan version.
2. For an ambiguous negative response, request a scope or keep it recipe-specific; do not infer an ingredient allergy.
3. Persist the feedback event atomically with an outbox message.
4. Apply the deterministic memory rule to the relevant soft preference and expose the resulting memory ID.
5. A replacement or deletion supersedes/retracts the previous signal and recomputes its contribution; do not stack conflicting responses indefinitely.

## Data and API contracts

createFeedback: POST /v1/feedback with Idempotency-Key.

    {"cookSessionId":"00000000-0000-4000-8000-000000000051","effort":"tooMuch","target":{"kind":"preparation","tag":"chopping"}}

Return canonical Feedback with id/version and submitted signal fields; affected memories are read through their own API. PATCH /v1/feedback/{feedbackId} and DELETE the same resource use If-Match and ownership checks. UI labels map to makeAgain=true, effort=tooMuch or taste=notForMe; positive enjoyment can use taste=loved and an explicit target. FeedbackTarget.kind distinguishes cookSession, plan, recipeVersion, ingredient, taste or preparation; resource IDs and tags follow its schema. At least one signal and a valid session or target are required. A standalone recipeVersion target permits feedback without logged cooking; a scoped ingredient/preparation target must be consistent with its associated owned plan/session. Free text is optional and never becomes a hard exclusion automatically.

## Permissions and lifecycle

Feedback is private to the account or guest. It is not a recipe rating visible to the creator and does not notify a friend. Store only documented signal history needed to support editing, provenance and deletion. Removing feedback removes its memory contribution unless another explicit source independently supports that memory. Account export must distinguish raw feedback from derived preferences.

## Failure and offline behavior

Save feedback locally first and queue idempotent account sync. Show Pending sync without blocking Done. A stale edit returns 412 with the current response and lets the person choose their intended final state. If a source recipe disappears, retain only the minimum private target context permitted by deletion policy and avoid broken public links. If memory projection fails, retain the accepted event, mark personalization pending and retry from the outbox.

## Integration and dependencies

F12 provides optional session context, F14 may combine saving with make_again, F16 defines deterministic projection and F18 exposes editing. F39 prevents social leakage; F54 monitoring observes projection lag without raw notes.

## Execution plan

- Define scoped signal types and source-target validation.
- Implement feedback create/edit/retract plus outbox-based memory recomputation.
- Build FEEDBACK with skip and precise confirmation copy.
- Add local pending queue and emit feedback_submitted, feedback_skipped and feedback_projection_delayed as separate events.

## Acceptance and release gates

Test Done without feedback, negative meal feedback without ingredient exclusion, edited conflicting signals, outbox replay, duplicate taps and offline submission after account deletion. Confirm skipping does not change ranking and raw notes are absent from analytics. Roll out feedback independently of personalization; a memory-engine kill switch can preserve submitted editable feedback while temporarily stopping its ranking effect.
