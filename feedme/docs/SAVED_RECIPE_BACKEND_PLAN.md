# Basic saved-recipe backend plan

Status: IMPLEMENTATION / VERIFICATION IN PROGRESS in the [seventh batch](PARALLEL_PROGRESS_COOKBOOK_TIMERS.md). The store, V006 and configured HTTP adapter are being implemented; focused tests are not full acceptance. The sixth source-frozen checkpoint is historical. [BUILD_STATUS.md](BUILD_STATUS.md) remains the evidence pointer.

## Scope and existing components

[F19](../../outputs/biteclub_blueprint/features/F19.md) makes basic saving, opening, searching and removing private recipe copies first-release features. [F14](../../outputs/biteclub_blueprint/features/F14.md) adds an explicitly chosen Make Again signal; ordinary Save and cooking completion do not imply that signal. [F30](../../outputs/biteclub_blueprint/features/F30.md) separately authorizes social copies. [F45](../../outputs/biteclub_blueprint/features/F45.md) defers custom collections, multiple-collection organization, manual ordering and enhanced filtering. This package must not enable F45, paid packs, households or Tonight.

The initial backend component is owned-plan/catalog Save plus the default private cookbook. It is deliberately not a claim that all F19 social-copy, offline and lifecycle acceptance is complete.

- [SavedRecipeRepository](../shared/kitchen/src/commonMain/kotlin/com/feedme/kitchen/SavedRecipeRepository.kt) already downloads `getSavedRecipe`, stores owner-scoped encrypted content, searches local titles, checks exact content/version compatibility, permits only monotonic provenance removal and fences learned recall. It performs no save, delete or remote enumeration. Its 512-entry bound is a local cache bound, not a server/free-tier save quota; its digest is not an authenticated server content manifest.
- [PlansStore](../server/src/main/kotlin/com/feedme/server/planning/PlansStore.kt) persists immutable Plans and current authority evidence. Its cooking seam distinguishes new selection from an actual existing cooking pin. It currently rejects `createPlan(savedRecipeId=...)` as unconfigured.
- [CanonicalPlanningAdapter](../shared/planning/src/commonMain/kotlin/com/feedme/planning/CanonicalPlanningAdapter.kt) materializes the actual reviewed/scaled `recipeSnapshot`. A scaled private snapshot is not a new published catalog version.
- [CookingStore](../server/src/main/kotlin/com/feedme/server/cooking/CookingStore.kt) retains exact Plan/proof/evidence pins and currently rejects `completeCookSession` with `makeAgain=true`. [CookingFlowController](../shared/mealflow/src/commonMain/kotlin/com/feedme/mealflow/CookingFlowController.kt) deliberately submits `makeAgain=false`. Neither is a Save implementation.

## Exact six-operation boundary

The [canonical OpenAPI](../../outputs/biteclub_blueprint/architecture/04_API_Contract.json) controls transport shapes and security. Do not add endpoints, fields, headers or pagination parameters from prose alone.

| Operation | Canonical route | Success and controls |
| --- | --- | --- |
| `saveRecipe` | `POST /v1/saved-recipes` | `201 SavedRecipe` + ETag; Idempotency-Key; UserBearer or GuestBearer |
| `listSavedRecipes` | `GET /v1/saved-recipes` | `200 SavedRecipePage`; optional q, cursor, limit; UserBearer or GuestBearer |
| `getSavedRecipe` | `GET /v1/saved-recipes/{savedRecipeId}` | `200 SavedRecipe` + ETag; UserBearer or GuestBearer |
| `deleteSavedRecipe` | `DELETE /v1/saved-recipes/{savedRecipeId}` | `204`, no body; Idempotency-Key + If-Match; UserBearer or GuestBearer |
| `listCollections` | `GET /v1/collections` | `200 CollectionPage`; optional cursor, limit; UserBearer or GuestBearer |
| `getCollection` | `GET /v1/collections/{collectionId}` | `200 Collection` + ETag; UserBearer or GuestBearer; canonical cursor/limit item pagination |

The reviewed canonical alignment adds optional nullable `Collection.nextItemCursor`. Absent means legacy complete IDs, null means terminal item page, and a string requires continuation of the same collection/version. `listCollections` embeds bounded first item pages; its outer nextCursor still pages collections. Current guest read access aligns with the existing guest list/save/read operations, retaining exact owner authorization and account-only custom organization. There are still exactly six operations, not a new collection-management feature.

Account requests require the verified registered `X-Device-Session`; a valid guest omits that header and uses an internally verified bounded guest identity, not a client-asserted local origin. All path IDs require current ownership. Query q has a 100-Unicode-scalar bound; cursor is opaque, principal/filter-bound and at most 2,048 characters; limit is 1–50, default 20. An opaque cursor is never authorization. Do not add conditional 304 behavior where the operation does not declare it.

`SaveRecipeRequest` permits planId, recipeVersionId, title (maximum 120 characters), collectionId and markMakeAgain, and requires at least one source via `anyOf`. `SavedRecipe` returns the existing id/version/timestamps/title/snapshot/sourceType/recalled fields and applicable license/provenance. It has no `created`, preferenceSignalId, authorization receipt or manifest field. Only ownPlan/catalog sources are implemented by this first component; postGrant/personal are not fabricated.

The six operations do not create custom collections, edit collection metadata, change ordering, attach to arbitrary custom collections or acquire social grants. An explicitly supplied collectionId is checked for ownership and for the supported default-cookbook capability; unsupported organization remains unavailable, not silently redirected.

## Implementation choices supported by the contracts

These are proposed implementation decisions, not already-landed behavior:

1. Create a concrete owner-scoped default collection within the first successful authorized Save transaction (or explicit trusted provisioning), never during a GET. Before any Save, list reads may be empty. Its localized display name comes from explicit application configuration, not a guessed locale or global shared ID. Default collection deletion is not enabled.
2. If both source IDs are supplied, resolve the Plan and require its pinned recipeVersionId to equal the supplied recipeVersionId; reject disagreement. `anyOf` does not justify silently preferring one ID or rejecting all otherwise-consistent two-ID requests.
3. Copy the exact authorized materialized recipe snapshot, not the whole Plan, private constraints, explanation facts, source media, comments or a freshly regenerated catalog body. Store its immutable content hash and source authorization/proof separately. A plan-based Save is a copy-rights decision, not a new meal-ranking decision; it must not unnecessarily require today's preferences to match the old meal.
4. Initial title uses the supplied title when present, otherwise the pinned recipe title. A duplicate Save does not silently rename an established copy. A conflicting explicit title needs an honest conflict rather than an undeclared rename; the current local repository treats title as immutable at that saved identity.
5. Absent/false markMakeAgain records no feedback. Until save-plus-feedback and retract/undo dependencies exist, true remains explicitly unconfigured. Never ignore true and return a success that omitted its requested effect.
6. Established copies are their own private authorization roots. Current ownership, revocation/deletion of that owner and audited recall still apply, but ordinary source retirement, future grant withdrawal or loss of paid organization cannot erase basic access. A fresh copy still requires actual current copy permission; a cooking pin alone is not that permission.

## Persistence and transaction composition

Use the existing [PgTransactions](../server/src/main/kotlin/com/feedme/server/db/PgTransactions.kt), [DurableCommands](../server/src/main/kotlin/com/feedme/server/db/DurableCommands.kt) and [OutboxStore](../server/src/main/kotlin/com/feedme/server/db/DurableEvents.kt), with a new expand-only migration after the existing versions. Preserve prior migration bytes/history. The [data model](../../outputs/biteclub_blueprint/architecture/03_Data_Model.md) already defines memory.saved_recipes, memory.collections and memory.collection_items; this plan adds no canonical transport fields.

Production composition needs a mandatory current principal/session authority and a mandatory licensed source/copy/recall authority. Neither has an accepting default, fabricated reviewed catalog or test credential implementation in main. The configured HTTP adapter remains optional; default service startup stays closed. Reuse the same exclusive principal lifecycle lock as planning, kitchen and cooking.

Proposed lock order: current principal/session → original command receipt → source Plan lineage or exact catalog/copy-rights/recall state → default/target collection → saved identity/membership. Lifecycle writers and future erasure/recall workers must share that ordering. Source callbacks operate on the supplied connection and must not commit, open a second transaction or perform unbounded provider/network work under locks.

Save atomically writes or deduplicates the immutable copy, creates the default membership, advances affected resource versions, writes the original-key receipt and appends registered outbox facts. Exact replay re-authorizes the current owned copy/recall state before disclosure and causes no duplicate copy, membership, signal or outbox effect. It must not recast an established copy as a fresh acquisition merely because its old source is now retired. A new copy cannot exploit that replay rule.

The deduplication key must retain authorized source identity and materialized content hash: different reviewed scaling cannot collapse merely because recipeVersionId matches. The data model's `(principal, source_type, source_id, recipe_hash)` uniqueness is the starting point; the cross-path source-ID issue below must be settled before DDL is frozen. Content/proof and mutable attribution/availability belong in separate fields. Same version cannot certify changed metadata, removed provenance cannot casually reappear, and the client must never receive a different recipe under the old immutable identity.

Deletion is an explicit owned mutation, not a catalog-selection operation: removing an unavailable or recalled copy must remain possible. Delete memberships and make the save unavailable atomically with its receipt and required invalidation facts. Preserve compact command/incarnation information so the old delete receipt cannot acknowledge a later re-save, and a stale Save retry cannot resurrect deleted content. Missing deletion succeeds only for its exact recorded command; arbitrary missing IDs are not success. A new authorized re-save needs a new saved identity/incarnation, not silent reuse of a deleted resource.

Plan/cooking TTL and saved-copy lifetime are different. Persist the copy's own authorization evidence; do not make an established save depend on a live expired planning/cooking row or use that independence to authorize a new copy. Retain another legitimate cooking/local reference when removing a save; do not broadly delete shared recipe bytes. No purge/erasure worker is implied by a tombstone. The data-model retention proposal is until owned deletion/erasure or applicable audited recall, subject to actual guest lifecycle and launch-market review—not a new forever-retention or compliance claim.

The [event registry](../../outputs/biteclub_blueprint/architecture/05_Events.md) provides `memory.recipe.saved.v1` (principalId, savedRecipeId, sourceType), `memory.collection.changed.v1` (principalId, collectionId, action) and, for the later explicit-signal transaction, `memory.feedback.changed.v1` (principalId, feedbackId, action). Do not put titles, recipe content, user notes, bearer values or private source profiles into those events. A worker/consumer is not implemented merely because its outbox fact exists.

## Bounds and genuine cross-contract gaps

- **Default-collection representation:** F19 prose says paged collection items; OpenAPI `getCollection` has no cursor/limit and returns a complete unbounded savedRecipeIds array. `CollectionPage` also embeds that representation. Do not invent item paging, truncate IDs, or limit basic saves to fit a response. Basic cookbook retrieval can use bounded `listSavedRecipes`, but scalable complete collection reads need a reviewed contract/response-policy resolution before this six-operation component can claim unrestricted acceptance.
- **Response admission:** SavedRecipePage embeds full snapshots. Fix an explicit service/HTTP/client-compatible byte policy before implementation, and admit each new snapshot with enough page-envelope budget before committing. Return fewer than limit with the exact next cursor when a page budget is reached; never issue an unusable cursor or skip the first over-budget item forever. The chosen cap must accommodate existing valid responses, not discover an already-committed success is unreadable. No arbitrary 512/1,000 free-save quota follows from client cache/manual-order bounds.
- **Cross-path deduplication:** F14 emphasizes principal/authorized source-version dedup; the data table additionally keys source_type/source_id/hash. OwnPlan can mean an origin Plan or the underlying reviewed recipe version, and catalog/ownPlan paths can resolve identical bytes. Define which paths share a save identity while preserving provenance and distinguishing materialized variants; do not assume a plan UUID or recipe UUID alone settles this.
- **Save deletion/invalidation:** The registry names save creation, collection change and recall, but no explicit saved-copy deletion event. Resolve the required consumer invalidation/action schema through canonical registry review; do not label deletion as another Save or claim cross-device purge from an unimplemented consumer.
- **Make Again and Undo:** There is no dedicated atomic undo endpoint or SavedRecipe response signal ID. FeedbackTarget has no savedRecipe kind. Use documented plan/recipeVersion/session targets plus explicit internal linkage only after resolving variant identity, signal retraction, and “newly saved by this action and not subsequently reused.” Do not invent a route or delete a reused save to approximate Undo.
- **Manifest/offline authority:** F19 mentions a content manifest, but SavedRecipe has no manifest field or dedicated route here. Local digest/schema validation is not server-authenticated license/review/recall evidence. Keep the manifest/complete-authorized-bundle gap explicit.
- **Guest collection detail:** OpenAPI allows guests to list collections but not getCollection. Preserve that boundary; do not infer guest detail access from the more general F19 prose. Guest-to-account attachment is separate explicit lifecycle work, not ID reuse or automatic merge.

The team can resolve protocol, bounds and event choices before implementation. Real provider configuration, licensed/editorially reviewed sources, audited recall, guest attachment and operational/legal retention are external launch authorities; tests cannot choose or fabricate them.

## Small implementation tasks and acceptance

1. Freeze the six-operation contract decisions and production authority/connection/byte-policy interfaces. Add the minimal owned-copy/default-membership migration and exact historical checksum/upgrade tests. No custom-collection capability.
2. Implement Save/list/read/delete/default-collection reads with real PostgreSQL, exact immutable pins, ownership, response admission, original-key receipts, deletion incarnations and registered outbox facts. Keep true markMakeAgain and unsupported source grants explicitly unavailable.
3. Add optional canonical HTTP ingress and actual `SavedRecipeRepository` download compatibility. Real-PG/Ktor tests must cover scaled Plan fidelity, same/new-key dedup, conflicting title/source IDs, unknown COMMIT and cancellation, concurrent Save/delete/recall, guest/account isolation, foreign collection IDs, retired-source established reads, delete/re-save/old-retry fences, Unicode/cursor/response bounds, provenance redaction, zero copied media/comments and unchanged source migrations. Label synthetic identity/catalog/CAS fixtures as test-only. Add client writer/UI consent and original-intent reconciliation separately; a download repository alone does not prove that journey.
4. Follow with explicit F14/F15 save-plus-signal and create/update/deleteFeedback transactions, exact current target validation, no duplicate signal, safe retraction and dependency-aware Undo. Only then consider enabling markMakeAgain=true or composing it with CookingStore's same-connection completion transaction. Completion still preserves server progress and never implies Save when false.
5. Follow with owned-save reuse through existing `createPlan(savedRecipeId)` and the existing planId-based CookStart. Fresh planning checks current inputs and review/recall while accepting the established copy as its own private source-rights root. Never invent a savedRecipeId field on CookStart or convert a saved private variant into a published catalog recipe. This is basic reuse, not deferred Tonight, households or packs.

Full F19/F14 release additionally requires the remaining F30 social grant/revocation/deletion race proofs, actual provider/editorial adapters, recall synchronization, signed offline authority where required, user-visible Save/Make Again consent and acknowledgement, retained-reference cleanup, guest attachment, accessibility and operational deployment. New-write kill switches must preserve established readable copies and owned deletion. No implementation, test count or release completion is asserted by this plan.
