# F02 — Smart Meal Helper

Phase: first release. Owner module: planning.

## Strategy

Reduce the decision of what to eat to one useful recommendation. The helper must work before social signup and with partial pantry information. Language interpretation is a convenience for collecting constraints, not the source of recipe truth. The same reviewed catalog and deterministic matching serve typed requests and form input.

## Experience and screen design

HOME keeps Help me make something visible beside the bounded friend collection. REQUEST contains a short ordinary-language field, ingredient chips, time and energy summaries, and Find a meal. Example placeholder: “Ten minutes, very tired, bread and yogurt.” Parsed constraints appear as editable chips before a recipe is accepted. Ambiguous ingredients or conflicting instructions receive an inline clarification, with PANTRY and EFFORT as manual alternatives. RECOMMENDATIONS shows one primary meal with actual preparation and missing ingredients; primary View recipe, secondary Make it easier and Something else. No match occupies the same card area and names a constraint the user can choose to revise.

## Production sequence

1. Create or retrieve a bounded guest/account planning context.
2. Interpret free text into a strict schema with unknown terms retained for confirmation. Disallow tool execution and invented recipe bodies.
3. Merge confirmed inputs with explicitly saved preferences; hard exclusions win over contradictory text.
4. Filter published catalog versions by recipe mode, exclusions, availability, equipment and hard time/effort limits.
5. Rank feasible recipes with a versioned deterministic policy, persist the input snapshot and return one result plus an opaque continuation cursor.

## Data and API contracts

createPlan: POST /v1/plans with Idempotency-Key. Input contains structured constraints and mode, with optional naturalLanguage, confirmedInterpretation and preferenceVersion.

    {"mode":"auto","naturalLanguage":"ten minutes, bread and yogurt","constraints":{"ingredientIds":[],"maxTotalMinutes":10,"energy":"assemble","equipmentIds":["bowl"],"servings":1,"hardExcludedIngredientIds":[]},"confirmedInterpretation":false}

Return Plan.id, version, status, constraints, interpretationCandidates, recipeSnapshot when ready, changes, reasons and catalogRevision. needsConfirmation returns no cookable result until ambiguous required constraints are resolved; noMatch is a successful domain response. Internal request hashes/ranking-policy versions are persisted for reproducibility and are not arbitrary client fields. GET /v1/plans/{planId} reads only a principal-owned plan. Use the canonical typed error schema and request correlation identifiers. Never put raw request text into telemetry. Bound request length, candidate traversal and guest usage to prevent uncontrolled compute.

## Permissions and lifecycle

Guest tokens authorize their own plans and cached catalog access, not social objects. Account attachment requires an explicit merge flow and does not treat local IDs as trusted ownership. Retain raw interpretation input only for the documented minimum operational purpose; retain the confirmed structured snapshot needed to explain a plan. Users may discard a request without changing lasting taste memory.

## Failure and offline behavior

If language interpretation times out, keep the user's text and reveal manual constraint controls. Catalog matching remains available when the language provider is disabled. A server timeout may be retried with the same key; show resolving status rather than duplicate results. Offline REQUEST can hold a local draft and display downloaded recipes, clearly identifying that current server matching is unavailable. Missing preferences revision requires refresh, never silently dropping exclusions.

## Integration and dependencies

Consumes pantry, profile, catalog and memory read models. F17 explains ranking from stored decision facts. F53 handles deep links and local drafts. No social membership, purchase or notification permission is required for a first recommendation.

## Execution plan

- Define shared ConstraintSnapshot and PlanState sealed types.
- Build schema-limited interpretation adapter with deterministic manual fallback.
- Implement filter-before-rank pipeline and fixture corpus covering conflicting constraints.
- Add HOME → REQUEST → RECOMMENDATIONS → RECIPE navigation and state restoration.
- Emit helper_request_started, helper_plan_resolved and meal_accepted, separating clicks from reported cooking.

## Acceptance and release gates

Verify hard exclusions survive adversarial or contradictory text, unsupported ingredients are never presented as validated matches, manual input works during provider failure, and another guest cannot read a plan. Proposed usability target: an acceptable meal within a minute, to be tested rather than claimed. Roll out helper_matching separately from language_interpretation; disable interpretation without disabling manual planning or saved recipes.
