# F14 — Make Again

Phase: first release. Owner modules: memory, catalog; collection storage.

## Strategy

Capture a deliberate “this is worth repeating” with one optional action. Save the actual recipe version the person chose and remember its usefulness for similar circumstances. A Make again action is a preference signal, not proof of completion and not authorization to share publicly.

## Experience and screen design

MEAL_DONE and RECIPE offer Make again; a result card may expose the same action after acceptance. On success, the label becomes Saved for next time with View cookbook and an Undo action. If a shared recipe disallows copying, explain that a private copy cannot be saved and offer Ask for recipe; do not disguise a bookmark as a durable recipe save. MEMORY_DETAIL separately manages the ranking preference. Saving a prepared-meal addition can retain its base-meal type and sensory choice so the next suggestion is contextual.

## Production sequence

1. Resolve the pinned recipe or variant and determine save authorization: catalog rights or a valid F30 grant.
2. In one durable operation, create/deduplicate the immutable recipe-only copy and record an explicit make_again signal tied to the resulting private recipe identity.
3. Append outbox events for collection and memory projections in the same database transaction.
4. Return the saved record immediately; show pending personalization only if the projection has not applied.
5. Undo removes the new preference signal and, only if newly created by this action, the new save after confirming no other user action now depends on it.

## Data and API contracts

saveRecipe: POST /v1/saved-recipes creates a private app-recipe save from a pinned planId or recipeVersionId, with Idempotency-Key and optional markMakeAgain. addCollectionItem: POST /v1/collections/{collectionId}/items attaches an existing savedRecipeId; it never acquires missing source rights. The default cookbook has a concrete owner-scoped collectionId. For a new creator-granted social copy, savePostRecipe uses POST /v1/posts/{postId}/recipe-saves and atomically creates the grant receipt, private copy, requested collection membership and optional explicit signal. Save operations accept markMakeAgain only when the user chose this named action; a generic Save never implies enjoyment. For an already-saved recipe, createFeedback POST /v1/feedback records the explicit make_again signal without another copy.

    {"collectionId":"00000000-0000-4000-8000-000000000041","recipeVersionId":"00000000-0000-4000-8000-000000000021","grantPolicyVersion":3,"markMakeAgain":true}

The example is the social savePostRecipe body; the path identifies the source post and the server resolves its active attachment. Return canonical SavedRecipe with id, version, snapshot, sourceType and applicable grant/provenance fields; do not require undeclared created or preferenceSignalId response fields. The transaction records the makeAgain signal internally, which is inspectable through memory/feedback reads. Server validation ignores a caller's asserted grant validity. Deduplicate by principal and authorized source content version; replaying a request must not create repeated memories. Existing saves can gain explicit feedback without duplicating content. Delete/undo operations use If-Match and their own mutation key, preserving a record reused since the original action.

## Permissions and lifecycle

Recipe-only copies follow F30: future grant revocation stops new copies, existing authorized copies remain except safety/legal recall, and creator identity is removed when required. No media/comments are copied. Guest users can keep a local private favorite for eligible catalog content; account sync requires explicit attachment. Paid library upgrades never remove basic access to this saved recipe.

## Failure and offline behavior

If saving times out, retry the same idempotency key and reconcile with the server record. A grant revoked before the transaction commits returns SAVE_NOT_ALLOWED; do not claim success. Offline eligible downloaded catalog recipes may be saved locally pending account sync; a new community copy requiring an unvalidated grant remains pending until online. The UI distinguishes Saved locally, Sync pending and Saved. Recall invalidates use even if an earlier save operation succeeded.

## Integration and dependencies

F19 owns cookbook access, F15 signal vocabulary, F16 preference projection, F18 editing, F30 rights and F43 optional participation. The save action is distinct from F25 Your Take publication and F12 meal completion.

## Execution plan

- Implement save-plus-signal transaction and content-version deduplication.
- Add immediate/queued save state and safe undo conditions.
- Build guest/account merge with duplicate detection.
- Emit make_again_requested/saved and save_grant_rejected; do not infer that a meal was eaten.

## Acceptance and release gates

Test duplicate taps, a lost response, grant revocation race, existing save plus new signal, undo after collection editing, offline guest merge and content recall. Assert zero copied source media and no social notification by default. Release make_again after grant and deletion tests pass; disable new writes if inconsistent while keeping all established private recipes readable.
