## Why this package exists

This advances the integrated failure matrix beyond the older same-process close/reopen tests. Interrupted pending setup remains a recovery gate, not automatic sign-in or erase.

Low-level credential and data plans alone remain insufficient: selected replay is not automatically a new disk-sync acknowledgement. The independent-ledger task removed unknown-outcome/readback promotion from credential, retirement and work callers. ## Required ordering

1. Acquire a real verified FeedMe identity using approved immutable configuration. Provider failure or cancellation leaves no selected setup.
2. Under the single session owner, inspect exact existing idle/predecessor states and prepare credential, private-data and work-origin plans. A generated ID is not a reservation.
3. Commit one composite intent to the independent control store and obtain a successful durability acknowledgement. An unknown result retains repair state and permits no downstream effect.
4. Select only the planned credential incarnation, private-data generation/key and empty work origin. Do not regenerate a missing selected key or replace an unresolved plan.
5. Persist and verify the exact private activation binding. No application screen, worker, transport request or timer receives an active lease during this stage.
6. Acknowledge completed setup in the control ledger only after the binding and all component identities agree. Then activate the process lease and construct the runtime access object. If interruption happens after durable completion but before lease publication, restore still requires the real identity verifier and exact binding.

The selection-only `begin`/`retry` API still implements steps2–4 and leaves `PendingSetup` intact. The integrated runtime now follows it with `complete`, which implements binding/seal/acknowledged completion before publication. Selected-data replay itself remains a no-op durability limitation; the changed binding write supplies the missing acknowledgement. Neither stored plans nor a readable Complete recreate verified live authority.

The work registry's lease-free planning/selection/seal operations must never be replaced by a fabricated early lease. Sealing preserves exact setup provenance until ordinary resume/lifecycle use consumes it. Task6c now confirms and coordinates exact abort on already-open stores; startup ownership remains6d. Ordinary snapshot or cleanup cannot substitute for acknowledged sealing or confirmed abort; callback admission is not relaxed.

## Recovery rules

Inspection is not consent. A selected/consumed/aborted observation may help choose a safe next action, but it cannot replace a required write acknowledgement. Continue a live verified create only with its retained exact plans and appropriate verified credentials; on restart, absence of those credentials is an explicit recovery requirement, not permission to invent them.

Confirmed abort owns only the resources named in the composite intent. Each cleanup operation revalidates exact scope, incarnation/generation/origin, emptiness and competing references. Completed steps retain their consumed fences and re-acknowledge as required; later retries never expand the target set. Newly written records, tombstones or work entries prevent empty-only abort even if an earlier inspection was empty. Unknown files and keys are preserved for a separate repair protocol.

No recovery control journal may be cleared until every required component has acknowledged completion and every owned recovery handle has closed successfully. Live create instead retains the application's lifetime stores while publishing access; it does not close those active stores as a completion step. [Retained owner components](STARTUP_RECOVERY_OWNERS.md) keep partial opening and retryable cleanup accessible. The [owned coordinator](OWNED_STARTUP_RECOVERY.md) now retains ALL-ABORTED evidence and close acknowledgements through fresh Complete; product-root integration remains. Ambiguous platform-close errors and old value-returning factory paths can still retain a native reservation until process exit. Public private-data recovery rejects rollback journals/WAL/SHM and requires API27+. None of this silently removes those gates.

## Integration boundaries

Identity provider/bootstrap selection, approved app IDs, native login/recovery screens, production workers/timers, server ownership and lifecycle, reviewed content, social safety, purchases, API26, full Xcode/iOS, physical devices and publication remain separately tracked. The public GitHub repository is a frozen development snapshot, not a deployment or automatic publication target for this new work.
