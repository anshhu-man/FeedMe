# F06 — Taste and Texture

Phase: first release; Heat enters only with reviewed launch content. Owner modules: planning, catalog.

## Strategy

Give FeedMe users optional taste and texture guidance without making them learn nutrition categories. A desired sensation helps choose an addition or meal: Crunch, Fresh, Creamy or Heat. These are descriptive taste goals, not health scores. A sensation remains a soft goal unless the user deliberately selects it as the point of an addition; hard exclusions, equipment and preparation limits always take priority.

## Experience and screen design

TASTE opens as an optional screen from REQUEST or ADAPT. Four selectable cards use text as well as visual cues. Heat is described as spice, avoiding confusion with cooking temperature; Fresh describes a sensory effect and never certifies freshness. Include No preference and a clear Continue action. RECOMMENDATIONS or VARIANT carries a small sensory label and a literal description, for example “A crisp topping.” The user can remove a taste choice without restarting ingredient entry. No suitable sensory match yields a clear explanation and an invitation to change the choice rather than a mismatched result disguised as success.

## Production sequence

1. Accept the optional selected sensation in constraints.tasteTags and preserve the rest of the snapshot.
2. Filter out recipes and additions failing hard requirements.
3. Match sensory tags authored for the finished recipe or a reviewed addition, not arbitrary ingredient stereotypes.
4. Rank exact sensory matches above partial matches using deterministic policy; identify a partial match explicitly if the user elects to see one.
5. Persist the selected sensation with the plan. Store lasting memory only through optional feedback or saving.

## Data and API contracts

createPlan POST /v1/plans or adaptPlan POST /v1/plans/{planId}/adaptations carries constraints.tasteTags containing the selected crunch, fresh, creamy or heat value; an empty array means No preference. RecipeVersion.tasteTags and authored summary/reason text explain the sensation. Heat may have an editorial mildness description in reviewed copy, never a universal tolerance guarantee.

    {"mode":"improve","baseMeal":{"description":"prepared noodles","preparationState":"alreadyPrepared","ingredientIds":["00000000-0000-4000-8000-000000000011"]},"constraints":{"ingredientIds":["00000000-0000-4000-8000-000000000012"],"energy":"assemble","equipmentIds":["bowl"],"servings":1,"hardExcludedIngredientIds":[],"tasteTags":["crunch"]}}

Return achieved tags in the pinned recipeSnapshot.tasteTags and an explicit tasteFit reason where supported; related options must be described as related in authored reason copy. An empty current selection means unrestricted sensory ranking and does not erase saved taste memories. Matching requests use normal plan idempotency and If-Match version rules. Invalid tags return 422 with allowed values, not an invented category. Editorial tags are versioned alongside recipe instructions.

## Permissions and lifecycle

Sensory choices are private planning inputs. Choosing Heat must not be published as a profile attribute. Clear current choice differs from Forget learned preference in MEMORY_DETAIL. The original preview supports Crunch/Fresh/Creamy; the spec includes Heat conditionally, so product copy and feature configuration must not imply an unimplemented option is already live.

## Failure and offline behavior

Retain selected chips during navigation and failed requests. Offline users can filter cached reviewed recipes by existing sensory tags, but no new adaptation is represented as server-validated. When a tag is withdrawn with a content revision, an old pinned recipe can remain readable unless recalled, while new matching uses current tags. An ingredient unavailable event delegates to Keep the Vibe instead of dropping the desired sensation silently.

## Integration and dependencies

F10 preserves sensory intent through substitutes; F07 applies it to additions or full meals. F15/F16 feedback can connect enjoyment to a specific sensation. F51 editorial review owns tags and explanations.

## Execution plan

- Add sensory enum, authored catalog fields and deterministic match fixtures.
- Build accessible TASTE cards with deselection and state restoration.
- Render exact/related labels and no-match actions on result screens.
- Emit sensory_intent_selected and sensory_match_unavailable using category codes only.

## Acceptance and release gates

Verify Crunch never overrides an exclusion, Fresh never creates a freshness claim, No preference preserves unrelated inputs, and substitutions report the resulting sensation accurately. Test all enabled categories against approved content. Ship sensory_choices independently of sensory_heat; rollback removes unsupported choices while keeping existing saved combinations accessible.
